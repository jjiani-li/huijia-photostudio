## 5. 关键流程与状态机

### 5.1 `POST /api/generations` 完整校验顺序

**顺序即契约**，与 `spec/03-接口契约.md` §3.5 的表逐条一致；任一步失败立即 `throw new AppError(...)`，不进入下一步。

| # | 条件 | 错误码 | 检查依据 |
|---|---|---|---|
| 1 | 当前用户 `users.verified_at IS NULL`（未实名） | `REALNAME_REQUIRED` | `spec/06-合规与风控.md` §5.2；`RN-01` |
| 2 | `count` 不在 {2,3,4} | `INVALID_PARAM` | 请求体 `count` |
| 3 | `eraCode` / `sceneId` 不存在或 `is_active=0` | `INVALID_PARAM` | `eras.is_active`、`scenes.is_active` |
| 4 | 锚点不属于当前用户 | `ANCHOR_NOT_FOUND` | `identity_anchors.user_id` |
| 5 | 锚点 `status != 'succeeded'` 或 `confirmed_by_user != 1` | `ANCHOR_NOT_CONFIRMED` | `spec/01-领域模型与数据库.md` §2.1；`SEC-01` |
| 6 | `consents` 中 `photo_usage` 不存在或已吊销 | `CONSENT_REQUIRED` | `consents.revoked_at IS NULL`；`SEC-03` |
| 7 | 今日 `usage_counters.images + count > users.daily_image_quota` | `QUOTA_EXCEEDED` | `day = dayKey()`；`SEC-04` |
| 8 | 该用户已有非终态 `generations` | `GENERATION_IN_PROGRESS` | `status IN ('queued','running')`；`SEC-05` |

第 1 步排在最前是硬约束：未实名时不进入后续校验、**不产生任何写操作**（`RN-01`）。表中未列出的第 0 道关卡由 `src/server/http/validate.ts` 承担：zod 解析请求体（`anchorId` 正整数、`eraCode` 字符串、`sceneId` 正整数、`count` 可选整数），失败同样是 `INVALID_PARAM`（带 `details.fields`），**发生在第 1 步之前**。第 4 步返回 `404 ANCHOR_NOT_FOUND` 而非 403（`API-04`：避免探测他人资源）；第 7 步必须在任何写操作之前完成（`SEC-04` 要求失败时**不产生 `generations` 行**）。M1/M2 期间没有真实登录流程，第 1 步与第 7 步以 `tickets/T02-数据层：迁移、schema 与种子数据.md` 种子植入的固定 `DEV_USER`（已实名、`verified_at` 非空）通过，真实登录与实名门槛在 `tickets/T12` / `tickets/T19` 接管（`spec/08-本地开发指南.md` §3.2）。prompt 阶段的内容审核（`422 CONTENT_REJECTED`，拼装完成、入队之前，同样不产生 `generations` 行、不预扣额度）不在本序列内，归 `modules/M07-生成后复核与内容审核.md` §5.6。

### 5.2 `createGeneration` 编排步骤

入口签名：`export function createGeneration(input: { userId: number; anchorId: number; eraCode: string; sceneId: number; count: number; }): GenerationRecord;`

1. **查锚点与配置** —— `anchors.findById(anchorId)` 断言 §5.1 第 4/5 步并取出 `anchor_text`（为空即 `ANCHOR_NOT_CONFIRMED`，`spec/05-Prompt工程.md` §2.1：【身份锚点】段缺失即拒绝生成）与 `preprocessed_photo_id`；`config.getEra(eraCode)`、`config.getScene(sceneId)` 断言第 3 步；`preprocessed_photo_id` 为 NULL 时按 `reference_photo_ids = []` 处理。
2. **解析组合档案** —— `config.getProfile(eraCode, sceneId)`，命中 `era_scene_profiles` 行则把其 `id` 与 `prompt_override` 写入；未命中（含 `is_active=0`）时两者均 `NULL`。
3. **调 `buildPrompt({ anchorText, era, scene, profile })`** → `{ prompt, promptHash, templateVersion }`；段落顺序、正面化约束、长度 warn 全由该函数负责（`spec/05-Prompt工程.md` §2、§9），本文件不修改其输出；`prompt_hash` 直接取返回值，**不另行计算**，否则 `E2E-03` 的逐字符相等断言被破坏。
4. **单事务写入** —— 落库字段：`user_id` / `anchor_id` / `era_code` / `scene_id` / `profile_id`；`reference_photo_ids`（预处理图 id 数组，本期恰 1 个元素，`E2E-04`）；`prompt` / `prompt_hash` / `template_version` / `era_pack_version = era.packVersion` / `scene_pack_version = scene.packVersion`；`model = ARK_IMAGE_MODEL`；`params_json`（`size` 取 `eras.default_size`、`output_format = 'png'`、`watermark = WATERMARK_DEFAULT`、`provider = PROVIDER`）；`requested_count`；`status = 'queued'`；`attempt = 0`；`created_at = nowIso()`。事务内的执行顺序固定为：① `checkActiveByUser(userId)` —— §5.1 第 8 步的排他复查，`> 0` → `throw new AppError('GENERATION_IN_PROGRESS', '上一组还在生成，稍等一下', 409)`；② 额度复查 —— `usageRepo.deduct` 的前置校验（`dayKey()` 当日 `images + count > users.daily_image_quota` → `QUOTA_EXCEEDED`），通过后 `usageRepo.deduct(userId, dayKey(), count)`（`generations += 1`、`images += count`）；③ `INSERT generations`；④ `auditRepo.write({ action: 'generation.create', target: 'generation:<id>' })`。
5. 返回 `GenerationRecord`（含 `params`），由 route handler 转成 `Generation` 形状。`size` 的取值与「总像素 ≥ 3,686,400」校验见 `modules/M05-年代场景配置与Prompt拼装.md` §5.2，属本次赋值的守卫，**不新增校验步骤、不改变 §5.1 的顺序**。§5.1 的第 1–7 步在事务**之外**先跑一遍（快速失败、不产生写操作），第 8 步的排他检查在事务**内、`INSERT` 之前**执行（否则刚插入的 `status='queued'` 行会被自己数进去，每次首次生成都误报 `409 GENERATION_IN_PROGRESS`）。本项目是**两个进程共享同一个 SQLite 文件**（`pnpm dev` 与 `pnpm worker`，见 `spec/04-技术基线与目录结构.md` §1），排他与额度的原子性依据 `db.transaction(...).immediate()` 的 `BEGIN IMMEDIATE` 语义（写事务一开始即取写锁）+ `getDb()` 的 `busy_timeout`（`spec/04-技术基线与目录结构.md` §4.3；本期不做多 worker）。

### 5.3 `generations` 状态机与终态判定

转移规则引用 `spec/01-领域模型与数据库.md` §2.2：

```
queued ──▶ running ──┬──▶ succeeded   n = requested_count
                     ├──▶ partial     1 ≤ n < requested_count
                     └──▶ failed      n = 0
                     (worker 崩溃回收：started_at 超时 → 回退 queued，attempt 不变)
```

其中 `n` = 本次执行**成功转存并落库**的 `generation_results` 行数（`E2E-05`、`E2E-06`）；判定在新行全部写入后、同一事务内完成：`status = n === requestedCount ? 'succeeded' : n > 0 ? 'partial' : 'failed'`。

- `succeeded`：`error_code` / `error_message` 均写 NULL；`partial`：`error_code` 写造成张数不足的**最后一个**失败码；`failed`：`error_code` 写失败原因，`error_message` 写上游原始 message（**仅落库，不透给用户**）。
- 三种终态都必须写 `finished_at = nowIso()` 与 `audit_logs(action='generation.finish')`；`succeeded` / `partial` 必须至少有 1 行 `generation_results`。
- `partial` **不触发自动重试**：重跑会把额度与产出重复翻倍，补齐缺口须走 §5.7 `POST /api/generations/:id/retry`。这是对 `spec/01-领域模型与数据库.md` §2.2 的收窄，理由见 §9。

### 5.4 worker 拉取与 claim

任务来源（三张表）、拉取顺序、claim 原子性、心跳、启动自检、回收、超时与自动重试的**唯一事实源**是 `spec/04-技术基线与目录结构.md` §4.6，本文件不复述。本模块只补两件事：

- `generations` 的 handler 实现规格在 §5.9；`prompt_reverse_jobs` 的 handler 规格在 `modules/M09-图片反推提示词.md`；
- `generations` 的终态判定（`succeeded` / `partial` / `failed`）与额度回滚见 §5.3、§5.6、§5.7。

### 5.5 心跳、启动自检、回收、超时与自动重试

见 `spec/04-技术基线与目录结构.md` §4.6（`ERR-01` / `ERR-02` / `ERR-04` 的判定都在那里）。本模块只在那张契约之上收窄两处：

- **`partial` 不触发自动重试**：重跑会把额度与产出重复翻倍，补齐缺口须走 §5.7 的 `POST /api/generations/:id/retry` 新建行（对 `spec/01-领域模型与数据库.md` §2.2 的收窄，理由见 §9）；
- `JOB_TIMEOUT_SECONDS` 与 `ARK_TIMEOUT_SECONDS` 同为 120 秒的关系见 §9。

### 5.6 额度预扣与失败回滚

- **预扣**发生在 `createGeneration` 事务内（§5.2 第 4 步）：`usage_counters(user_id, day)` UPSERT 后 `images += count`、`generations += 1`；`day` 取 **`generations.created_at` 的 UTC 日期**，不是 worker 完成日。
- **回滚**发生在写终态前的同一事务内，产出 `n` 张、未产出 `requested_count - n` 张：`UPDATE usage_counters SET images = images - :unproduced WHERE user_id = :userId AND day = :generationDay;`（`day` 仍用入队日，跨天完成时不打错行）。`unproduced === 0` 时不执行该语句；`generations` 计数**不回滚**（任务确实发生了）。
- **保留产出张数**：`succeeded` 时 `images` 净增 `requested_count`（`E2E-08`）；`partial` 时净增 `n`；`failed` 时净增 0。回滚后不会出现 `images < 0`：预扣与回滚用同一 `day`，且 `unproduced ≤ requested_count`。

### 5.7 `POST /api/generations/:id/retry` 的新建行语义

- 允许的原任务状态：`succeeded` / `partial` / `failed`；原任务为 `queued` / `running` → `409 GENERATION_IN_PROGRESS`。
- 语义 = **新建 `generations` 行**，继承 `anchor_id` / `era_code` / `scene_id` / `requested_count` / `params_json`，`attempt = 0`、`status = 'queued'`、`created_at` 取当前时间；**绝不更新旧行**及其 `generation_results`（`E2E-09`）。
- 复用 `createGeneration` 的**同一校验序列与同一事务**（§5.2），因此 §5.1 的第 1/5/6/7 步（`REALNAME_REQUIRED` / `ANCHOR_NOT_CONFIRMED` / `CONSENT_REQUIRED` / `QUOTA_EXCEEDED`）同样生效。
- prompt **重新拼装**而非复制旧行：配置包可能已升级，`buildPrompt` 是唯一入口，必须重新落当时的 `template_version` / `era_pack_version` / `scene_pack_version`（`spec/05-Prompt工程.md` §7.2 第 3 条）。
- 入口签名：`export function retryGeneration(input: { userId: number; generationId: number }): GenerationRecord;`

### 5.8 上游错误码 → 本项目错误码映射（`src/server/ark/errors.ts`）

唯一映射函数：`export function mapArkError(err: unknown): { code: ErrorCode; retryable: boolean; raw: string };`。覆盖 `docs/火山引擎接口文档.md` §5 的全部 8 类与 `spec/03-接口契约.md` §5.1 已声明的其余分支。mock 回放由用例显式指定失败分支，三个文件名已冻结在 `spec/08-本地开发指南.md` §5.1：`fixtures/ark/invalid-size.json`（`InvalidParameter`，size 低于 3,686,400）→ `INTERNAL`、`fixtures/ark/model-not-open.json`（`ModelNotOpen`）→ `PROVIDER_ERROR`、`fixtures/ark/timeout.json`（超时）→ `PROVIDER_TIMEOUT`（可自动重试 1 次）；前两者挂钩 `ERR-03`，第三者挂钩 `ERR-01`。

| 未登录 / 未配置（§5.6）、`InvalidParameter.NonUTF8Body`（§5.7） | `INTERNAL` | ❌ | 分别等价于 `ARK_API_KEY` 缺失或失效、我方发送编码 bug |

| 其他 HTTP 4xx | `PROVIDER_ERROR` | ❌ | |
| 网络超时 / fetch abort（含 `AbortError`） | `PROVIDER_TIMEOUT` | ✅ | |
| 图片下载失败（签名 URL 过期 / 403）、本地写盘失败 | `STORAGE_ERROR` | ✅ | 必须立即转存，签名链 86400s 过期 |

判定顺序：先看 `error.code` 字符串（`ModelNotOpen` / `InvalidParameter*` / `InvalidEndpointOrModel.*` / `InternalServiceError`），再看 HTTP 状态，最后落到 `INTERNAL`。返回体的 `model` 字段**不得用于断言**（返回值是规范化基础 ID，`README.md` §4.1）。

### 5.9 执行一个生成任务（handler 骨架）

`src/jobs/handlers/generate.ts` 的 `export async function runGenerateJob(generation: GenerationRecord): Promise<void>;` 按序：① `getArk()` 按 `PROVIDER` 取 provider，`reference_photo_ids` 逐张读 `photos.storage_key` → 本地文件 → Base64 data URI；② 调 `ark.generateImage({ prompt, images, size, outputFormat, watermark, count })`，`count > 1` 时请求体带 `sequential_image_generation: 'auto'` 与 `sequential_image_generation_options.max_images = requested_count`（`.scratch/seedream_era_scene.js` 实测用法）；③ 逐张**立即转存**（上游 `data[].url` 是 86400s 有效期的签名链）：下载 → 写隐式标识 → `LocalStorageProvider` 先写 `.tmp` 再 rename → 插 `photos(kind='generated')`，固定序列与 `AIGC_IMPLICIT_MARKER` 语义以 `spec/06-合规与风控.md` §3.3 为准；④ 逐张按 `modules/M07-生成后复核与内容审核.md` §5.1 的顺序处理：先 `moderateResult()`（硬闸门：`reject` → 中止该张及后续张的转存、写 `content_reviews(stage='result', verdict='reject')` 与 `audit_logs(action='moderation.reject')`），后 `eraReview()`（软标注：写 `era_check_json`、`age_delta`，失败留 `NULL` 并 warn）；被拒的该张不计入 `n`，全部被拒即 `failed` + `CONTENT_REJECTED`（`SEC-08`）。
⑤ 逐张插 `generation_results`，`ordinal` 从 0 连续递增；⑥ 按 §5.3 写终态、按 §5.6 回滚额度、写 `audit_logs(action='generation.finish')`，全部在**同一事务**内；handler 内部捕获所有异常并转成 `error_code` / `error_message` 写库，**不得把 `AppError` 抛给 worker 循环**（`spec/04-技术基线与目录结构.md` §4.1）。

## 6. 边界与错误

码、HTTP 状态与用户可见文案的唯一事实源是 `spec/03-接口契约.md` §5；本文件只记**本模块的触发条件**，不复述文案。

| 错误码 | 触发条件 |
|---|---|
| `REALNAME_REQUIRED` | 未实名（`users.verified_at IS NULL`）发起生成 |
| `INVALID_PARAM` | `count ∉ {2,3,4}`；`eraCode` / `sceneId` 不存在或未启用；zod 解析失败 |
| `ANCHOR_NOT_FOUND` | 锚点不存在或不属于当前用户 |
| `ANCHOR_NOT_CONFIRMED` | 锚点 `status != 'succeeded'` 或 `confirmed_by_user != 1`，或 `anchor_text` 为空 |
| `CONSENT_REQUIRED` | `photo_usage` 授权不存在或已吊销 |
| `QUOTA_EXCEEDED` | `usage_counters.images + count > users.daily_image_quota` |
| `GENERATION_IN_PROGRESS` | 已有非终态 `generations`；retry 时原任务非终态 |
| `PROVIDER_ERROR` | 上游返回错误（含模型未开通、模型 ID 错误、限流、5xx） |
| `PROVIDER_TIMEOUT` | 上游超时或 `JOB_TIMEOUT_SECONDS` 超时 |
| `STORAGE_ERROR` | 图片下载失败、写盘失败 |
| `CONTENT_REJECTED` | 结果审核 `reject`（由 §5.9 第 ④ 步写入） |
| `INTERNAL` | §5.8 映射表里映射为 `INTERNAL` 的上游错误、未捕获异常 |

写库的 `error_message` 保存上游原文用于排查；响应里的 `error.message` 一律取 `spec/03-接口契约.md` §5 的文案，**不得透出上游 message 与 RequestId**（`spec/04-技术基线与目录结构.md` §4.1）。

## 8. 测试要点

单元测试（`vitest`，`pnpm test`）：① §5.1 八条校验各一个用例，断言抛出的 `code` 与顺序（第 1 步 `REALNAME_REQUIRED` 先于第 5 步；第 4 步失败时不得先报第 5 步）——`RN-01`、`SEC-01`、`SEC-03`、`SEC-04`、`SEC-05`；② 额度不足用例额外断言 `generations` 表行数未增加——`SEC-04`；③ `createGeneration` 成功后 `usage_counters.images` 恰好 + `count`、`generations` + 1，`generations.prompt` 与 `buildPrompt` 输出逐字符相等且 `prompt_hash` 取自返回值，`reference_photo_ids` 恰 1 个元素且该 photo `kind='preprocessed'`——`E2E-03`、`E2E-04`、`E2E-08`、`PR-08`；④ `spec/04-技术基线与目录结构.md` §4.6 的 claim 规则：连续两次 claim 同一行，第二次 `changes === 0`；⑤ §4.6 的回收规则：三张表各自的陈旧 `running` 行回到 `queued` 且 `attempt` 不变——`ERR-02`；⑥ §4.6 的自动重试规则：`attempt=0` 时重试一次（`attempt=1`），`attempt=1` 时落 `failed`——`ERR-01`。
⑦ 终态判定三例（`n=requested_count`→`succeeded`，`0<n<requested_count`→`partial`，`n=0`→`failed`），`ordinal` 为 `0..n-1` 连续且 `UNIQUE(generation_id, ordinal)` 不冲突——`E2E-05`；⑧ 回滚：`partial` 时 `images` 净增 `n`，跨天完成时打进队日那一行——`E2E-08`；⑨ `mapArkError` 对上表逐条断言 `code` 与 `retryable`——`ERR-03`；⑩ mock 回放 `fixtures/ark/invalid-size.json` / `ark/model-not-open.json` / `ark/timeout.json`，三者分别落到 `INTERNAL`（不重试）/ `PROVIDER_ERROR`（不重试）/ `PROVIDER_TIMEOUT`（重试 1 次）——`ERR-01`、`ERR-03`；⑪ `retryGeneration`：原任务 `succeeded`/`partial`/`failed` 各建新行且旧行未被修改，原任务 `running` → `GENERATION_IN_PROGRESS`——`E2E-09`。

契约与链路（`pnpm check:acceptance`，`PROVIDER=mock`）：`API-04`、`E2E-01`–`E2E-10`、`SEC-04`、`SEC-05`、`ERR-01`、`ERR-02`、`ERR-03`、`ERR-04`。其中 `ERR-03`：mock 通过 `fixtures/ark/invalid-size.json` 返回 `InvalidParameter`（size 低于 3,686,400），断言任务 `error_code='INTERNAL'` 且接口响应中不出现 `image size must be at least` 字样；`ERR-01` 用 `fixtures/ark/timeout.json` 走超时后重试 1 次的路径。

## 9. 非目标与待定决策
非目标（见 §1.2 与 `spec/04-技术基线与目录结构.md` §5）：多 worker、通用任务队列、用户可编辑 prompt、多人全家福（`reference_photo_ids` 本期只写 1 个元素）。

1. **`partial` 不自动重试**：`spec/01-领域模型与数据库.md` §2.2 只写了"失败自动重试 1 次"，未区分 `partial`（理由见 §5.3）；若要自动补齐缺口，需先定义"只补未产出的 ordinal"，属新功能。
2. **`JOB_TIMEOUT_SECONDS` 与 `ARK_TIMEOUT_SECONDS` 同为 120**：生成 handler 内联的审核与复核各是一次上游调用，默认值下总时限紧张，建议在 `spec/08-本地开发指南.md` §4 说明关系或抬高前者（本文件不改默认值）。
3. **`params_json.outputFormat` 固定 `'png'`**：`output_format` 仅 Seedream lite 可设；换模型时需按模型能力降级为 `jpeg`。
4. **`POST /api/generations/:id/retry` 的完整错误集**：`spec/03-接口契约.md` §3.5 只列出 `GENERATION_IN_PROGRESS` 与 `QUOTA_EXCEEDED`，本文件因复用 `createGeneration` 而使 `REALNAME_REQUIRED` / `ANCHOR_NOT_CONFIRMED` / `CONSENT_REQUIRED` 同样可能出现，需追认或改为独立校验序列。
5. **面部相似度阈值**（`spec/00-总纲.md` §4.4，≥ 0.55）本期不实现，`generation_results.realism_score` 已预留且恒 `null`。
