# M01 · 照片资产与存储

> **层级**：实现规格层 · 后端模块
> **上游**：`docs/raw/AIGC_PRD.md` §2.4 ／ `spec/00-总纲.md`、`spec/01-领域模型与数据库.md` §3.4、`spec/03-接口契约.md` §3.2、`spec/04-技术基线与目录结构.md` §4.5
> **下游**：`modules/M02-预处理与质量评分.md`、`modules/M06-生成编排.md`、`modules/M07-生成后复核与内容审核.md`、`modules/M08-账号历史与彻底删除.md`、`pages/P01-上传与身份确认.md`、`tickets/T03-照片资产、本地存储与上传.md`

> 一句话职责：把用户上传的旧照片安全落到本地磁盘并写进 `photos` 表，再以「只属于当前用户」的方式把它读回来。

## 1. 职责与边界

1. 定义 `StorageProvider` 抽象与唯一实现 `LocalStorageProvider`（照片以文件存在本地目录，`photos.storage_key` 存相对路径），并提供 `photos` 的 repository 函数（字段以 `spec/01-领域模型与数据库.md` §3.4 为准）；
2. `POST /api/photos`：multipart 解析、mime 白名单、大小上限、sha256 内容去重、宽高探测、落盘 + 落库 + 审核/审计三写；
3. `GET /api/photos/:id/file`：归属与软删除校验、`?w=` 缩放、AIGC 标识响应头、缓存头；
4. `DELETE /api/photos/:id`：只做**软删除标记**，级联规则委托给 `domain/deletionService`（见 `modules/M08-账号历史与彻底删除.md` §4–6）。

明确不做什么：

| 不做 | 落在哪 |
|---|---|
| 归一化、方向校正、EXIF 剥离、质量评分 | `modules/M02-预处理与质量评分.md`（`src/server/images/`） |
| 物理删除磁盘文件与行 | purge worker（`src/jobs/handlers/purge.ts`，见 `modules/M08-账号历史与彻底删除.md`） |
| 隐式标识写入（AIGC 元数据） | `src/server/images/mark.ts`（见 `spec/06-合规与风控.md`） |
| 对象存储 / CDN / 公网 URL | `spec/00-总纲.md` §6.2；契约里不存在任何外部图片地址 |
| 从上游签名 URL 下载转存、上传阶段的审核**判定** | `modules/M06-生成编排.md` §5；判定见 `modules/M07-生成后复核与内容审核.md`（本模块只**写** `content_reviews(stage='upload')` 一行） |
| 缩略图预生成 / 缓存目录 | `?w=` 每次实时缩放，不落旁路文件 |

## 3. 数据读写

### 3.1 `photos`（读写）

字段以 `spec/01-领域模型与数据库.md` §3.4 为准；上传写入的非平凡取值：

| 字段 | 写入值 |
|---|---|
| `kind` | 固定 `'original'`（`preprocessed` 由 `modules/M02-预处理与质量评分.md`、`generated` 由 `modules/M06-生成编排.md` 产生） |
| `storage_key` | `buildKey(userId, ext)` → `u{userId}/{uuid}.{ext}`，**相对路径**，绝不存 URL |
| `mime` | 规范化后的四选一：`image/jpeg` / `image/png` / `image/webp` / `image/heic`；允许值与落库值的唯一声明处见 `spec/01-领域模型与数据库.md` §3.4 |
| `bytes` / `width` / `height` | `Buffer.byteLength(buffer)`（与落盘实数比对，见 §4.2 第 3 条）；`probeImage()` 的宽高，三种失败形态的去向见 §6.4（仅「容器可解析、读不到宽高」一类写 `NULL` 并继续） |
| `sha256` | 文件字节的 sha256（小写十六进制），用于同用户内去重 |
| `source_photo_id` / `quality_json` / `deleted_at` | 均为 `NULL`（`quality_json` 仅 `preprocessed` 写） |
| `created_at` | `nowIso()`（UTC ISO-8601，见 `spec/04-技术基线与目录结构.md` §4.2） |

读：`GET /api/photos/:id/file` 只读单行；`DELETE` 写 `deleted_at`。查询模式与索引（`spec/02-schema.sql`）：去重查询 `WHERE user_id=? AND sha256=? AND kind='original' AND deleted_at IS NULL` 走 `idx_photos_sha256` + `idx_photos_user_created`；归属读 `WHERE id=? AND user_id=? AND deleted_at IS NULL` 走主键；`source_photo_id` 无专用索引（见 §10.2 第 2 条）。

### 3.2 `content_reviews` 与 `audit_logs`（写）

一次成功的上传（含命中去重复用）写**恰好一行** `content_reviews` 与一条 `audit_logs`：

```sql
INSERT INTO content_reviews (user_id, stage, target_type, target_id, verdict, reason, model, created_at)
VALUES (?, 'upload', 'photo', ?, ?, ?, ?, ?);
INSERT INTO audit_logs (user_id, action, target, meta_json, created_at)
VALUES (?, 'photo.upload', 'photo:' || ?, ?, ?);
```

- 内容审核判定（`moderationVerdict`）∈ {'pass','reject','review'} 由 `moderateUpload()` 给出，**每个阶段无论何种内容审核判定都写恰好一行** `content_reviews`（`pass` / `review` 同样写，不存在"默认 pass 不写"或"仅 reject 时写"的路径）；`reason` / `model` 可为 `NULL`（`model` 仅在调用模型审核时写）；`target_type` 固定 `'photo'`，`target_id` = `photos.id`（去重命中时写**被复用的那一行**的 id）；
- 内容审核判定（`moderationVerdict`）为 `reject` 时该 `photos` 行**立即软删**（写 `deleted_at`，磁盘文件由 `runPurge()` 清理，用户侧不可见），另写一条 `audit_logs(action='moderation.reject')`，端点返回 `422 CONTENT_REJECTED`（§6.1）；内容审核判定为 `pass` / `'review'` 一律放行。
- `meta_json` 固定形状：`{ "mime": string, "bytes": number, "sha256": string, "deduped": boolean }`；`DELETE /api/photos/:id` 的 `action='photo.delete'` 由 `deletionService` 写（见 `modules/M08-账号历史与彻底删除.md`）。

### 3.3 事务边界

上传是**先写磁盘、后写事务**（`spec/04-技术基线与目录结构.md` §4.3 要求所有写操作包在事务里）：校验 → 读 buffer → sha256 → 查去重（命中即返回已有行）→ 落盘（`storage.save`，原子 rename）→ 单事务内 `INSERT photos` → `INSERT audit_logs` → 调 `moderateUpload()` 取内容审核判定（`moderationVerdict`）并写 `content_reviews(stage='upload')`（无论 `pass` / `review` / `reject` 都写）；内容审核判定为 `reject` 时在同一事务内写 `photos.deleted_at` 与 `audit_logs(action='moderation.reject')`，端点返回 `422 CONTENT_REJECTED`；事务失败则 `storage.delete(key)` 回滚磁盘并抛 `STORAGE_ERROR`（流程见 §6.1）。去重命中时**不落盘、不新增行**，但仍在同一事务里补写 `content_reviews` 与 `audit_logs`（`deduped: true`），保证"每次上传都有审计"。

| 端点 | 契约位置 | 本模块实现 |

### 4.1 `StorageProvider` 接口（`src/server/storage/types.ts`）

```ts
import type { Iso } from '@/shared/types';

export type StorageKey = string;                 // 形如 'u12/3f9a2c1e-....jpg'，相对存储根
export type ImageExt = 'jpg' | 'png' | 'webp' | 'heic';
export interface SaveResult { key: StorageKey; bytes: number; }
export interface StoredStat { key: StorageKey; bytes: number; modifiedAt: Iso; }   // mtime，UTC ISO-8601

// 错误语义：key 缺失 → AppError(NOT_FOUND)；其他 IO 错误 → AppError(STORAGE_ERROR)
export interface StorageProvider {
  save(key: StorageKey, data: Buffer): Promise<SaveResult>;   // 原子写：写同目录 `<key>.<uuid>.tmp` → rename
  read(key: StorageKey): Promise<Buffer>;
  delete(key: StorageKey): Promise<boolean>;                  // 不存在返回 false（幂等），不抛错
  exists(key: StorageKey): Promise<boolean>;
  stat(key: StorageKey): Promise<StoredStat | null>;          // 不存在返回 null，不抛错
  resolveAbs(key: StorageKey): string;                        // 相对 key → 绝对路径；纯函数换算，不触盘
}

export function buildKey(userId: number, ext: ImageExt): StorageKey;  // `u${userId}/${randomUUID()}.${ext}`
export function getStorage(): StorageProvider;                        // 进程内单例，当前恒为 LocalStorageProvider
```

### 4.2 `LocalStorageProvider` 实现要点（`src/server/storage/local.ts`）

1. **根目录与 key**：`path.resolve(process.env.STORAGE_DIR ?? './storage')`，首次使用 `mkdir(root, { recursive: true })`；调用方只允许用 `buildKey(userId, ext)`，`u{userId}/` 是按用户分片的目录，purge 时按目录删除。
2. **path traversal 防护**（每个方法入口第一行 `assertSafeKey(key)`）：key 必须匹配 `/^u[1-9]\d*\/[A-Za-z0-9._-]+$/`；显式拒绝含 `..`、含 `\` 或 `:`（Windows 盘符/ADS）、以 `/` 开头、`path.isAbsolute(key)` 为真；`resolveAbs` 内二次确认 `const abs = path.resolve(root, key)`，若 `abs !== root && !abs.startsWith(root + path.sep)` 则抛 `AppError('STORAGE_ERROR', '保存失败，请重试', 500)`；**不**回落到"就近目录"，避免竞态下写错位置。
3. **原子写**：`tmp = abs + '.' + randomUUID() + '.tmp'`（与目标同目录，保证同文件系统 rename 原子）；`fs.writeFile(tmp, data)` → `fs.rename(tmp, abs)`；任一步失败 `unlink(tmp)` 后抛 `STORAGE_ERROR`。成功后 `save` 再 `stat` 一次，用**实际落盘字节数**返回 `bytes`（与 `photos.bytes` 的一致性由调用方断言）。
4. **错误映射**：`ENOENT` → `AppError('NOT_FOUND', '这张照片找不到了', 404)`；`EACCES` / `ENOSPC` / `EISDIR` / 其他 → `AppError('STORAGE_ERROR', '保存失败，请重试', 500)`。映射后日志保留原始 errno，绝不进用户可见文案。
5. `resolveAbs` 只做换算、不做 IO：`GET /api/photos/:id/file` 不需要它，它只服务于 purge worker 的日志与运维排查。

## 5. `photos` repository 函数清单（`src/server/db/repositories/photos.ts`）

约定（`spec/04-技术基线与目录结构.md` §4.3）：入参为原子值或 DTO，返回 camelCase 领域对象 `PhotoRecord`，**不返回数据库原始行**；JSON 列在 repository 边界用 zod 校验。

```ts
export interface PhotoRecord {
  id: number; userId: number; kind: 'original' | 'preprocessed' | 'generated';
  storageKey: string; mime: string; bytes: number; width: number | null; height: number | null;
  sha256: string; sourcePhotoId: number | null;
  qualityJson: Quality | null;   // 仅 kind='preprocessed' 非空，形状见 spec/03-接口契约.md §4 Quality
  deletedAt: Iso | null; createdAt: Iso;
}
export interface NewPhoto {
  userId: number; kind: PhotoRecord['kind']; storageKey: string; mime: string; bytes: number;
  width: number | null; height: number | null; sha256: string;
  sourcePhotoId: number | null; qualityJson: Quality | null; createdAt: Iso;
}

// —— 本模块使用 ——
export function insertPhoto(input: NewPhoto): PhotoRecord;
export function findActivePhotoForUser(id: number, userId: number): PhotoRecord | null;
export function findActiveOriginalBySha256(userId: number, sha256: string): PhotoRecord | null;
export function insertContentReview(input: NewContentReview): void;   // 实现在 reviews.ts，本模块调用
export function listActivePhotosByIds(userId: number, ids: number[]): PhotoRecord[];

// —— 供 modules/M02、modules/M03、modules/M04、modules/M06、modules/M08 使用；本模块只交付签名，不实现调用 ——
export function findOriginalById(id: number, userId: number): PhotoRecord | null;
//   只认 `kind = 'original'` 且 `deleted_at IS NULL` 且 `user_id = :userId`；无行返回 null（调用方转 404 NOT_FOUND）
export function findPreprocessedBySource(sourcePhotoId: number): PhotoRecord | null;
//   同一条原图只应有一张预处理图：取最新一张，且 `deleted_at IS NULL`
export function insertPreprocessed(input: {
  userId: number; sourcePhotoId: number; storageKey: string; mime: string;
  bytes: number; width: number; height: number; sha256: string; quality: Quality;

//   插入 `kind = 'preprocessed'` 行：`quality_json = JSON.stringify(quality)`、`source_photo_id = :sourcePhotoId`；与原图存在性检查在同一事务
export function listActivePhotosByUser(userId: number, opts: { limit: number; beforeCreatedAt?: Iso }): PhotoRecord[];

```

`findActivePhotoForUser` 的 SQL 必须同时带上归属与软删除条件，**不允许**先按 id 查再在 JS 里比对 `userId`（防止后面有人误改判定顺序）：`SELECT * FROM photos WHERE id = ? AND user_id = ? AND deleted_at IS NULL LIMIT 1;`

## 6. 关键流程与状态机

### 6.1 `POST /api/photos`

```
requireUser() ──────────────────────────────────▶ 401 UNAUTHENTICATED
formData 取字段 'file'（必须存在且为 File） ─────▶ 400 INVALID_PARAM
file.size > MAX_UPLOAD_MB * 1024 * 1024 ────────▶ 413 FILE_TOO_LARGE
file.type ∈ {image/jpeg, image/png, image/webp, image/heic} ─▶ 否则 400 INVALID_FILE_TYPE
buffer = Buffer.from(await file.arrayBuffer())；再查一次长度（防 size 不可信）→ 超限同上
sha256 = createHash('sha256').update(buffer).digest('hex')
findActiveOriginalBySha256(userId, sha256) 命中 ─▶ 事务补 content_reviews(stage='upload')+audit_logs{depuped:true} → 201 已有行
未命中 ─▶ ext = MIME_EXT[type]（jpeg→jpg, png→png, webp→webp, heic→heic）→ buildKey(userId, ext) → storage.save(key, buffer)
        ─▶ { width, height } = await probeImage(buffer)   → 三种失败形态的去向见 §6.4；只有「读不到宽高」一类继续上传
        ─▶ 单事务 insertPhoto → audit_logs{'photo.upload'}          ← photos 行已落库
        ─▶ moderationVerdict = await moderateUpload(photo.id)    ← 唯一入口，无论 pass/review/reject 都写一行 content_reviews(stage='upload')
        ─▶ moderationVerdict='reject' → 写 photos.deleted_at（立即软删，磁盘文件由 runPurge() 清理）
                            → audit_logs{'moderation.reject'} → 422 CONTENT_REJECTED
        ─▶ moderationVerdict='pass' / 'review' → 201 { photo: { id, kind:'original', url, mime, bytes, width, height, sha256, createdAt } }
```

`kind` 恒为 `'original'`：`preprocessed` 只能由 `POST /api/photos/:id/preprocess` 产生（`modules/M02-预处理与质量评分.md`），本端点**不得**接受 `kind` 参数。`probeImage()` 的失败分类与去向见 §6.4：`width` / `height` 允许为 `NULL`，不阻断上传。

### 6.2 `GET /api/photos/:id/file`

```
requireUser() ──▶ 401
findActivePhotoForUser(id, userId)：不存在 / 属于他人 / 已软删除 → 404 NOT_FOUND（三者共用 404，不回 403，满足 API-04 反探测）
storage.read(photo.storageKey)：文件缺失 → 404 NOT_FOUND（行与盘不一致）
w 未传 ─▶ Content-Type = photos.mime；body = buffer 原样
w 已传 ─▶ w 为整数且 ∈ [16, 2048]，否则 400 INVALID_PARAM
          buffer = await sharp(buffer).resize({ width: w, withoutEnlargement: true }).jpeg({ quality: 80 }).toBuffer()
          Content-Type = 'image/jpeg'
公共响应头：Cache-Control: private, max-age=3600 ／ Content-Length: <最终字节数>
           X-AIGC-Generated: true    ← 仅当 photo.kind === 'generated' 时附加；其余 kind 不带该头
```

- `withoutEnlargement: true`：小图请求大 `w` 时**不放大**（`spec/00-总纲.md` §4 红线，不做超分）；`kind='generated'` 的隐式标识元数据由生成侧写入（`src/server/images/mark.ts`），本端点只负责这个显式响应头；
- 路由文件需声明 `export const runtime = 'nodejs'` 与 `export const dynamic = 'force-dynamic'`（二进制响应不参与静态化）。

### 6.3 `DELETE /api/photos/:id`

```
requireUser() ──▶ 401
deletionService.deletePhoto({ photoId: id, userId })   ← 归属校验 + 级联软删除，细节见 modules/M08-账号历史与彻底删除.md §4
   ├─ 不属于当前用户 → 404 NOT_FOUND
   ├─ 已软删除 → 200（幂等，cascaded 计数为 0）
   └─ 首次删除 → 写 deleted_at + audit_logs('photo.delete')，返回级联计数
```

物理文件与行由 purge 任务延迟清理（`modules/M08-账号历史与彻底删除.md` §5），本模块的 handler 不做任何 unlink。生命周期（承接 `spec/01-领域模型与数据库.md` §2.3）：

```
active ──DELETE /api/photos/:id──▶ soft-deleted（deleted_at 非空，立即从所有读取路径消失）
soft-deleted ──purge worker（deleted_at 早于 N 分钟）──▶ 磁盘文件删除 + 行物理删除
```

### 6.4 `probeImage()` 的失败分类（`sharp` 失败的唯一映射表）

`probeImage(buffer)` 用 `sharp(buffer)` 取 `metadata()`（`src/server/images/probe.ts`）。`sharp` 的失败分三种形态，去向各不相同，**全模块只有这一处规定它们的映射**，§3.1 与 §7 只引用、不复述：

| 失败的形态 | 判据 | 去向 |
|---|---|---|
| 容器可解析、但读不到宽高 | `metadata()` 成功但 `width` / `height` 缺失（本机 libvips 没有 heif 解码能力时就长这样） | `photos.width` / `photos.height` 写 `NULL`，**继续**：上传 `201`，预处理与后续链路照常 |
| 解码器打不开文件 | `sharp(buffer)` / `metadata()` 抛「无法识别的格式 / 解码器打不开」类错误 | `INVALID_FILE_TYPE`（400，`spec/03-接口契约.md` §5），不落盘、不写行 |
| 其它 `sharp` 失败（磁盘、内存、libvips 内部错误） | 不属于上面两类 | `STORAGE_ERROR`（500），不落盘、不写行 |

判定顺序：先试 `metadata()`；它抛错即第二类，返回但缺 `width` / `height` 即第一类，其余异常归第三类。第一类**不阻断**上传（白名单已接受该 `mime`，见 `spec/01-领域模型与数据库.md` §3.4），只让 `width` / `height` 为 `NULL`。

## 7. 边界与错误

错误码、HTTP 状态与用户可见文案的唯一事实源是 `spec/03-接口契约.md` §5，本节只记触发条件、不复述。

| 错误码 | 触发条件 |
|---|---|
| `UNAUTHENTICATED` | 无会话或会话过期 |
| `INVALID_PARAM` | multipart 里没有 `file` 字段 / 值不是文件 / `?w=` 不是 [16,2048] 的整数 |
| `INVALID_FILE_TYPE` | `file.type` 不在白名单；或 `sharp` 解码器打不开文件（两类去向见 §6.4 的失败分类表） |
| `FILE_TOO_LARGE` | 字节数 > `MAX_UPLOAD_MB` |
| `CONTENT_REJECTED` | 上传阶段内容审核判定（`moderationVerdict`）为 `reject`（`moderateUpload()`）；该 `photos` 行已软删 |
| `NOT_FOUND` | 照片不存在 / 属于他人 / 已软删除 / 行存在但磁盘文件缺失 |
| `STORAGE_ERROR` | 落盘、rename、读取、路径校验失败（含 path traversal 被拒）；其它 `sharp` 失败的去向见 §6.4 的失败分类表 |
| `INTERNAL` | 兜底（`spec/04-技术基线与目录结构.md` §4.1） |

**heic 的已知限制（必须显式暴露，不要静默降级）**：白名单接受 `image/heic`（允许值见 `spec/01-领域模型与数据库.md` §3.4），但 `sharp` 能否解码 heif 取决于本机 libvips 构建（`spec/08-本地开发指南.md` 已列为已知限制）；去向一律按 §6.4 的失败分类表：容器能解析、只是读不到宽高时**不是错误**（宽高写 `NULL`，上传照常 `201`），只有解码器打不开文件才返回 `400 INVALID_FILE_TYPE`，**不做**"转成 jpg 再存"的兜底——那会篡改用户原始字节，违反 `spec/00-总纲.md` §1.3「保留唯一证据」的定位；`file.type` 为空字符串（部分客户端不发 Content-Type）时**不**按扩展名猜测，直接 `INVALID_FILE_TYPE`。

## 10. 非目标与待定决策

### 10.1 非目标（本期不做）

断点续传/分片上传/并发上传队列；图片格式转换（heic → jpg 落盘转码）与上传时的尺寸归一（后者是 `modules/M02-预处理与质量评分.md` 的职责）；磁盘用量配额与清理策略（`users.daily_image_quota` 只约束**生成**张数）；`ETag` / `If-None-Match` / Range 请求（`spec/04-技术基线与目录结构.md` §5 未要求，前端也未用）。

### 10.2 待定决策

1. **去重的 `kind` 范围**：`spec/03-接口契约.md` §3.2 未限定 `kind`；本文件限定为 `kind='original'`，否则会把 `preprocessed` / `generated` 行的 `id` 当作新上传的原图返回，污染只接受 `original` 的 `POST /api/anchors`。需在 `tickets/T03-照片资产、本地存储与上传.md` 的 `## Comments` 里确认。
2. **`source_photo_id` 缺索引**：`spec/02-schema.sql` 只为 `photos` 建了 `(user_id, created_at DESC)`、`(sha256)`、`(deleted_at)` 三个索引，`findPreprocessedBySource` 走全表扫描。MVP 数据量下可接受；若 `modules/M02-预处理与质量评分.md` 要求索引，需新增 `002-*.sql`。
3. **测试文件位置约定**：`spec/04-技术基线与目录结构.md` 未规定测试文件路径，本文件采用 co-located `*.test.ts`；若 `tickets/T01-项目脚手架与本地开发环境.md` 建立了独立 `tests/` 目录，需统一改名。
4. **环境变量读取位置**：本模块直接读 `process.env.STORAGE_DIR` 与 `process.env.MAX_UPLOAD_MB`；若 `tickets/T01-项目脚手架与本地开发环境.md` 建立集中式 env 解析，应改为经该模块读取，并保留 `STORAGE_DIR` 默认值 `./storage` 的行为不变。
5. **`X-Content-Type-Options: nosniff`**：`spec/03-接口契约.md` 未要求该响应头，本文件不加，避免发明契约；可作为 `spec/06-合规与风控.md` 的增强项提出。
