# M07 · 生成后复核与内容审核

> **层级**：实现规格层 · 后端模块
> **上游**：`docs/raw/AIGC_PRD.md` §4、§5.5、§6.2、§9 ／ `spec/00-总纲.md` §4.3–§4.4、`spec/03-接口契约.md` §2.2/§3.2/§3.5/§4/§5、`spec/05-Prompt工程.md` §4、`spec/06-合规与风控.md` §7
> **下游**：`tickets/T11-生成后复核与内容安全审核.md`、`modules/M06-生成编排.md` §5、`pages/P03-结果历史与下载.md`
> 一句话职责：生成图落地前做两件事——**年代穿帮复核 + 年龄偏差估计**（可缺，不阻断交付）与**内容安全审核**（不可缺，内容审核判定（`moderationVerdict`）不通过即中止该张及其后续张的转存）。年龄偏差检查是 `spec/05-Prompt工程.md` §4「防美化三处落点」的第 3 处。

## 1. 职责与边界
### 1.1 做什么
| # | 职责 | 产物 |
|---|---|---|
| 1 | **年代穿帮复核**：读生成图，判定画面中是否出现**所选年代之后才存在**的物件 | `generation_results.era_check_json`（形状 = `spec/03-接口契约.md` §4 `EraCheck`） |
| 2 | **年龄偏差估计**：估计生成图人物年龄区间中值，与锚点 `features.ageRange` 中值相减 | `generation_results.age_delta`（**可为负**） |
| 3 | **内容安全审核（result / prompt 阶段）**：判定生成图与拼装后的 prompt 是否含违规内容 | `content_reviews(stage='result' \| 'prompt')`；内容审核判定（`moderationVerdict`）不通过时中止该张及其后续张的转存、或拒绝入队 |
| 4 | 内容审核判定（`moderationVerdict`）不通过的审计留痕 | `audit_logs(action='moderation.reject')` |

### 1.2 明确不做什么
- ❌ 不阻断年代穿帮的交付：年代复核判定（`eraCheckVerdict`）为 `review` / `reject` 不删图、不置任务失败，只在结果卡片标注（§5.3）；
- ❌ 不实现自动人脸相似度打分（`realism_score` 本期恒为 `NULL`，§9），也不做"年代主题 cosplay"判定（属人工评审，`spec/07-验收标准.md` §4）；
- ❌ 不做人工审核后台：内容审核判定（`moderationVerdict`）为 `review` 等同放行并留痕，无人工处置通道（`spec/06-合规与风控.md` §7）；
- ❌ 不重复实现 upload 阶段审核，只声明其判定口径与失败路径（§5.6）；落点在 `tickets/T03-照片资产、本地存储与上传.md`；
- ❌ **不覆盖 F4（图片反推提示词）**：反推只输出文本与推荐代号、不产出图片，因此没有年代穿帮复核也没有年龄偏差检查；反推产物的可信度由用户在**上传页采纳时**自行决定（`pages/P01-上传与身份确认.md` §4.4；推荐值随会话内存态带进 `pages/P02-年代与场景选择.md` §7），见 `modules/M09-图片反推提示词.md`；
- ❌ 不新增 HTTP 端点、不新增数据库表/字段、不新增环境变量。
**两个判定的命名**：本文件涉及两种判定，取值域同为 `pass` / `review` / `reject`，后果却相反——**年代复核判定**（`eraCheckVerdict`，`eraReview()` 写出的 `EraCheck.verdict`）只做卡片标注，不删图、不置任务失败（§5.3）；**内容审核判定**（`moderationVerdict`，`moderate*()` 写出的 `content_reviews.verdict`）不通过才阻断该张交付（§5.6）。取值与列名（`EraCheck.verdict` / `content_reviews.verdict`）均保持不变；两个术语的定义以仓库根 `CONTEXT.md` 的 `### 复核与审核` 为唯一事实源。

## 3. 数据读写
写入：`generation_results.era_check_json`（复核成功才写，失败保持 `NULL`）、`generation_results.age_delta`（估计中值 − 锚点中值，整数，**可为负**，不可计算时 `NULL`）、`generation_results.realism_score`（**可选自动打分**，本期不写、恒 `NULL`）、`generations.status` / `error_code` / `error_message`（result 阶段被内容审核判定（`moderationVerdict`）为 `reject` 的图不写 `generation_results` 行、不计入计数 `n`；任务终态由 `n` 决定，`n === 0` 时 `failed` + `CONTENT_REJECTED`，见 §5.6）、`content_reviews`（`stage` / `target_type` / `target_id` / `verdict` / `reason` / `model`，每个阶段无论内容审核判定（`moderationVerdict`）为 `pass` / `review` / `reject` 都写一行，`reason` 取审核模型给出的理由）、`audit_logs`（`action='moderation.reject'`，`target` 形如 `generation:7` / `photo:12`）、`photos.deleted_at`（result 阶段内容审核判定为 `reject` 时软删该张已转存的 `kind='generated'` 图；upload 阶段内容审核判定为 `reject` 时软删该 `photos` 行）。

读取：`identity_anchors.features_json.ageRange`（`age_delta` 的基准年龄区间）、`eras.name` / `eras.constraint_pack`（复核输入中的"所选年代口径"；`scenes.name` 只用于日志与 fixture 选择，不进复核 prompt）。

```sql
UPDATE generation_results SET era_check_json = @eraCheckJson, age_delta = @ageDelta  -- JSON.stringify(EraCheck) 或 NULL；INTEGER 或 NULL
 WHERE generation_id = @generationId AND ordinal = @ordinal;
INSERT INTO content_reviews (user_id, stage, target_type, target_id, verdict, reason, model, created_at)
VALUES (@userId, 'result', 'generation', @generationId, 'reject', @reason, @model, @createdAt);
```

## 5. 关键流程与状态机
### 5.1 生成任务内的调用顺序
`src/jobs/handlers/generate.ts`，每个 `generations` 任务：

```
claim → 置 running → ArkProvider.generateImages
  → 对每个 ordinal i：① 转存为 photos(kind='generated')
                     ② moderateResult()  ← 审核在前，硬闸门：内容审核判定 reject → 中止该张及其后续张的转存（§5.6）；pass/review → 写 content_reviews(stage='result')
                     ③ eraReview()       ← 复核在后，软标注：成功 → 写 era_check_json + age_delta；抛 PROVIDER_TIMEOUT/PROVIDER_ERROR → 不写，warn 日志，继续
  → 处理结束（含被内容审核判定中止后续张） → 终态按 n 判定（succeeded / partial / failed，§5.6） → audit_logs(action='generation.finish')
```

**顺序理由**：内容审核判定（`moderationVerdict`）拒绝只需中止该张及其后续张的转存，越早发现浪费越少；年代复核判定（`eraCheckVerdict`）失败只是少一个标注，不应占用中止路径。

### 5.2 年代穿帮复核：提示词设计要点
prompt 常量由 `src/server/security/eraReview.ts` 唯一持有（handler **不得内联文本**），版本常量 `ERA_CHECK_PROMPT_VERSION = 'era-check-v1'`。输入：生成图（`image_url`）+ `eras.name` + `eras.constraint_pack` 原文（其语义已含"必须属于该年代或更早"）。下列要求逐条落到 prompt 文本：

1. **只报告"所选年代之后才存在的物件"**；更早的物件与跨年代中性的自然物（树木、天空、地面、水体）一律不报——这是复核的唯一定义；
2. **不报告画质类问题**（颗粒、色调、曝光、对焦、构图、表情、服装是否好看），也不报告人脸相似度、美化程度、AI 感（会污染 `findings`）；
3. `findings[].item` 是**单一物件名**（≤ 12 字，如 `智能手机`）；`reason` 一句话说明"画面何处 + 为什么晚于所选年代"（≤ 40 字）；
4. **宁漏不误报**：看不清、不确定的一律不报；
5. 年代复核判定（`eraCheckVerdict`）口径写死：`pass` = 未发现晚于年代的物件；`review` = 1–2 个且位于非主体位置（远景、背景角落）；`reject` = 主体位置或 ≥ 3 处穿帮；
6. `findings` **最多 5 条**，超出按严重度截断；无发现时必须是空数组，不得输出占位项；
7. 同时估计画面中人物年龄区间，键名 `estimatedAgeRange`（如 `"70-78"`），区间宽度 ≤ 8 岁；无法判断时给 `null`；
8. **严格 JSON 输出，禁止 Markdown 代码块与解释文字**：`{ "verdict": "pass | review | reject", "findings": [ { "item": "智能手机", "reason": "人物右手持黑色全面屏手机，1990 年代不存在该物件" } ], "estimatedAgeRange": "70-78" }`

模型输出不可直接信任，`eraReview.ts` 必须归一：`verdict` 非枚举值或缺失 → 按 `findings` 推导（空 → `pass`，非空 → `review`）；`verdict='pass'` 但 `findings` 非空 → 提升为 `review`；`findings` 超 5 条截断、`item`/`reason` 非字符串的条目丢弃；落库投影**只保留 `EraCheck` 的 4 个键**（`estimatedAgeRange` 消费后丢弃），`const passed = verdict === 'pass'`。

### 5.3 年代复核判定（`eraCheckVerdict`）不阻断交付
- 落库与卡片：`pass` → `{passed:true, verdict:'pass', findings:[], model}`、无标注；`review` → `{passed:false, verdict:'review', findings:[…], model}`、卡片标"可能不符合所选年代，仅供参考"；`reject` → `{passed:false, verdict:'reject', findings:[…], model}`、卡片标"明显不符合所选年代"；
- 四种情况下（含复核调用失败、`eraCheck: null`）**图片都保留、可下载，任务状态都不受影响**。

**不删图、不置失败的理由**：复核的 `item` / `reason` 本身可能错（把 90 年代的固定电话认成现代设备），升格为硬闸门等于用一次未经人工验证的判断没收用户已付额度的产出；而 `spec/00-总纲.md` §4.4 的年代一致性 ≥ 70% 与年代穿帮率 ≤ 3% 都是**批次级比例**，逐张阻断无法达成；`era_check_json` 落库后可离线统计穿帮率，反推是哪个年代包/组合需要迭代 prompt（`spec/05-Prompt工程.md` §7.2 的"改包 → 升 `pack_version`"回路）。

### 5.4 年龄偏差 `age_delta` 的计算
```ts
const ANCHOR_MID = midOfRange(features.ageRange);   // identity_anchors.features_json.ageRange
const ESTIMATED_MID = midOfRange(review.estimatedAgeRange);
const age_delta = (ANCHOR_MID === null || ESTIMATED_MID === null) ? null : ESTIMATED_MID - ANCHOR_MID;
function midOfRange(s: string | null): number | null;   // "75-85岁" / "70-78" → 两端整数求平均并四舍五入；解析失败返回 null
```

- 基准**只用结构化字段** `features.ageRange`（`spec/03-接口契约.md` §4），不解析 `anchor_text` 里的数字——单一来源，避免两处漂移；
- `age_delta` 是有符号整数：**负数 = 生成图比源照片年轻**。

> **负数是最危险的失败方向，必须在文档、代码、日志、卡片四处显式区分**：模型的天然倾向是理想化与减龄，这正是 `spec/00-总纲.md` §4.3 的红线"把老人磨年轻"。
> 🔴 **`age_delta` 不得取绝对值后上报**；监控分别统计"变年轻"与"变年长"的比例，只有前者触发 `spec/05-Prompt工程.md` §4 的反美化回路。`eraReview.ts` 对 `age_delta < 0` 必须单独打一条 `warn`，附带 `eraCode` / `sceneId`，便于定位是哪个年代包在推减龄。

### 5.5 年龄偏差的呈现与阈值
对齐 `spec/00-总纲.md` §4.4"年龄保真度 `|age_delta| ≤ 5` 岁"：

| 条件 | 卡片呈现 |
|---|---|
| `age_delta ≤ -6` | "看起来比原照片年轻了 X 岁"（**强调态**，最危险方向：极可能是抹平皱纹/老年斑导致的减龄，家属最容易一眼否定） |
| `age_delta ≥ +6` | "看起来比原照片年长 X 岁"（也不达标，但方向相对不刺眼，多为年代包带来的苍老感） |
| `\|age_delta\| ≤ 5` 或 `NULL` | 不显示任何提示（达标静默；无从判断则不猜） |

呈现只做标注，**不阻断下载，也不自动重生成**；"再来一组"仍是用户主动动作（`spec/01-领域模型与数据库.md` §2.2）。`spec/00-总纲.md` §4.4 的 60%/70%/5% 三项指标依赖人工评审，自动化只提供上述标注与落库数据。

### 5.6 内容审核三阶段
| 阶段 | 触发点 | 判定什么 | 落库 | `moderationVerdict='reject'` 路径 |
|---|---|---|---|---|
| `upload` | `POST /api/photos`（`tickets/T03-照片资产、本地存储与上传.md` 落点） | 上传文件本身是否含违规画面（裸露、暴力、违法内容） | `content_reviews(stage='upload', target_type='photo', target_id=photos.id)` | 落盘并写入 `photos` 行后审核：`422 CONTENT_REJECTED`；该行**立即软删**（`deleted_at`），并写 `content_reviews` 与 `audit_logs(action='moderation.reject')`；磁盘文件由 `runPurge()` 清理 |
| `prompt` | `POST /api/generations` 的"拼装完成 → 入队前"（`generationService`） | 拼装后的 prompt 全文是否含违规内容 | `content_reviews(stage='prompt', target_type='generation', target_id=<预留 id>)` | `422 CONTENT_REJECTED`；**不产生** `generations` 行，不预扣额度 |
| `result` | worker 转存候选图之后（§5.1 ②） | 生成图是否含违规内容 | `content_reviews(stage='result', target_type='generation', target_id=generations.id)` | **中止该张及后续张的转存**：软删该张已转存的 `kind='generated'` 图、不再转存后续张；被拒的图**不写** `generation_results` 行、不计入计数 `n`；任务终态由 `modules/M06-生成编排.md` §5.3 的公式决定（`n === requestedCount → succeeded`、`0 < n < requestedCount → partial`、`n === 0 → failed`，此时 `error_code='CONTENT_REJECTED'`） |

三阶段任何内容审核判定（`moderationVerdict`）为 `reject` 都额外写 `audit_logs(action='moderation.reject')`，`meta_json` 记 `{stage, targetId, reason}`；内容审核判定为 `review` 在三个阶段都**等同放行**，仅留痕。

🔴 **审核失败（上游超时/报错）与内容审核判定（`moderationVerdict`）的区别**：内容审核判定是模型给出的结论，失败是没拿到结论。审核是合规硬约束，**不放过未审核的结果**：`PROVIDER_TIMEOUT` / `PROVIDER_ERROR` 按 `spec/03-接口契约.md` §2.2 自动重试 1 次，仍失败则该张不交付、不计入 `n`，写对应 `error_code`，终态按 `n` 判定（`n === 0` 时 `failed`）。这与复核的"失败就留空"（§5.3）是刻意的不对称。

**prompt 阶段的实际覆盖面（诚实说明）**：本期进入 prompt 的用户侧内容只有 `identity_anchors.anchor_text`（由模型读图产出，不是用户手打），年代与场景只能从 `eras` / `scenes` 中选，`prompt_override` 来自种子数据，均不可注入。因此它真正能拦到的只有：① 锚点提取时模型从照片中读入的违规文字（如照片上的标语）间接进入 prompt；② 为将来"自定义场景描述"入口预留的注入防线（`spec/00-总纲.md` §6.2 明确本期不做该入口）。**它是防线不是主力**，主力仍是 upload 与 result 两个"对着真实图像"的阶段；此点须写进实现注释与该 ticket 的 `## Comments`。
## 6. 边界与错误
| 错误码 | 触发条件 |
|---|---|
| `CONTENT_REJECTED` | upload / prompt 阶段内容审核判定（`moderationVerdict`）= `reject`；落点——`POST /api/photos` 或 `POST /api/generations` |
| `CONTENT_REJECTED` | result 阶段内容审核判定（`moderationVerdict`）= `reject`；落点——worker 中止该张及后续张的转存、被拒图不计入 `n`；`n === 0` 时写 `generations.status='failed'`、`error_code='CONTENT_REJECTED'`，否则按 `n` 得 `partial` / `succeeded`；前端由 `GET /api/generations/:id` 读到 |
| `PROVIDER_TIMEOUT` | 审核或复核调用超时（`ARK_TIMEOUT_SECONDS`）；落点——审核：重试 1 次后仍失败则该张不交付、终态按 `n` 判定；复核：留 `NULL` 继续 |
| `PROVIDER_ERROR` | 审核或复核调用返回上游错误；落点——同上 |
| `INTERNAL` | 模型返回的 JSON 无法解析；落点——审核：等同 `PROVIDER_ERROR` 路径；复核：留 `NULL` 继续 |

约束（`spec/04-技术基线与目录结构.md` §4.1）：码与 HTTP 状态、用户可见文案的唯一事实源是 `spec/03-接口契约.md` §5，本节只记触发条件、不复述；worker handler **不得**抛 `AppError` 出去，审核导致的终止必须写入 `generations.error_code` / `error_message`；worker 日志用 `logger.warn({ job: 'generate', generationId, stage }, 'msg')` 结构，不复用用户文案。
