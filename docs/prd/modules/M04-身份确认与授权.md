> 一句话职责：把「特征锚点已提取成功」变成「用户主张这就是他 + 两项授权已落库」，并让未确认或未授权的锚点在接口层彻底不可用于生成。

## 1. 职责与边界
### 1.1 做什么

| # | 做什么 |
|---|---|
| 1 | `POST /api/anchors/:id/confirm`：校验锚点可用 → 校验两项授权 → 幂等写 `consents` → 写 `identity_anchors.confirmed_by_user` / `confirmed_at` → 同事务写两条审计 |
| 2 | `POST /api/anchors/:id/retry`：**新建行**重提取（`attempt = 旧 + 1`，继承 `input_photo_ids` / `preprocessed_photo_id`），旧行与旧结果零修改 |
| 3 | `DELETE /api/anchors/:id` 的调用点（级联范围与顺序见 `modules/M08-账号历史与彻底删除.md`）；服务端吊销授权的能力与 `consents.revoked_at` 语义（§5.5），本期**不做吊销 UI、不加端点** |
| 4 | 生成前置校验中的 `ANCHOR_NOT_CONFIRMED`（409）与 `CONSENT_REQUIRED`（403）两步，顺序固定（§5.3）；`src/server/security/audit.ts` 的唯一写入入口与 action 枚举（§9） |

### 1.2 为什么确认节点是强制的
`spec/00-总纲.md` §3 把链路 ③④ 之间定义为强制节点：一次生成产出 2–4 张（`requested_count`），锚点错了错的是整批；`anchor_text` 会原样进入 prompt 的【身份锚点】段（`spec/05-Prompt工程.md` §2.1，缺失即拒绝生成），链路里没有人工复核环能判断"这段文本描述的是不是照片里的那个人"，只有用户知道。**确认 ≠ 认可画质**（链路里没有"修复"这一步，`README.md` §0.1）；与 `modules/M02-预处理与质量评分.md`、`modules/M03-身份锚点提取.md` 的边界即在此。

**与实名门槛的分工**：本模块的强制节点是"用户确认这就是他 + 勾选授权"；"生成前必须已实名"是另一个门槛，落在 `modules/M08-账号历史与彻底删除.md` §2，错误码 `REALNAME_REQUIRED`。两个门槛互不替代。

### 1.3 明确不做什么
- ❌ 实名认证、身份证校验、人脸比对（`spec/07-验收标准.md` §6）；授权书上传、亲属关系证明、多方签名；吊销 UI 与吊销端点（`spec/03-接口契约.md` 无此端点，不得自行发明）；删改 `consents` 历史行（§5.5）；
- ❌ 在前端做"可否生成"的权威判断（`spec/03-接口契约.md` §6 第 2 条）；在 confirm 里顺带触发提取或生成（confirm 只做状态与授权写入）。

## 3. 数据读写
**读**：`identity_anchors` 的 `id, user_id, status, anchor_text, attempt, input_photo_ids, preprocessed_photo_id, quality_json, confirmed_by_user, confirmed_at` 在 confirm / retry 时按 `user_id = 当前用户` 读取，**不区分"不存在"与"不属于我"**，统一 `404 ANCHOR_NOT_FOUND`；`consents` 读 `id, scope, revoked_at` 做 confirm 复用判定与生成前置校验（§5.3、§5.5）；`photos` 只读 `id, kind, deleted_at` 做 retry 继承前的归属校验。

**写**：`consents` 插入 `user_id, scope, anchor_id, agreed_at`（仅当该 `anchor_id` + `scope` 无 `revoked_at IS NULL` 行时）；`consents.revoked_at` 仅由吊销入口（§5.5）更新，confirm 与 retry 都不写此列；`identity_anchors` 更新 `confirmed_by_user, confirmed_at`（`confirmed_at` 只在 0→1 时写），retry 则整行 `INSERT`（`status='queued'`）；`audit_logs` 插入 `user_id, action, target, meta_json, created_at`（§9）。

**关键 SQL**（依次为生成前置的有效授权判定、confirm 的幂等复用判定、确认写入；`COALESCE` 保证重复确认不改首次确认时间，`WHERE confirmed_by_user = 0` 同时给出"本次是否真的发生了状态变化"）：

```sql
SELECT 1 FROM consents WHERE user_id = ? AND scope = 'photo_usage' AND revoked_at IS NULL LIMIT 1;
SELECT id FROM consents WHERE user_id = ? AND anchor_id = ? AND scope = ? AND revoked_at IS NULL ORDER BY id DESC LIMIT 1;
UPDATE identity_anchors SET confirmed_by_user = 1, confirmed_at = COALESCE(confirmed_at, ?) WHERE id = ? AND confirmed_by_user = 0;
```

## 5. 关键流程与状态机
### 5.1 confirm：单事务

```ts
export function confirmAnchor(userId: number, anchorId: number, consents: ConsentScope[]):
  { anchor: Anchor; consents: ConsentScope[] };
```

`db.transaction` 内固定顺序（同步函数，`better-sqlite3` 为同步 API）：① 归属与存在性，缺失抛 `404 ANCHOR_NOT_FOUND`；② 可用性，仅 `status === 'succeeded'` 且 `anchor_text` 非空，否则 `409 ANCHOR_NOT_CONFIRMED`；③ 授权项完整性，`CONSENT_SCOPES` 两项必须同时提交，缺项抛 `400 INVALID_PARAM`（`details.fields.consents`）；④ `nowIso()` 只取一次，`consents.agreed_at` 与 `audit_logs.created_at` 必须逐字符相等；⑤ 幂等写 `consents` 两行（`consentsRepo.ensureActive`，同 `anchorId` + `scope` 未吊销则复用）；⑥ `anchorsRepo.markConfirmed` 写 `confirmed_by_user` / `confirmed_at`（仅 0→1 落值）；⑦ 同事务写审计两条 `anchor.confirm` 与 `consent.agree`，`target = anchor:{id}`，返回 `{ anchor, consents }`。`CONSENT_SCOPES = ['photo_usage', 'family_agreement'] as const`，定义在 `src/shared/types.ts`，与 `spec/01-领域模型与数据库.md` §3.11 的 `scope` 取值一致。状态机（confirm 视角）：

```
succeeded, anchor_text != null, confirmed_by_user = 0
      │ ①②③ 通过
      ▼
confirmed_by_user = 1, confirmed_at = 首次确认时间
      ├─ retry → 新行（旧行确认状态保留，供历史追溯）
      ├─ 重复 confirm → 仍 200；consents 复用不新增；confirmed_at 不变；审计每次请求都写
      └─ 授权被吊销 → confirmed_by_user 仍为 1，但 §5.3 的 ② 会拦下
```

③ 失败时整个事务回滚，`confirmed_by_user` 仍为 0（`spec/04-技术基线与目录结构.md` §4.3）——这是 `SEC-02` 的机器可验证形式。重复 confirm 仍写审计：每次点击都是一次真实的授权意思表示，而 `confirmed_at` 不变使审计成为唯一的"再次确认"证据。

### 5.2 retry：新建行，旧行不动

```ts
export function retryAnchor(userId: number, anchorId: number): Anchor;
```

① 读旧行 `findByIdForUser`，缺失 → `404 ANCHOR_NOT_FOUND`；② 旧行必须为终态（`succeeded` / `failed`），`queued` / `running` → `409 ANCHOR_NOT_CONFIRMED`（复用"锚点不可用"语义）；③ `INSERT` 新行（`status='queued'`）；④ 写审计 `anchor.extract`，`target = anchor:{新 id}`，`meta = { retryOf: 旧 id, attempt: 新 attempt }`。

新行字段清单：`input_photo_ids` **逐字符继承**旧行 JSON 文本（用户没换照片，重试的是提取）；`preprocessed_photo_id` 继承旧行（可能为 `NULL`，为 `NULL` 时由 `modules/M03-身份锚点提取.md` 的规则对 `input_photo_ids[0]` 触发预处理）；`attempt` = 旧行 + 1（`spec/03-接口契约.md` §3.3）；`model` / `prompt_version` 取 `ARK_VISION_MODEL` 与 `ANCHOR_PROMPT_VERSION`（`anchor-v1`）的**当前**值（旧行保留旧版本号，历史仍可复现，`spec/05-Prompt工程.md` §7.1）；`quality_json` 继承旧行快照（预处理图未变，省一次 `sharp` 计算）；`confirmed_by_user` / `confirmed_at` 为 `0` / `NULL`（新锚点是新主张，必须重新确认，§1.2）；`anchor_text` / `features_json` / `error_code` / `error_message` / `started_at` / `finished_at` 为 `NULL`（由 worker 重新提取）；`created_at` = `nowIso()`（新行在 `GET /api/history` 里按 `created_at DESC` 排最前）。

**旧行与旧结果不被修改**：旧 `anchor_text` 是"用户当时看到并确认过的文本"，覆盖后历史链路无法解释当时为什么生成出那张图；`generations.anchor_id` 与 `consents.anchor_id` 都指回旧行，改写会破坏 `E2E-03` 与授权留痕（`spec/01-领域模型与数据库.md` §4）。

### 5.3 生成前置校验：两步的顺序与位置
实现位置：`src/server/domain/generationService.ts` 的 `createGeneration()`，严格按 `spec/03-接口契约.md` §3.5 的表格顺序；与本文件相关的是其中第 4、5 步：

```ts
// 前置：未实名 → 409 REALNAME_REQUIRED（modules/M08-账号历史与彻底删除.md §2）；count / eraCode / sceneId 校验（modules/M06-生成编排.md）；锚点归属 → 404 ANCHOR_NOT_FOUND
if (anchor.status !== 'succeeded' || anchor.confirmedByUser !== 1) // ① 锚点可用性（先）
  throw new AppError('ANCHOR_NOT_CONFIRMED', '需要先确认"这就是他"，才能开始生成', 409);
if (!consentsRepo.hasActiveScope(db, userId, 'photo_usage'))       // ② 授权（后）
  throw new AppError('CONSENT_REQUIRED', '需要先确认照片使用授权', 403);
```

**为什么 CONFIRMED 必须先于 CONSENT**：①"这就是他"与两项勾选在同一次提交里发出（§5.1），未确认时报 `CONSENT_REQUIRED` 会把用户引向与当前阻塞点无关的解释；②`consents` 行是 confirm 的副产物，"未确认"在正常链路里蕴含"无有效授权"，先判授权会得到错误的第一因；③顺序固定后 `SEC-01` 不依赖测试数据里是否存在 `consents` 行；④整段顺序 `404 → 409 → 403`，存在性先于权限，避免用 403 泄漏"这个锚点存在但不属于你"（`spec/07-验收标准.md` 的 `API-04`）。

### 5.4 DELETE 的调用点

```ts
// app/api/anchors/[id]/route.ts
export const DELETE = withErrorHandling(async (_req, ctx) => ok(
  await deletionService.cascadeFromAnchor((await requireUser()).id, parseId(ctx.params.id)))); // 非法 :id → INVALID_PARAM
```

级联标记的**范围与顺序**见 `modules/M08-账号历史与彻底删除.md`；本文件只负责调用点与响应形状（`{ ok: true, cascaded: { generations, results } }`）。**幂等**：重复删除返回 `200`（`spec/03-接口契约.md` §1.5），锚点已软删除时 `cascaded` 全为 0；他人锚点 → `404 ANCHOR_NOT_FOUND`。写审计 `anchor.delete`，`target = anchor:{id}`，`meta` 为 `cascaded` 计数快照；`consents` **不删行**，命中该锚点的有效行写 `revoked_at`（§5.5 末段、`modules/M08-账号历史与彻底删除.md` §3.3）。

### 5.5 授权吊销：`revoked_at` 语义与入口
`revoked_at IS NULL` 表示授权有效、可用于 `photo_usage` 判定；`revoked_at` 非空表示该行授权自该时刻起失效、一律视为不存在。所有判定必须带 `revoked_at IS NULL`（`spec/01-领域模型与数据库.md` §3.11 的索引 `(user_id, scope)` 命中后再过滤此列）；**吊销不删行、不改 `agreed_at`**（表中无 `updated_at` 列），失效时刻只有 `revoked_at` 一个来源；吊销后**不自动恢复**——用户重新确认（§5.1）会插入**新的** `consents` 行（`revoked_at = NULL`），旧行的 `revoked_at` 永久保留，形成"同意 → 吊销 → 再同意"的完整轨迹。删除级联（`modules/M08-账号历史与彻底删除.md` §3.3）写**同一个** `revoked_at` 列、同样不删行，是本列的第二条写入路径（末段）。

服务端入口（本期无 UI、无端点）：

```ts
// src/server/domain/anchorService.ts：吊销该用户某授权项的全部有效行，返回被吊销的行数。
export function revokeConsents(userId: number, scope: ConsentScope): number;
// UPDATE consents SET revoked_at = ? WHERE user_id = ? AND scope = ? AND revoked_at IS NULL
```

调用点只有三处：`scripts/acceptance.ts` 的 `SEC-03`（吊销 `photo_usage` 后发起生成必须得 `403 CONSENT_REQUIRED`）；将来的投诉/下架流程（`spec/06-合规与风控.md` §10，本期不做）；账号处置流程（`modules/M08-账号历史与彻底删除.md`）。**不新增端点**，也不在测试之外自动调用。

**`DELETE /api/anchors/:id` 与 `DELETE /api/photos/:id` 都不删 `consents` 行，但命中被删锚点的行会写 `revoked_at`**（`modules/M08-账号历史与彻底删除.md` §3.3、`spec/01-领域模型与数据库.md` §2.3、`spec/06-合规与风控.md` §6.2）：删除后该行授权立即失效，轨迹完整保留；锚点行被物理删除后不会留下 `revoked_at IS NULL` 的悬空授权。删除本身另写 `audit_logs`（`photo.delete` / `anchor.delete`），与吊销入口（§5.5）在审计上可区分——删除是"我不要再看到这些图"，吊销是"我当初的同意撤销了"，两者都落 `revoked_at`，但审计动作名不同。

## 6. 边界与错误

| 错误码 | 触发条件 |
|---|---|
| `UNAUTHENTICATED` | confirm / retry / DELETE 未登录或会话过期（`requireUser()` 抛出） |
| `ANCHOR_NOT_FOUND` | 锚点不存在、已软删除、或属于他人（三者不区分） |
| `ANCHOR_NOT_CONFIRMED` | confirm 时 `status != 'succeeded'` 或 `anchor_text` 为空；retry 时旧行非终态；生成时 `status != 'succeeded'` 或 `confirmed_by_user != 1` |
| `INVALID_PARAM` | confirm 的 `consents` 未同时包含两项；`confirmed` 不为 `true`（schema 用 `z.literal(true)`）；路径 `:id` 非整数 |
| `CONSENT_REQUIRED` | 生成时 `photo_usage` 无 `revoked_at IS NULL` 的行 |
| `INTERNAL` | 事务内未预期异常（含审计写入失败，`spec/04-技术基线与目录结构.md` §4.1） |

约定：`INVALID_PARAM` 的具体缺失项**不新增错误码**，一律走 `details.fields`（前端据此高亮复选框，§10）；码与 HTTP 状态、用户可见文案的唯一事实源是 `spec/03-接口契约.md` §5，本节只记触发条件、不复述。

## 8. 测试要点
### 8.1 单元测试（`pnpm test`，`vitest`）
`confirmAnchor`：① 成功路径 → `confirmedByUser: true`、`confirmedAt` 非空，`consents` 恰好 2 行且 `revoked_at IS NULL`，`audit_logs` 恰好 2 条（`anchor.confirm` / `consent.agree`）且其 `created_at` 与 `consents.agreed_at` 逐字符相等；② `status` 为 `failed` / `running` / `queued`，或 `succeeded` 但 `anchor_text` 为 `NULL` → `ANCHOR_NOT_CONFIRMED` / 409，且 `confirmed_by_user` 仍为 0、`consents` 0 行、`audit_logs` 0 行（事务原子性）；③ `consents` 只缺一项（两个方向各测一次）→ `INVALID_PARAM` / 400，`details.fields.consents` 恰好列出缺失项，DB 无任何写入（**`SEC-02` 的单元形态**）；他人锚点 → `ANCHOR_NOT_FOUND` / 404（不是 403）；`{ confirmed: false }` → `INVALID_PARAM` / 400 且不写行；④ 连续调用两次 → 均 200，`consents` 仍 2 行，`confirmed_at` 不变，`audit_logs` 4 条；先 `revokeConsents(userId, 'photo_usage')` 再 confirm → `consents` 新增 1 行、旧行 `revoked_at` 仍非空。

`retryAnchor`：⑤ 新行 `attempt === 旧行.attempt + 1`，`input_photo_ids` 与 `preprocessed_photo_id` 与旧行**逐字符相等**，`status='queued'`，`confirmed_by_user = 0`；旧行全部字段（`anchor_text` / `features_json` / `confirmed_by_user` / `finished_at` / `error_code`）前后逐字段相等；旧行 `queued` / `running` → 409 且不产生新行；`audit_logs` 新增 `anchor.extract`，`meta_json.retryOf === 旧 id`。⑥ `createGeneration` 顺序（**`SEC-01` / `SEC-03`**）：`confirmed_by_user = 0` 且无任何 `consents` 行 → 409（不得是 403）；`confirmed_by_user = 1` 且 `photo_usage` 的 `revoked_at` 非空 → 403 `CONSENT_REQUIRED`，且**不产生** `generations` 行。⑦ `audit()` 在已开启的事务内抛错 → 整个事务回滚、`audit_logs` 无残留行；`meta` 经 `JSON.stringify` 写入后读回为对象；`target` 形如 `anchor:3`。

### 8.2 契约与链路检查（`pnpm check:acceptance`，`PROVIDER=mock`）
`SEC-01`：未确认锚点（`confirmed_by_user=0`）发起生成 → `409 ANCHOR_NOT_CONFIRMED`，依赖 §5.3 的**判定顺序**，测试数据无需预置 `consents`。`SEC-02`：confirm 时 `consents` 缺 `family_agreement` → `400 INVALID_PARAM`，并复查数据库：`identity_anchors.confirmed_by_user` 仍为 0、`consents` 无新增行。`SEC-03`：调 `revokeConsents` 吊销 `photo_usage` 后发起生成 → `403 CONSENT_REQUIRED`。`SEC-09`：确认锚点时写入 `audit_logs(action='anchor.confirm')` 与 `audit_logs(action='consent.agree')` 各一条——这是"授权留痕"义务的检查项（`spec/06-合规与风控.md` §2 第 5 项、`spec/07-验收标准.md` §2.5），归属本模块。相关但不属本文件：`API-03`（未登录 → 401）、`API-04`（他人锚点 → 404，不返回 403）、`DEL-01`–`DEL-04`（§5.4 的级联与 `anchor.delete` 审计）、`E2E-01`（链路第 4 步即 confirm）。完成判定：`pnpm check`（类型 + lint）零错误、`pnpm test` 全绿、`pnpm check:acceptance` 中 `SEC-01/02/03` 与 `SEC-09` 通过（`spec/07-验收标准.md` §5）。

## 9. 审计写入约定

```ts
// src/server/security/audit.ts
export type AuditAction =
  | 'auth.code_sent' | 'auth.login' | 'auth.logout' | 'auth.realname'
  | 'photo.upload' | 'photo.preprocess' | 'photo.mark' | 'photo.delete' | 'photo.purge'
  | 'anchor.extract' | 'anchor.confirm' | 'anchor.delete' | 'consent.agree'
  | 'generation.create' | 'generation.finish' | 'moderation.reject';

export interface AuditEntry {
  userId: number | null;                 // 匿名操作（发码前）为 null
  action: AuditAction;
  target?: string | null;                // 'anchor:3' / 'photo:12' / 'generation:7'
  meta?: Record<string, unknown> | null; // 只放原子值
}
/** 唯一业务入口。必须在调用方已开启的事务内调用。 */
export function audit(entry: AuditEntry, at?: string): void;
```

- **时间戳与落库**：默认时间取 `nowIso()`；传 `at` 时用于让 `audit_logs.created_at` 与同事务内业务写入的时间戳**逐字符相等**（§5.1 ④）。落库只有一句 `INSERT INTO audit_logs (user_id, action, target, meta_json, created_at) VALUES (?,?,?,?,?)`，SQL 在 `src/server/db/repositories/audit.ts`，`meta_json` 由 `JSON.stringify` 序列化。
- **取值一致**：`AuditAction` 的 16 个取值与 `spec/01-领域模型与数据库.md` §3.14 的清单**完全一致**，不增不减；本文件写其中 4 个：`anchor.confirm`、`consent.agree`、`anchor.extract`（retry）、`anchor.delete`，另 4 个 `auth.*`（`auth.code_sent` / `auth.login` / `auth.logout` / `auth.realname`）归 `modules/M08-账号历史与彻底删除.md`。16 个 action 中**没有吊销项**，故 `revokeConsents`（§5.5）不写审计；若将来合规要求留痕，须先按 §3.14 增补 action 名。
- **事务、失败与调用点**：`audit()` **不允许**在业务事务外调用（`spec/04-技术基线与目录结构.md` §4.3）；审计写入失败**不回吞**，抛出异常让整个事务回滚——这些 action 是合规证据，宁可让请求失败也不留半截记录。调用点仅 `src/server/domain/*`、`src/server/auth/*`、`src/jobs/handlers/*`，`app/api/**/route.ts` **不得**直接调 `audit()`。
- **`meta` 内容**：只放 id、`attempt`、`scope` 数组、`cascaded` 计数。禁止放 prompt 全文（`generations.prompt` 已落库），禁止放手机号/邮箱明文（用 `src/server/auth/mask.ts`）。

## 10. 两个授权勾选框的逐字文案

| `scope` | 勾选框文案（逐字，建议采用） |
|---|---|
| `photo_usage` | `我确认我手上有这张照片的使用权，也确认照片里的人是我认识的人。` |
| `family_agreement` | `我已经和家里其他亲属说过这件事，他们同意我用这张照片来做。` |

同页面的辅助与操作文案（非授权项）：勾选框下方小字（**默认可见、不可折叠**）为 `如果家里有不同意见，请先沟通好再来做。`；提交按钮为 `这就是他，开始生成`，未勾齐时的行内提示为 `需要两项都勾上才能开始`。约定：两项**都必须显式勾选**，前端**不得**预勾选，不得用一个"同意以上全部"的合并框代替；复选框的 `name` 直接取 `scope` 值，提交给 `POST /api/anchors/:id/confirm` 的 `consents` 数组顺序与文案顺序无关；缺项时后端返回 `400 INVALID_PARAM`，`details.fields.consents` 列出缺失项，前端据此高亮对应复选框。页面位置与视觉见 `pages/P01-上传与身份确认.md`、`pages/P00-设计基准与路由.md`；本文件是这两句文案的**权威来源**。
