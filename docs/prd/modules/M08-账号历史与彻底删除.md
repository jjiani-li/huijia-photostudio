## 1. 职责与边界
**做**：① 账号——验证码下发（归一化、10 分钟过期、同 `identifier` 60 秒节流）、登录建号、会话签发与吊销、`requireUser()` 鉴权、手机号/邮箱脱敏；② 实名——`POST` / `GET /api/me/realname` 与生成前硬门槛（§2.2）；③ 历史——按 `identity_anchors.created_at DESC` 返回「原图 → 预处理图 → 生成结果」链路（§4）；④ 彻底删除——两个 `DELETE` 的级联软删除与 `deleted_at` 到期后的物理清理（§3.3、§5.2、§5.3）。

**落点**：`src/server/auth/{session,sms,idVerify,mask}.ts`、`src/server/security/quota.ts`、`src/server/db/repositories/{users,sessions,loginCodes,usage,photos,anchors,generations,consents,audit}.ts`、`src/server/domain/deletionService.ts`、`src/jobs/{worker,registry,handlers/purge}.ts`、`app/api/{auth/**,me,me/realname,history,photos/[id],anchors/[id]}/route.ts`、`scripts/acceptance.ts`。

**不做（禁令与红线）**：
- ❌ 密码、社交登录、一键登录、注册表单、找回密码（`spec/00-总纲.md` §6.1 F5 只要求验证码登录）；历史导出、分享、跨用户查询；
- ❌ 真实短信通道与**真实身份核验**：`SMS_PROVIDER=real` / `ID_VERIFY_PROVIDER=real` 取该值时抛 `INTERNAL`；**本地实名 ≠ 真实身份核验**（`spec/06-合规与风控.md` §5.2 对照表）；
- ❌ 文件加密存储、HTTPS、对象存储、外链签名（`spec/00-总纲.md` §6.2）；❌ 用户自助注销 / 批量清空——本期「彻底删除」的粒度是单张照片与单个锚点；**反推任务（`prompt_reverse_jobs`）不进历史**（§4）；
- ❌ 金额计费（只有 `usage_counters` 计数）；不新增表、不新增错误码、不新增 `audit_logs.action`（`spec/01-领域模型与数据库.md` §3.14 的清单是封闭集合，本模块只写其中的 `auth.*`：`auth.code_sent` / `auth.login` / `auth.logout` / `auth.realname`）。

**归属 ticket**：`tickets/T12`（账号、会话与额度，覆盖 §1–3；其中 §3.1 的 `readQuota()` / `QuotaView` 随额度下沉归 `tickets/T09`）、`tickets/T13`（历史记录、再生成与彻底删除，覆盖 §4–6）、`tickets/T19-实名、用户资料与生成门槛.md`（实名，覆盖 §2.2）。
## 2. 账号、会话与实名
### 2.1 验证码登录与会话
**标识归一化**（`normalizeIdentifier(raw, channel?)`）：`trim`；含 `@` 或显式 `channel='email'` 走邮箱（转小写，须匹配 `/^[^@\s]+@[^@\s]+\.[^@\s]+$/`），否则走手机号（去掉空格、`-`、`(`、`)`，剥离 `+86` / 前导 `86`，须为 `1[3-9]\d{9}`）；失败 → `400 INVALID_PARAM`。归一化结果即 `login_codes.identifier` 与 `users.phone` / `users.email` 的写入值。
- **发码**（`requestLoginCode`）：节流查询命中（同 `identifier` 60 秒内已有 `consumed_at IS NULL` 的记录）→ `429 CODE_RATE_LIMITED`；否则 `code = crypto.randomInt(0, 1_000_000).toString().padStart(6, '0')` → `INSERT login_codes(purpose='login', expires_at = now + 10min)` → `getSmsSender().send(identifier, code)` → `INSERT audit_logs(action='auth.code_sent')` → `{ sent: true, expiresInSec: 600, devCode? }`。
- **登录**（`loginWithCode`，单事务）校验顺序固定为「存在/已消费 → 过期 → 码值」：无 `purpose='login'` 行或 `consumed_at` 非空 → `400 CODE_INVALID`；`expires_at < now` → `400 CODE_EXPIRED`；码不符 → `400 CODE_INVALID`。随后 `UPDATE login_codes SET consumed_at` → 按 `phone` / `email` 查/建 `users`（`nickname` 先写占位值，再 `UPDATE users SET nickname = '用户' || printf('%04d', id % 10000)`，等价 TS `用户${String(id).padStart(4,'0').slice(-4)}`）→ `UPDATE users SET last_login_at` → `INSERT sessions(token_hash = sha256hex(token), expires_at = now + 30 天)` → `INSERT audit_logs(action='auth.login')`。
- 码比对用 `crypto.timingSafeEqual`（比较前校验长度均为 6）；`SMS_PROVIDER=console` 时 `DEV_LOGIN_CODE`（默认 `000000`）可作「万能码」通过码值比对，**但仍要求存在未消费且未过期的记录**。`ConsoleSmsSender` 打印 `[SMS] 138****8000 验证码 000000（10 分钟内有效）`；`exposeDevCode()` 返回 `process.env.SMS_PROVIDER === 'console'`，route handler 仅在其为真时给响应加 `devCode`，并调 `assertDevCodeAllowed(payload)` 做实现层断言（失败抛 `INTERNAL`，**不透出 code**）。
- **会话 cookie**：`Set-Cookie: sid=<crypto.randomBytes(32).toString('base64url')>; HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000`（30 天，与 `sessions.expires_at` 一致）；不设 `Secure`、不设 `Domain`（本地 http）。`sessions.token_hash = sha256(token)` 十六进制小写，明文只在响应里出现一次。**登出**：`UPDATE sessions SET revoked_at = now WHERE token_hash = ? AND revoked_at IS NULL` + 清 cookie（同名 `Max-Age=0`）+ `audit_logs(action='auth.logout')` → `{ ok: true }`。状态机：`active ── 登出 ──▶ revoked`（`revoked_at` 非空）；`active ── expires_at < now ──▶ expired`（不做定时清理，只在查询时判定）。
```ts
export const SID_COOKIE = 'sid';
export interface SessionUser { id: number; phone: string | null; email: string | null; nickname: string; status: number }
export function getSessionUser(): SessionUser | null;   // 读 cookie → sha256 → sessions 活跃行 → users.status=1
export function requireUser(): SessionUser;             // 失败 throw new AppError('UNAUTHENTICATED', …, 401)（文案取 spec/03-接口契约.md §5）
export function createSession(userId: number): { token: string; expiresAt: string };
export function destroySession(token: string | null): void;
export function maskPhone(phone: string | null): string | null;   // '13800138000' → '138****8000'；长度不足 7 时整串替换为等长 '*'
export function maskEmail(email: string | null): string | null;   // 'abcd@x.com' → 'a***@x.com'；local 长度 1 → '***@x.com'
export function maskIdentifier(identifier: string): string;       // 含 '@' 走 maskEmail，否则 maskPhone；null 入参返回 null
```
`getSessionUser()` 顺序：cookie 缺失或不匹配 `^[A-Za-z0-9_-]{43}$` → `null`（不查库）；`sessions` 命中条件 `token_hash = ? AND revoked_at IS NULL AND expires_at > nowIso()`；再查 `users`，`status = 0` 视为不可用。每个受保护端点在 handler 第一行调 `requireUser()`（`spec/03-接口契约.md` §1.2 的受保护清单）。脱敏规则：手机号保留前 3 与后 4 位、中间固定 4 个 `*`；邮箱保留本地部分首字符 + `***` + `@` + 域名原文。`GET /api/me` 的 `user.phone` / `user.email` 必须经此二函数，`API-05` 据此断言响应含 `*`。
### 2.2 实名（生成前门槛）
**三个字段**（`spec/01-领域模型与数据库.md` §3.1）：`users.real_name`、`users.id_hash`（UNIQUE，`sha256(证件号)`，**只存哈希、不存明文**）、`users.verified_at`（**非空即已实名**）；列名**不得泄漏到任何 API 响应**（`spec/06-合规与风控.md` §5.2）。
**端点**（逐字取自 `spec/03-接口契约.md` §3.1，不新增字段）：`POST /api/me/realname` 请求 `{ realName, idNumber }`、响应 `200 { realNameStatus: RealNameStatus }`，写入 `users.real_name`、`users.id_hash`、`users.verified_at`；`realName` / `idNumber` 为空或格式非法 → `400 INVALID_PARAM`（`details.fields`），`id_hash` 已被其他用户占用 → `400 INVALID_PARAM`（`details.fields`）。`GET /api/me/realname` 响应 `200 { realNameStatus: RealNameStatus }`（`verified` / `verifiedAt` / `realName`，形状见 `spec/03-接口契约.md` §4）；未实名时 `verified=false`、`verifiedAt=null`、`realName=null`。
```ts
// src/server/auth/idVerify.ts —— 与 Storage / SMS / Ark 三个 Provider 抽象同一惯例
export interface IdVerifyRequest { realName: string; idNumber: string }
export interface IdVerifyResult { realName: string; idHash: string; verifiedAt: string }
export interface IdVerifyProvider { verify(req: IdVerifyRequest): IdVerifyResult }
export function getIdVerifyProvider(): IdVerifyProvider;
// ID_VERIFY_PROVIDER=local（默认）→ LocalIdVerifyProvider；=real → throw new AppError('INTERNAL', …, 500)
```
`LocalIdVerifyProvider` = **格式校验（长度与校验位）+ 唯一性校验（`id_hash` 唯一）**；`real` 是生产留空位（`spec/04-技术基线与目录结构.md` §1 的四个 Provider 抽象表、`spec/08-本地开发指南.md` §4–§5）。
**生成门槛**：`POST /api/generations` 的校验序列**第 1 步**即 `users.verified_at IS NULL` → `409 REALNAME_REQUIRED`，**硬拒绝，且不产生 `generations` 行**；无降级路径、不自动重试（`spec/03-接口契约.md` §3.5、`spec/06-合规与风控.md` §5.2）。校验顺序以 `spec/03-接口契约.md` §3.5 为准——**实名在锚点确认之前**，先于 `modules/M04-身份确认与授权.md` §5.3 的 `ANCHOR_NOT_CONFIRMED`（409）与 `CONSENT_REQUIRED`（403）两步。
**本地实名 ≠ 真实身份核验**：本地不接触任何权威数据源，不做联网核验、人脸比对、一号多账号拦截、频次风控；「本地实现 / 生产必须补」的逐项对照见 `spec/06-合规与风控.md` §5.2，本文件不重复。**审计留痕**：`POST /api/me/realname` 成功时在同一事务内写 `audit_logs(action='auth.realname')` 一行（`user_id` = 当前用户，`target='user:{id}'`）；校验失败（`INVALID_PARAM`）不写。检查项 `RN-01`（未实名生成被拒且无 `generations` 行）、`RN-02`（`id_hash` 不以明文落库，同证件号重提得同一哈希）、`RN-03`（唯一性冲突被拒）、`RN-04`（审计留痕）见 `spec/07-验收标准.md` §2.10；端点检查项 `API-09`；owning ticket `tickets/T19-实名、用户资料与生成门槛.md`。
## 3. 数据读写与关键 SQL
### 3.1 账号、会话与额度

| 表 | 操作 | 字段 |
|---|---|---|
| `login_codes` | INSERT / SELECT / UPDATE | `identifier`（归一化后）、`code`、`purpose='login'`、`expires_at`、`created_at`、`consumed_at` |
| `users` | SELECT / INSERT / UPDATE | 按 `phone` / `email` 查；首登 INSERT（`nickname`、`daily_image_quota` 默认 20、`created_at`）；UPDATE `nickname`、`last_login_at`、`real_name` / `id_hash` / `verified_at`（§2.2） |
| `sessions` | INSERT / SELECT / UPDATE | `token_hash`（sha256 十六进制小写）、`expires_at`（创建 + 30 天）、`created_at`、`revoked_at` |
| `usage_counters` | SELECT / UPSERT | `(user_id, day)` → `images` / `generations`；无行按 0 计；额度判断读 `users.daily_image_quota`，入队预扣 `count`、worker 内未产出张数回滚（`modules/M06-生成编排.md` §5） |
| `audit_logs` | INSERT | `auth.code_sent`、`auth.login`、`auth.logout`、`auth.realname`（§2.2） |

`GET /api/me` 只暴露当日额度数值：`interface QuotaView { day: string; images: number; limit: number; remaining: number }`；`readQuota(userId: number): QuotaView`（`src/server/security/quota.ts`，随额度下沉归 `tickets/T09`）；`toApiUser(u: UserRecord): ApiUser`（`ApiUser` = `User` + `createdAt`，`mask.ts` 在此调用）。
### 3.2 历史
只读，不写任何表（`spec/04-技术基线与目录结构.md` §3.1 允许 `/api/history` 直连 repository）：`identity_anchors`（`user_id` + `status='succeeded'`，按 `(created_at, id) DESC`）；`photos`（`input_photo_ids` 中第一个未软删除的行 = 原图、`preprocessed_photo_id` 对应行）；`generations`（按 `anchor_id`，每锚点最近 10 条）；`generation_results`（按 `generation_id`，`photo_id` 对应照片未软删除）。

**未完成的照片**（`GET /api/photos`，`spec/03-接口契约.md` §3.2）：同一批表上的**互补查询**——取 `photos.deleted_at IS NULL` 且不被任何 `status='succeeded'` 锚点链路（`input_photo_ids` / `preprocessed_photo_id` / 该锚点 generations 下 `generation_results.photo_id`）引用的行，按 `(created_at, id) DESC` 分页。**游标与 §4 的历史分页各自独立、不通用**（混用 → `400 INVALID_PARAM`）。
### 3.3 彻底删除（级联规则）
写路径：`photos` UPDATE `deleted_at`（`WHERE deleted_at IS NULL` 保幂等）；`consents` UPDATE `revoked_at`（`anchor_id IN (受影响锚点) AND revoked_at IS NULL`，**不删行**）；`identity_anchors` / `generations` / `prompt_reverse_jobs` **物理 DELETE**（三表均无 `deleted_at` 列，且 `anchor_text` / `prompt` / `result_prompt` 含人物特征描述，软删会在「彻底删除」后长期留存）；`generation_results` **物理 DELETE**（与 `generations` 同一事务，`spec/01-领域模型与数据库.md` §2.3）；`audit_logs` INSERT `photo.delete`（`target='photo:{id}'`）与 `anchor.delete`（`target='anchor:{id}'`）。

**`DELETE /api/photos/:id` 级联规则表**（按目标照片的 `kind`）：

| 目标 `kind` | `photos` 被 UPDATE `deleted_at` | `identity_anchors` | `generations` | `generation_results` | `consents` |
|---|---|---|---|---|---|
| `original` | 该行 + `source_photo_id = :id AND kind='preprocessed'` 的派生图 + 受影响 generations 下 `generation_results.photo_id` 指向的 `kind='generated'` 图 | 物理 DELETE：`preprocessed_photo_id = :id` **或** `json_each(input_photo_ids)` 含 `:id` | 物理 DELETE：`anchor_id IN (受影响锚点)` | 物理 DELETE（与 `generations` 同一事务） | UPDATE `revoked_at` |
| `preprocessed` | 该行 + 受影响 generations 下的 generated 图（其 `source_photo_id` 指向的 original **不动**） | 物理 DELETE：仅 `preprocessed_photo_id = :id` 的锚点 | 同上 | 同上 | 同上 |
| `generated` | 该行（不含其他） | 不动 | 不动 | 保留 | 不动 |

**`DELETE /api/anchors/:id` 级联规则**：`identity_anchors` 仅物理 DELETE 该行（`id = :id AND user_id = :userId`）→ `generations` 物理 DELETE（`anchor_id = :id AND user_id = :userId`）→ 上述 generations 的 `generation_results.photo_id` 指向的 `kind='generated'` 图 UPDATE `deleted_at`；`generation_results` 物理 DELETE（与 `generations` 同一事务）；`consents` 写 `revoked_at`（`anchor_id = :id AND revoked_at IS NULL`）。关键语义：**删锚点不删原图与预处理图**；**删生成图不影响其 `generations` 行与锚点**。用户的 `prompt_reverse_jobs` 行按 `user_id = :userId AND source_photo_id IN (:受影响照片)` 一并物理 DELETE（`source_photo_id` 与 `user_id` 级联，`spec/01-领域模型与数据库.md` §3.15）。
### 3.4 关键 SQL
发码节流：`SELECT id FROM login_codes WHERE identifier = :identifier AND consumed_at IS NULL AND created_at > :nowMinus60s ORDER BY created_at DESC LIMIT 1;`

历史分页（`json_each` 展开 `input_photo_ids`；行值比较需 SQLite ≥ 3.15，`better-sqlite3` 已满足）：
```sql
SELECT a.id, a.anchor_text, a.confirmed_at, a.created_at, a.input_photo_ids, a.preprocessed_photo_id FROM identity_anchors a
WHERE a.user_id = :userId AND a.status = 'succeeded' AND EXISTS (
    SELECT 1 FROM json_each(a.input_photo_ids) je JOIN photos p ON p.id = je.value WHERE p.user_id = a.user_id AND p.deleted_at IS NULL)
  AND (:cursorCreatedAt IS NULL OR (a.created_at, a.id) < (:cursorCreatedAt, :cursorId))
ORDER BY a.created_at DESC, a.id DESC LIMIT :limit + 1;
```
每锚点最近 10 条生成：`SELECT * FROM (SELECT g.*, ROW_NUMBER() OVER (PARTITION BY g.anchor_id ORDER BY g.created_at DESC, g.id DESC) AS rn FROM generations g WHERE g.user_id = :userId AND g.anchor_id IN (:anchorIds)) WHERE rn <= 10;`（SQLite ≥ 3.25 窗口函数）

级联标记（同一事务内的批量语句）：
```sql
UPDATE photos SET deleted_at = :now WHERE id IN (:photoIds) AND deleted_at IS NULL;
UPDATE consents SET revoked_at = :now WHERE anchor_id IN (:anchorIds) AND revoked_at IS NULL;
DELETE FROM prompt_reverse_jobs WHERE user_id = :userId AND source_photo_id IN (:photoIds);
DELETE FROM generations WHERE id IN (:generationIds);
DELETE FROM identity_anchors WHERE id IN (:anchorIds);
DELETE FROM generation_results WHERE generation_id IN (:generationIds);
```
物理清理扫描：`SELECT id, user_id, storage_key, bytes FROM photos WHERE deleted_at IS NOT NULL AND deleted_at < :threshold ORDER BY deleted_at ASC LIMIT :batchSize;`（走 `idx_photos_deleted`）
## 4. 历史链路
`GET /api/history?cursor=<opaque>&limit=20`（形状见 `spec/03-接口契约.md` §3.6）：响应 `{ items: HistoryItem[], nextCursor }`，`HistoryItem` 含 `anchorId`、`anchorText`、`confirmedAt`、`sourcePhoto`、`preprocessedPhoto`、`generations: Generation[]`；照片 `url` 一律带 `?w=400`。
- 游标是**不透明串** `base64url(createdAt + '|' + id)`，前端只回传不解析（`spec/03-接口契约.md` §6.4）；`limit` 不在 `[1,50]`、或解码后不匹配 `^\d{4}-\d{2}-\d{2}T.*\|\d+$` → `400 INVALID_PARAM`。
- 只返回未软删除的照片；某锚点的原图全部软删除时该锚点不出现（§3.4 的 `EXISTS` 子句），这是 `DEL-01` 的直接实现；`generations` 最多返回该锚点下最近 10 条；只返回 `status='succeeded'` 的锚点（`HistoryItem.anchorText` 不可空）。
- **边界**：链路只覆盖「原图 → 预处理图 → 锚点 → 生成结果」。**反推任务不进入历史**——它是工具，不产出照片资产，也不占 `usage_counters.images`；本条不新增端点、不新增历史字段。
- **用同样设定再生成**：`POST /api/generations/:id/retry` 产生**新行**（`attempt = 0`，继承 `anchorId` / `eraCode` / `sceneId` / `count` / `params`），旧行与其 `generation_results` 零修改（`spec/03-接口契约.md` §3.5、`modules/M06-生成编排.md` §5）。
## 5. 关键流程与状态机
### 5.1 限流与实名门槛

| 环节 | 规则 |
|---|---|
| 发码限流 | 同 `identifier` 60 秒内已有 `consumed_at IS NULL` 的记录 → `429 CODE_RATE_LIMITED`（`API-07`）；`expiresInSec` 恒为 `600` |
| 登录校验顺序 | 固定为「存在/已消费 → 过期 → 码值」，避免用过期状态探测码值 |
| 实名门槛 | 生成序列第 1 步（§2.2）：`users.verified_at IS NULL` → `409 REALNAME_REQUIRED`，不产生 `generations` 行 |
| 会话与脱敏 | 见 §2.1 的状态机与 `getSessionUser()` 顺序；`GET /api/me` 的 `user.phone` / `user.email` 必须为 `mask.ts` 输出，`/api/history` 响应体不得出现手机号或邮箱明文 |

### 5.2 级联软删除
`deletePhoto(userId, photoId)` / `deleteAnchor(userId, anchorId)` 先做归属校验（`photos.user_id` / `identity_anchors.user_id` 不等于当前用户 → `404 NOT_FOUND`，**不返回 403**，`API-04`）；级联解析顺序为「目标 → 受影响锚点 → 受影响 `generations` → 受影响 generated 照片 → 受影响反推任务」，再在**单个 `db.transaction()`** 内批量执行 §3.4 的语句并写审计。
**响应计数**：`cascaded.preprocessed` = 被标记的 `kind='preprocessed'` 行数；`cascaded.anchors` = 被物理删除的锚点数；`cascaded.generations` = 被物理删除的 `generations` 数；`cascaded.results` = 这些 generations 名下 `generation_results` 的行数（删除前记数）。键名与 `spec/03-接口契约.md` §3.2 / §3.3 完全一致，**不新增键**（`DELETE /api/photos/:id` 恰 `preprocessed` / `anchors` / `generations` / `results`；`DELETE /api/anchors/:id` 恰 `generations` / `results`）。
**幂等**：目标行存在且已软删（照片）、链路上已物理删除的重复调用、或目标行已被 `runPurge()` 物理清理 → `200 { ok: true, cascaded: 全零 }`（`spec/03-接口契约.md` §1.5）；目标行属于其他用户 → `404 NOT_FOUND`（不返回 403，`API-04`）。
### 5.3 物理清理
```ts
// src/jobs/handlers/purge.ts
export const PURGE_INTERVAL_MS = 10 * 60 * 1000;   // worker 触发间隔
export const PURGE_GRACE_MINUTES = 10;             // deleted_at 早于该阈值才可清理
export const PURGE_BATCH_SIZE = 200;
export interface PurgeResult { scanned: number; purged: number; failed: number; deletedResults: number }
export async function runPurge(now?: string): Promise<PurgeResult>;
```
单批流程（`now` 缺省用 `nowIso()`）：① 按 §3.4 的扫描 SQL 取 `deleted_at < now - PURGE_GRACE_MINUTES` 的照片；② 逐行 `getStorage().delete(storage_key)`——文件不存在视为成功（幂等，记 `logger.warn`），单行失败记 `failed` 并**跳过该行**（保留 `photos` 行，下轮重试），不整批失败；③ 单个 `db.transaction()`：`DELETE FROM generation_results WHERE generation_id NOT IN (SELECT id FROM generations)`（兜底清理孤儿行）→ `DELETE FROM prompt_reverse_jobs WHERE source_photo_id IN (:batchIds)` → `DELETE FROM photos WHERE id IN (:batchIds)` → 逐行 INSERT `audit_logs(action='photo.purge', user_id, target = 'photo:' + id, meta_json = { bytes, storageKey })`；④ 若 `scanned === PURGE_BATCH_SIZE`，立即再跑一批，直到不足一批。
**触发方式**：`purge` **不进入任何任务表**（`src/jobs/registry.ts` 不注册该类型；它不是可领取任务，`spec/03-接口契约.md` §2 的三类异步操作不含它），由 `src/jobs/worker.ts` 主循环执行——主循环的启动回收、拉取顺序、空转等待与并发度见 `spec/04-技术基线与目录结构.md` §4.6。purge 自己的两条规则：进程启动第一轮立即 `runPurge()` 一次；其后每轮在「当前无 `running` 任务」且 `Date.now() - lastPurgeAt >= PURGE_INTERVAL_MS` 时执行；异常必须被捕获并记日志，**绝不中断 worker**。`DEL-03` 由 `scripts/acceptance.ts` 直接 `import { runPurge }` 后调用一次实现「手动触发」，**不新增 `pnpm` 脚本**；`CMP-05`（连续两次 `runPurge()`，第二次全零）是同一实现的幂等断言。
**照片生命周期**：`active (deleted_at IS NULL) ── DELETE /api/photos/:id ──▶ soft-deleted`（`deleted_at = now`，立即从 `/api/history` 与 `/api/photos/:id/file` 消失，audit `photo.delete`）`── runPurge()（deleted_at < now - 10min）──▶ purged`（删磁盘文件 → 删 `generation_results` / `prompt_reverse_jobs` → 物理 DELETE `photos` 行，audit `photo.purge`）。**「彻底」的判定标准**（`spec/06-合规与风控.md` §6.2）：删除后 `storage/` 下不存在任何未被 `photos` 行引用的残留文件，且 `photos` 行本身也不再存在；仅软删不算彻底；按 `spec/09-施工纪律.md` §1 的权威性顺序，以 `spec/03-接口契约.md` §1.5 为准——`purged` 后的重复 `DELETE` 恒返回 `200`（幂等，`cascaded` 全为 0）。
## 6. 边界与错误

| 错误码 | 触发条件 |
|---|---|
| `UNAUTHENTICATED` | cookie 缺失/格式非法、`sessions` 无活跃行、`expires_at` 已过、`revoked_at` 非空、`users.status=0` |
| `NOT_FOUND` | 两个 `DELETE` 的目标属于其他用户；`GET /api/photos/:id/file` 命中软删除行 |
| `INVALID_PARAM` | `identifier` 归一化失败；`cursor` 非法；`limit` 不在 `[1,50]`；实名的 `realName` / `idNumber` 为空或格式非法（含 `id_hash` 被占用） |
| `CODE_INVALID` | 无 `login_codes` 行、`consumed_at` 非空、或码值与记录不符（非 console 万能码） |
| `CODE_EXPIRED` | 记录存在且未消费，但 `expires_at < now` |
| `CODE_RATE_LIMITED` | 同 `identifier` 60 秒内已有 `consumed_at IS NULL` 的记录 |
| `REALNAME_REQUIRED` | 生成时 `users.verified_at IS NULL`（§2.2） |
| `INTERNAL` | `SMS_PROVIDER=real` / `ID_VERIFY_PROVIDER=real`（本期无真实通道）；`assertDevCodeAllowed` 断言失败 |

归一化后的 `identifier` 才写库与查库（`users.phone` 恒 11 位纯数字、`users.email` 恒小写），`API-05` 的脱敏断言不受输入大小写影响；照片清理失败只影响该行（`photos.deleted_at` 保持原值，下轮重试）；以上八项错误码全部来自 `spec/03-接口契约.md` §5，本文件**不新增错误码**；码与 HTTP 状态、用户可见文案的唯一事实源是该表（§5），本文件只记触发条件、不复述。
