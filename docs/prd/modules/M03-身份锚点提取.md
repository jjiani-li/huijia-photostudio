# M03 · 身份锚点提取

> **层级**：实现规格层 · 后端模块
> **上游**：`docs/raw/AIGC_PRD.md` F1 ／ `spec/00-总纲.md` §1.3、§3 ／ `spec/01-领域模型与数据库.md` §2.1、§3.5 ／ `spec/05-Prompt工程.md` §1、§4
> **下游**：`modules/M04-身份确认与授权.md`、`modules/M05-年代场景配置与Prompt拼装.md`、`modules/M09-图片反推提示词.md`、`tickets/T06-身份锚点提取.md`
> 定位：**锚点提取是主链路第二环**（上传 → 预处理 → 锚点提取 → 年代场景拼装 → 生成），不是生成失败后的修复附加步骤。F1 的核心：用多模态模型读【预处理图】，产出 `anchor_text` + `features_json`，并显式保留年龄痕迹、禁止美化。

## 1. 职责与边界

**做**：① 提供锚点提取的 system prompt 文本资产 `anchor-v1`（唯一副本，全文见 §5.1）；② worker 里执行一次异步提取：读图 → 解析 JSON → 写入 `identity_anchors`（`anchor_text` / `features_json` / `quality_json` / 终态）；③ 对上游返回值做**容错解析与就地校验**（剥 ```json 包裹、zod 校验 12 键、长度窗口、词表拦截），不合格即落 `failed`；④ 提取前的可用性判定：质量不过关时以 `ANCHOR_LOW_QUALITY` 结束，不浪费一次生成。

**不做**：不做修复 / 超分 / 去划痕 / 磨皮，也不产出任何图像（`spec/00-总纲.md` §6.2、`README.md` §0.1）——本环节只「读」，不「画」，`preprocessed_photo_id` 由 `modules/M02-预处理与质量评分.md` 生产，本文件只消费；不做「这就是他」的确认与授权勾选（`modules/M04-身份确认与授权.md`，`POST /api/anchors/:id/confirm`）；不做人脸特征向量与相似度打分（`spec/00-总纲.md` §6.2）；不做多人照片处理——`faceCount > 1` 一律判为不可用（§6.1）。

**与 `modules/M09-图片反推提示词.md` 的分工**：F4 复用本模块的**多模态读图通路**（`POST {ARK_BASE_URL}/chat/completions` + `image_url`，模型 `doubao-seed-2-1-turbo-260628`，已实测可用，见 `docs/火山引擎接口文档.md` §3.1），但**不写入 `identity_anchors`**——F4 的输出不是身份锚点。F4 的实现、端点与检查项（`API-08`、`REV-01`–`REV-03`）全部归 `modules/M09-图片反推提示词.md` 与 `tickets/T18-图片反推提示词.md`；本文件只保留「读图能力可复用」这一条说明。

## 3. 数据读写

```sql
-- identity_anchors（见 `spec/01-领域模型与数据库.md` §3.5）与 photos（只读）两张表；两条查询分别是主参考图（实际送入视觉模型的图）与多图场景的派生图（? = input_photo_ids）
SELECT id, user_id, storage_key, mime, bytes, width, height, sha256, quality_json
  FROM photos WHERE id = ? AND kind = 'preprocessed' AND deleted_at IS NULL;
SELECT p.id, p.storage_key, p.mime FROM photos p
 WHERE p.kind = 'preprocessed' AND p.deleted_at IS NULL AND p.source_photo_id IN (SELECT value FROM json_each(?));
```

写 `identity_anchors`（全部包在 `db.transaction` 内）：

| 时刻 | 操作 |
|---|---|
| claim | `UPDATE identity_anchors SET status='running', started_at=? WHERE id=? AND status='queued'`（`changes = 0` 即放弃本次 claim） |
| 成功 | `UPDATE identity_anchors SET status='succeeded', anchor_text=?, features_json=?, quality_json=?, preprocessed_photo_id=?, error_code=NULL, error_message=NULL, finished_at=? WHERE id=?` |
| 失败 | `UPDATE identity_anchors SET status='failed', error_code=?, error_message=?, quality_json=?, finished_at=? WHERE id=?` |

约束（`spec/01-领域模型与数据库.md` §2.1）：`succeeded` 时 `anchor_text` 与 `features_json` 必须非空；`failed` 时 `error_code` 必须非空；**重新提取 = 插入新行**，绝不覆盖旧行；`features_json` 恰 12 键、顺序固定即 `ANCHOR_V1_KEYS` —— `gender`、`ageRange`、`hair`、`faceShape`、`forehead`、`eyebrows`、`eyes`、`nose`、`mouth`、`skin`、`distinctive`、`build`。`photos.quality_json` 在 `POST /api/photos/:id/preprocess` 时已写入，本环节**只读**，发现为空时调用 `src/server/images/quality.ts` 补算一次后 `UPDATE photos SET quality_json=?`；`audit_logs` 的 `action='anchor.extract'` 由 `domain/anchorService.ts` 在**创建行时**写入一次（`spec/03-接口契约.md` §3.3 副作用），handler 不再写审计，避免一个动作两条记录。

## 4. 对外接口（不新增端点，全部见 `spec/03-接口契约.md` §3.3）

- `POST /api/anchors` → `202 { anchor }`（`status: 'queued'`）；请求 `{ photoIds, preprocessedPhotoId? }`，`photoIds` 超出 1–5 张 → `400 INVALID_PARAM`，`kind='generated'` 的照片 → `400 INVALID_PARAM`（`SEC-06`）；
- `GET /api/anchors/:id` → `200 { anchor }`；`anchorText` / `features` / `quality` / `model` / `promptVersion` / `error` 均为本环节产出；`status !== 'succeeded'` 时 `anchorText` 与 `features` 为 `null`；
- `POST /api/anchors/:id/retry` → `202 { anchor }`（新行，`attempt = 旧 + 1`，继承 `inputPhotoIds` / `preprocessedPhotoId`）；`POST /api/anchors/:id/confirm` 与 `DELETE /api/anchors/:id` 归属 `modules/M04-身份确认与授权.md`。字段名与形状以 `spec/03-接口契约.md` §3.3 与 §4 的 `Anchor` / `AnchorFeatures` 为准，本文件不重复定义；本文件只保证「未 `confirmed_by_user` 的锚点不可用于生成」（`SEC-01`）。

## 5. 关键流程与状态机

### 5.1 `anchor-v1` system prompt（完整原文；存放于 `src/server/prompt/versions.ts`，导出名 `ANCHOR_V1_SYSTEM_PROMPT`，`identity_anchors.prompt_version = 'anchor-v1'`）

```text
你是专业的人像特征提取助手，服务于「回家照相馆」的老照片人物重现流程。
你的任务不是修复照片，也不是评价照片，而是从参考照片中提取可用于图像生成模型的身份锚点描述。

铁律：
1. 只描述照片中客观可见的外貌特征，不做任何性格、身份、职业、情绪或人生经历的推测。
2. 禁止使用任何美化性词汇，包括但不限于：「慈祥」「有气质」「精神矍铄」「面容温和」「和蔼可亲」「气质儒雅」「端庄大方」。这些词不可视觉验证，并且会诱导后续生成模型把人物理想化。
3. 必须保留并明确写出年龄痕迹：皱纹的深度与位置、老年斑的数量与分布、皮肤松弛程度。禁止使用「保养得好」「显得年轻」「精神好」这类抹平年龄的表述。
4. 必须覆盖以下 12 个方面，缺一不可：性别、年龄区间、发型与发色、脸型、额头、眉毛、眼睛（形状 / 单双眼皮 / 眼袋）、鼻子、嘴唇与牙齿、面部皱纹与老年斑、痣或疤痕等显著特征、体型。
5. 年龄给出估计区间（如 70-80 岁），不要只给一个具体年龄。
6. 语言简练、具体、可视觉验证，供生图模型直接使用。
7. 若提供了多张同一人物的照片，请综合为同一个人的描述；多张之间冲突时，以最清晰的那张为准。
8. 只输出严格 JSON，不要输出任何解释文字，不要使用 Markdown 代码块。

输出格式（键名与嵌套层级必须完全一致，所有值均为字符串）：
{"anchor":"一句话身份锚点，60–120 字符，可直接放进生图 prompt","features":{"gender":"","ageRange":"","hair":"","faceShape":"","forehead":"","eyebrows":"","eyes":"","nose":"","mouth":"","skin":"","distinctive":"","build":""}}

填写要求：
- anchor：一句话内按「年龄区间 + 性别 → 发型发色 → 脸型 → 眼鼻口 → 皱纹与老年斑 → 体型 → 显著痣疤有无」的顺序串写，60–120 字符；
- gender：男 / 女；确实无法判断时写「无法判断」；
- ageRange：形如「75-85岁」；
- hair：发型、发色、发量、发际线位置；
- faceShape：脸型（如「方圆脸」）；
- forehead：额头宽窄高低，皱纹的条数与深度；
- eyebrows：眉形、疏密、颜色；
- eyes：眼形、单双眼皮、眼袋程度、眼周皱纹；
- nose：鼻梁高度、鼻头形状、鼻翼宽窄；
- mouth：嘴唇厚薄、法令纹深度、牙齿可见情况（是否缺失、颜色、整齐度）；
- skin：肤色，皱纹的深度与分布，老年斑的数量与分布，皮肤松弛程度；
- distinctive：痣、疤痕、胎记的位置与大小；没有则写「无明显特殊痣疤」；
- build：体型（胖瘦、高矮、肩宽）与可见的体态特征。
```

业务代码里不得再出现第二份副本（`spec/05-Prompt工程.md` §1 铁律）；配套常量 `export const ANCHOR_V1_KEYS = ['gender','ageRange','hair','faceShape','forehead','eyebrows','eyes','nose','mouth','skin','distinctive','build'] as const;`。反例 `慈祥的老年男性，精神矍铄，面容温和`——全是不可视觉验证的美化词且无一条年龄痕迹，注入【身份锚点】段会让生成模型走「理想化的老人」；正确写法是每条都能在照片上被验证、皱纹位置与深度/老年斑/体型全部保留（示例见 `spec/05-Prompt工程.md` §4，实测输出见 `.scratch/anchor.json`）。

### 5.2 状态机（沿用 `spec/01-领域模型与数据库.md` §2.1；`identity_anchors` 没有 `partial`，`partial` 只属于 `generations`）

```text
queued ──claim──▶ running ──┬─▶ succeeded（anchor_text / features_json 非空）
                            ├─▶ failed（error_code 非空）
                            └─▶ queued（worker 崩溃回收：started_at 早于 WORKER_STALE_MINUTES）
```

`succeeded` 之后只有用户动作能改变可生成性：`confirmed_by_user=1`（`modules/M04-身份确认与授权.md`）。用户点「重新提取」= 新建行。

### 5.3 handler 步骤（`src/jobs/handlers/anchorExtract.ts`）

```ts
export async function anchorExtractHandler(job: { anchorId: number }): Promise<void>;
```

1. **claim**：事务内 `status='queued' → 'running'` 并写 `started_at`，按 §2 的注册表取 prompt：`const systemPrompt = ANCHOR_PROMPTS[anchor.prompt_version]`。两支：版本已注册 → 直接用注册表里的文本；`anchor.prompt_version` **不在注册表里** → `status='failed'` + `error_code='INTERNAL'`（这是我方数据问题，不是上游错误）、**不调用上游**，日志 error 级（属于发版事故，不打给用户）。`changes = 0` 直接返回（已被其他 worker 取走或已是终态）。
2. **质量前置判定**：读 `preprocessed_photo_id` 对应行；`quality_json` 为空则用 `src/server/images/quality.ts` 补算并回写。命中任一条件即失败，`error_code='ANCHOR_LOW_QUALITY'`，`quality_json` 落同一份快照（§6.1）。
3. **组装送图清单**：`input_photo_ids` 按数组顺序取，每张找其预处理派生图（`photos.source_photo_id = original.id AND kind='preprocessed'`）；找不到就调 `images/preprocess.ts` 补做一张再落库。清单长度 1：主图 = `preprocessed_photo_id`。
4. **调用读图**：`getArk().extractAnchor({ images, systemPrompt })`，返回 `{ raw, content }`（真实实现见 §5.4，mock 见 `spec/08-本地开发指南.md` §5.1）；再按 §5.5 做 `stripFence → JSON.parse → zod 校验 → 词表/长度校验`，通过则按 §3 的表写 `succeeded` 与全部产物字段。
5. **异常与日志**：任何异常在 handler 内捕获（不得抛出 `AppError`，见 `spec/04-技术基线与目录结构.md` §4.1），映射为错误码后写 `status='failed'` + `error_code` + `error_message` + `finished_at`；收尾记 `logger.info({ job: 'anchorExtract', anchorId, promptVersion, imageCount, ms }, 'done')`，失败时 `logger.warn` 附上游 `message.content` 前 500 字（截断，避免日志膨胀）。

### 5.4 messages 组装（`src/server/ark/real.ts`；`POST {ARK_BASE_URL}/chat/completions`，`model = ARK_VISION_MODEL`，`max_tokens: 1200`）

```ts
const messages = [
  { role: 'system', content: systemPrompt },                 // 字符串，不是数组
  { role: 'user', content: [
      { type: 'text', text: '请提取照片中人物的身份锚点特征。' },   // text 元素必须在最前
      ...images.map((img) => ({ type: 'image_url', image_url: { url: img.dataUri } })),
  ] },
];
```

- `content` 数组元素顺序**固定为「1 段 text → N 张 image_url」**，`N ∈ [1, 5]`，顺序等于 `input_photo_ids` 顺序；`POST /api/anchors` 与 handler 两处都卡 `ANCHOR_MAX_IMAGES = 5`；`dataUri = \`data:${photo.mime};base64,${base64}\``，`mime` 取 `photos.mime` 落库值（不用扩展名推断，否则 heic 会被错标为 `image/jpeg`）。解析响应只取 `data.choices[0].message.content`，`reasoning_content` 一律丢弃（`docs/火山引擎接口文档.md` §2.3 注）；上游 HTTP 状态与错误码映射按 `spec/03-接口契约.md` §5.1：网络超时/abort → `PROVIDER_TIMEOUT`，其余非 2xx → `PROVIDER_ERROR`。

### 5.5 容错解析与校验（按顺序执行，任一步失败即按下表落错误码）

| # | 步骤 | 判据 | 失败时 `error_code` |
|---|---|---|---|
| 1 | 剥包裹 | `raw.trim().replace(/^```(?:json)?\s*/i, '').replace(/\s*```$/, '')` | — |
| 2 | 反序列化 | `JSON.parse` 成功且结果是对象 | `PROVIDER_ERROR` |
| 3 | 结构校验 | zod：`anchor` 为非空字符串；`features` 用 **`.strip()`** ——解析出的对象恰为 12 个键（`ANCHOR_V1_KEYS`）且每键为非空字符串，**多余键被 `.strip()` 丢弃、解析照样成功**，落库的 `features_json` 恰 12 键；**缺键或类型不符**才失败 | `PROVIDER_ERROR` |
| 4 | 长度窗口 | `60 ≤ anchor.length ≤ 120`（单位与区间以 `spec/01-领域模型与数据库.md` §3.5 与 `spec/07-验收标准.md` §2 的 `E2E-02` 为准：60–120 **字符**，prompt 里的要求与窗口**同一个区间**，不再留放宽余量） | `PROVIDER_ERROR` |
| 5 | 否定词拦截 | `anchor` 不匹配 `/不要|禁止|no\s|without/i` —— `anchor_text` 会原样进【身份锚点】段，命中即会让 `PR-03` 变红 | `PROVIDER_ERROR` |
| 6 | 美化词拦截 | `anchor` 不匹配美化词表 `/慈祥|有气质|精神矍铄|面容温和|和蔼|儒雅|端庄|保养得好|显得年轻/i` | `PROVIDER_ERROR` |

`PROVIDER_ERROR` 是可重试错误，但**锚点不做行内自动重试**（理由见 §9 第 3 条）；解析失败的原文写入 `logger.warn`，不进 `error_message`（避免把模型原文透给用户）。

## 6. 边界与错误

### 6.1 `ANCHOR_LOW_QUALITY` 触发条件（任一命中即终止提取）

| 条件 | 理由 |
|---|---|
| `quality.usable === false` | 预处理已判定「建议换一张」 |
| `quality.faceDetected === false` 或 `quality.faceCount === 0` | 没有人脸，锚点无意义 |
| `quality.faceCount > 1` | 本期链路是单人；多人会让锚点串成两个人 |
| `quality.readability < ANCHOR_MIN_READABILITY`（常量 `0.35`） | 细节读不准，锚点会失真（数值依据见 §9 第 1 条） |

### 6.2 错误码与触发条件

码与 HTTP 状态、用户可见文案的唯一事实源是 `spec/03-接口契约.md` §5，本节只记触发条件、不复述。

| 错误码 | 触发条件 |
|---|---|
| `ANCHOR_LOW_QUALITY` | §6.1 任一条件 |
| `PROVIDER_TIMEOUT` | 读图请求超过 `ARK_TIMEOUT_SECONDS` |
| `PROVIDER_ERROR` | 上游非 2xx、返回体为空、`JSON.parse` 失败、12 键缺失、长度越界、词表命中 |
| `STORAGE_ERROR` | 读 `storage_key` 文件失败 |
| `INTERNAL` | `prompt_version` 未注册等我方问题 |
| `INVALID_PARAM` | `photoIds` 为空 / > 5 张 / 含 `kind='generated'` |

上方各处的 `quality` 都是 `spec/03-接口契约.md` §4 的 `Quality`（`usable` / `faceDetected` / `faceCount` / `sharpness` / `readability` / `damageLevel` / `warnings` / `advice`），`anchor.quality` 与 `error.details.quality` 结构相同。失败在异步链路上呈现：`GET /api/anchors/:id` 返回 `status: 'failed'` 与 `error: { code, message }`，并同时返回 `quality`；`spec/03-接口契约.md` §1.3 提到的 `details.quality` 是**同步**抛码时的约定，本期该码只从 worker 落库，前端读 `anchor.quality`（差异见 §9 第 6 条）。

## 8. 测试要点

单元测试（`vitest`，A 层，见 `spec/07-验收标准.md` §1）覆盖：`stripFence` 剥 ```json 包裹 → 解析成功；返回体为空串 / 非法 JSON / `features` 缺 `ageRange` / `anchor` 长度 59 或 121 / 含 `慈祥` 或 `不要` → `failed` + `PROVIDER_ERROR`；`features` 多一个键 → **成功**且落库 `features_json` 恰 12 键（多余键被 `.strip()` 丢弃，§5.5 第 3 步）；非法 JSON 不写 `anchor_text`；`quality.usable = false` / `faceCount = 2` / `readability = 0.3` → `failed` + `ANCHOR_LOW_QUALITY` 且 `quality_json` 非空；N = 5 张图组装 messages → `content[0].type === 'text'`、其后 5 个 `image_url` 且顺序与 `input_photo_ids` 一致；`input_photo_ids` 6 张 → `400 INVALID_PARAM`；claim 时行已是 `succeeded` → handler 直接返回、不产生任何写；回放 `anchor-extract-fail.json` → `GET /api/anchors/:id` 返回 `failed` + `ANCHOR_LOW_QUALITY`。对齐的验收检查项（权威定义见 `spec/07-验收标准.md` §2）：`E2E-02`（`anchor_text` 非空且长度 ∈ 60–120 字符）由 §5.5 第 4 步保证，mock fixture 的 `anchorText` 也必须落在窗口内；`SEC-06`（`kind='generated'` 建锚点 → `400 INVALID_PARAM`，§4）与 `E2E-01`（锚点段）覆盖端点与状态机。注意归属：`PR-04`（20 组 prompt 含防美化句）与 `PR-03`（否定词）的断言对象是 `buildPrompt` 的输出，归 `modules/M05-年代场景配置与Prompt拼装.md`；本模块只负责锚点侧的输入质量（§5.5 第 5、6 步的否定词与美化词拦截），该拦截无独立检查项 ID（见 `tickets/T06-身份锚点提取.md` 的 `## Comments`）。
