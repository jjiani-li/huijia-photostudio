# M02 · 预处理与质量评分

> **层级**：实现规格层 · 后端模块
> **上游**：`docs/raw/AIGC_PRD.md` §3、§4 ／ `spec/00-总纲.md` §1.3、§4.4 ／ `spec/03-接口契约.md` §3.2、§4
> **下游**：`modules/M03-身份锚点提取.md`、`modules/M06-生成编排.md`、`pages/P01-上传与身份确认.md`、`tickets/T04-预处理与质量评分.md`

F1 的前半段：把上传的旧照片整理成**模型读得准**的形态并给出可读性判定——**不修复、不美化、不做超分**（`docs/prd/README.md` §0.1）。产物只有两个用途：`identity_anchors.preprocessed_photo_id`（读图输入）与 `generations.reference_photo_ids`（生图参考图），见 `spec/03-接口契约.md` §3.2、§3.3、§3.5。
## 1. 职责与边界
**1.1 做什么**：① 方向校正（按 EXIF Orientation 旋转到正向）② 色彩空间统一到 sRGB ③ 剥离 EXIF / ICC / IPTC / XMP 元数据 ④ 尺寸归一（长边目标 1600px，**不足时绝不放大**）⑤ 统一输出 `image/jpeg`，质量 92 ⑥ 质量评分 → `quality_json`（`Quality` 8 键）⑦ 落库 `photos(kind='preprocessed')`，`source_photo_id` 指向原图。
### 1.2 为什么这里没有"修复"
用户那张旧照片是这个人的唯一证据：先用 AI 把它重画清楚，后续锚点提取与生成锚定的就都是一张 **AI 想象的脸**，身份保真从根上断了（`spec/00-总纲.md` §1.3），§4.4 的"面部相似度 ≥ 0.55"从第一条就无解。因此本模块只做**读得像**（让多模态模型与 Seedream 能稳定读取），不做**看着好看**（`docs/prd/README.md` §0.1）。
### 1.3 明确不做（禁令清单）
| 不做 | 理由 |
|---|---|
| 超分 / 分辨率提升 / 放大（含 2x、4x） | 放大 = 用插值或模型**编造**像素；编造的像素会进入锚点与参考图 |
| 去噪 / 去划痕 / 去灰尘 / 去网纹 | 抹掉的细节位置无法还原，属于"画"而非"读" |
| 锐化（`unsharp`/`sharpen`）/ 提高对比度 / 直方图拉伸 | 会改变皱纹、老年斑的可辨识边界，与 `spec/00-总纲.md` §4.2 冲突 |
| 美颜 / 磨皮 / 减龄 / 提亮肤色 | `docs/prd/README.md` §0.4 红线 |
| 人脸裁剪 / 人脸对齐 / 换脸预处理 | 会改变脸型比例与构图；构图继承是 `docs/raw/AIGC_PRD.md` §5.7 已记录的坑 |
| 基于 AI 的重绘或"修复 provider" | `spec/00-总纲.md` §6.2 已列为本期不做；扩展位 `EnhanceProvider` 保留 |
| 缩略图 | 走 `GET /api/photos/:id/file?w=`，由存储层按需生成（`spec/04-技术基线与目录结构.md` §2） |
| 阻断流程 | `usable=false` 仍返回 `200`，由前端决定是否放行（§6.1） |
| 隐式标识写入 | `src/server/images/mark.ts` 只对 `kind='generated'` 生效（`spec/06-合规与风控.md`） |
## 2. 涉及文件
路径取自 `spec/04-技术基线与目录结构.md` §2，**不新增目录**（应用根 = 仓库根）。端点 `app/api/photos/[id]/preprocess/route.ts`；服务 `src/server/domain/anchorService.ts`（导出 `preprocessPhoto(userId, photoId)`，唯一允许同时调 repository + `images/` + `storage/` 的地方）；纯函数 `src/server/images/preprocess.ts`、`src/server/images/quality.ts`、`src/server/images/probe.ts`；`src/server/db/repositories/photos.ts`（`findPreprocessedBySource` / `insertPreprocessed` / `findOriginalById`）、`src/server/storage/{index,local}.ts`、`src/server/security/audit.ts`；错误码复用 `src/server/domain/errors.ts` 的 `NOT_FOUND` / `INVALID_PARAM` / `INVALID_FILE_TYPE` / `STORAGE_ERROR` / `INTERNAL`（触发条件见 §6.3），**不新增**；`src/shared/types.ts` 只消费 `Quality` / `Photo`。测试：`src/server/images/{preprocess,quality}.test.ts`（见 §8.1）。
## 3. 数据读写
### 3.1 读
`photos` 取 `id, user_id, kind, storage_key, mime, bytes, width, height, sha256, deleted_at`，条件 `id = :id AND user_id = :userId AND deleted_at IS NULL`。`kind` 校验：`generated` → `400 INVALID_PARAM`（生成图不得再作输入，`spec/01-领域模型与数据库.md` §3.4、`SEC-06`）；`preprocessed` → `400 INVALID_PARAM`（本端点只接受 `kind='original'`）。
### 3.2 幂等键查询（本模块的核心 SQL）
```sql
SELECT id, storage_key, mime, bytes, width, height, sha256, quality_json, created_at
FROM photos
WHERE source_photo_id = :sourcePhotoId AND kind = 'preprocessed' AND deleted_at IS NULL
ORDER BY created_at DESC LIMIT 1;
```
命中即**直接返回该行**（§5.3）。去重键是 `source_photo_id`，**不是** `sha256`——`photos.sha256` 的重用规则只属于 `POST /api/photos`（`spec/03-接口契约.md` §1.5）。
### 3.3 写与不写

写入**只经** `photos.insertPreprocessed(...)`（签名见 `modules/M01-照片资产与存储.md` §5；`mime` 恒传 `'image/jpeg'`），下面的 SQL 是它的实现：

```sql
INSERT INTO photos (user_id, kind, storage_key, mime, bytes, width, height,
                    sha256, source_photo_id, quality_json, deleted_at, created_at)
VALUES (:userId, 'preprocessed', :storageKey, 'image/jpeg', :bytes, :width, :height,
        :sha256, :sourcePhotoId, :qualityJson, NULL, :nowIso);
```
| 字段 | 取值规则 |
|---|---|
| `kind` / `mime` | 固定 `'preprocessed'` / 固定 `'image/jpeg'` |
| `storage_key` | `buildKey(userId, 'jpg')` → `u{userId}/{uuid}.jpg`，**相对路径**，不写公网 URL |
| `width` / `height` | 归一化后实际像素（`probe.ts` 复核值，**不是**计算值） |
| `sha256` | 归一化后**文件内容**的 sha256 |
| `source_photo_id` / `quality_json` | 入参原图的 `photos.id` / `JSON.stringify(Quality)`，键名与 `spec/03-接口契约.md` §4 逐字段一致（camelCase；它是 JSON 列，不做 snake 转换） |
同事务内追加 `audit_logs`：`INSERT INTO audit_logs (user_id, action, target, meta_json, created_at) VALUES (:userId, 'photo.preprocess', 'photo:' || :newPhotoId, '{"sourcePhotoId":12,"usable":true,"readability":0.78}', :nowIso);`；`action` 取值来自 `spec/01-领域模型与数据库.md` §3.14 的固定清单。本模块不写 `identity_anchors.quality_json`（那是 `modules/M03-身份锚点提取.md` 创建锚点行时对本模块 `Quality` 的**快照复制**），也不写 `content_reviews`（上传阶段的审核行由 `POST /api/photos` 写，`spec/03-接口契约.md` §3.2）。
## 4. 对外接口
唯一端点 `POST /api/photos/:id/preprocess`（定义见 `spec/03-接口契约.md` §3.2）：受保护端点（`requireUser()`；未登录 → `401 UNAUTHENTICATED`）；同步执行，预期 < 2s，成功返回 `200`，响应形状 `{ photo: Photo, quality: Quality }`，**不新增字段、不新增端点**；`usable = false` 时**同样返回 `200`**（原文："由前端决定是否放行"）；幂等：同一 `sourcePhotoId` 已存在 `preprocessed` 行则直接返回该行（§5.3）。`quality` 的 8 个键**顺序与含义照抄** `spec/03-接口契约.md` §4 的 `Quality`，本模块是它的唯一生产者；浮点值写库前 `Math.round(v * 1000) / 1000` 取三位小数（与 `docs/raw/AIGC_PRD.md` §9 的 `quality_score NUMERIC(4,3)` 精度一致），保证 `API-02` 的响应断言稳定：

| 键 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `usable` | `boolean` | — | 可用性终判，见 §6.1 |
| `faceDetected` | `boolean` | — | 是否检出人脸（或退化模式下是否有中心高频能量，见 §4.2） |
| `faceCount` | `number` | ≥ 0 整数 | 检出的人脸数；退化模式下为 `faceDetected ? 1 : 0` |
| `sharpness` | `number` | [0, 1] | 清晰度，见 §4.1 |
| `readability` | `number` | [0, 1] | 综合可读性，见 §4.1 |
| `damageLevel` | `number` | [0, 1] | 破损/褪色程度，见 §4.1 |
| `warnings` | `string[]` | 可空数组 | 不阻断的提示，见 §6.2 |
| `advice` | `string \| null` | — | `usable=false` 时的换图建议；`usable=true` 恒为 `null` |
### 4.1 评分算法与标定表（分析副本：对归一化结果再构造一次 `sharp()`，缩到长边 ≤ 1024 的灰度图）
```ts
// src/server/images/quality.ts
type SharpStats = {                 // sharp().stats() 的返回形状（只列本模块用到的键）
  channels: Array<{ stdev: number }>; isOpaque: boolean; entropy: number; sharpness: number;
};

export interface AnalysisInput {
  gray1024: Uint8Array;        // 长边 ≤ 1024 的灰度原始像素（sharp().greyscale().resize({ width: 1024, height: 1024, fit: 'inside', withoutEnlargement: true }).raw()）
  stats: SharpStats;           // sharp().stats() 的返回值（channels / isOpaque / entropy / sharpness）
  histogram: number[];         // gray1024 的 256 桶直方图（由 preprocess.ts 计算，不来自 sharp）
  width: number;               // 归一化后的实际宽高（像素）
  height: number;
  faceBox: { x: number; y: number; w: number; h: number } | null; // 人脸框（本机没启用人脸检测时为 null）
}
export function scoreQuality(a: AnalysisInput): Quality;

const clamp01 = (v: number) => Math.min(1, Math.max(0, v));
// —— 以下 5 个本地量全部由上面的字段直接导出，伪代码不引用任何外部符号 ——
const L      = a.stats.sharpness;                                          // Laplacian 卷积标准差
const sd     = a.stats.channels[0].stdev;                                  // 亮度通道标准差
const pixels = a.gray1024.length;                                          // 灰度图一字节一像素，长度即像素总数
const hi     = a.histogram.slice(250).reduce((s, n) => s + n, 0) / pixels; // 单通道 uint8 中 v>=250 的占比
const lo     = a.histogram.slice(0, 6).reduce((s, n) => s + n, 0) / pixels; // 单通道 uint8 中 v<=5 的占比

const sharpness     = clamp01((L - SHARP_FLOOR) / (SHARP_CEIL - SHARP_FLOOR));
const resScore      = clamp01(Math.min(a.width, a.height) / 1000);           // 短边 1000px 记满分
const contrastScore = clamp01(sd / 64);                                      // 亮度标准差 64 记满分
const faceSizeScore = a.faceBox ? clamp01((Math.max(a.faceBox.w, a.faceBox.h) / Math.max(a.width, a.height) - 0.05) / (0.30 - 0.05)) : FALLBACK_FACE_SIZE_SCORE;
const readability   = 0.35 * resScore + 0.25 * contrastScore + 0.25 * sharpness + 0.15 * faceSizeScore;
const tailScore     = clamp01((hi + lo) / 0.08);   // 尾部合计 8% 视为严重损坏
const hfLoss        = clamp01(1 - L / HF_REFERENCE);                        // HF_REFERENCE = 20.0
const damageLevel   = 0.5 * tailScore + 0.5 * hfLoss;
```
**六个字段各自由谁算**（本模块是纯函数，只消费不生产）：进 `scoreQuality()` 之前，`preprocess.ts` 的归一化流水线（§5.1 步 ⑦）对归一化缓冲再构造一次 `sharp()` 产出 `gray1024`（`.greyscale().resize({ width: 1024, height: 1024, fit: 'inside', withoutEnlargement: true }).raw()`）与 `stats`（同一实例的 `.stats()`），`width` / `height` 取该流水线归一化并经 `probe.ts` 复核后的实际像素；`histogram` 是 `gray1024` 的 256 桶计数，由 `preprocess.ts` 逐字节统计、**不来自 sharp**；`faceBox` 由 §4.2 选定的人脸检测方案给出，未启用检测（退化路径）时为 `null`。
标定表（标定常数：`SHARP_FLOOR = 3.0`、`SHARP_CEIL = 15.0`、`HF_REFERENCE = 20.0`、`FALLBACK_FACE_SIZE_SCORE = 0.6`）：

| 子分 | 权重 | 常数 | 依据 |
|---|---|---|---|
| `resScore` | 0.35 | `1000` | 分辨率是"面部细节够不够"的第一决定项 |
| `contrastScore` | 0.25 | `64` | 正常曝光 jpeg 的亮度标准差量级；褪色照显著偏低 |
| `blurScore`（= `sharpness`） | 0.25 | 同 `sharpness` | 焦不实/抖动直接毁掉特征 |
| `faceSizeScore` | 0.15 | `0.05` / `0.30` | 人脸长边占整图长边 5% 以下基本不可读，30% 以上充分 |
`tailScore` 抓**高光溢出 / 暗部压死**（过曝的白脸、发黑的脸），泛黄褪色**不触发**它；`hfLoss` 抓高频能量整体缺失（糊 + 脏），与 `sharpness` 同源但取相反方向，故给 0.5 权重。常数必须用 `docs/老照片/*.jpg` 与 `fixtures/` 样本标定，标定值写回常量并在 `tickets/T04-预处理与质量评分.md` 的 `## Comments` 记录实测表。本模块**不做划痕/破损检测**：任何"破损位置"结论都会诱导后续做修复（`spec/00-总纲.md` §1.3），故上游的"破损程度"只降级为尾部 + 高频两项。
### 4.2 人脸检测方案选型（含退化路径）
三个候选：① `@vladmandic/face-api`（Node 版，TFJS CPU）② `onnxruntime-node` + 现成人脸检测 onnx 模型——两者都产出 `faceDetected` / `faceCount` / `faceBox`，代价是新依赖 + 模型权重文件（native 模块在 Windows 上需预编译产物）；③ **退化路径：中心区域高频能量估计**，零新依赖，复用 §4.1 的拉普拉斯统计。
退化路径（确定性可复现）：取居中、宽高各 60% 的中心区域，`faceDetected = centerL >= CENTER_FACE_FLOOR`（`CENTER_FACE_FLOOR = 6.0`）；命中时 `faceCount = 1`、`faceSizeScore = FALLBACK_FACE_SIZE_SCORE = 0.6`，并在 `warnings` 追加 §6.2 的"未启用本地人脸检测"提示。三个方案任选其一是允许的，但必须在 `tickets/T04-预处理与质量评分.md` 的 `## Comments` 写明选了哪一个；不选 ①② 时 `usable` 判定不得因此收紧（`faceDetected` 只在退化模式下参与判定，见 §6.1），否则本地零外部依赖的约束（`docs/prd/README.md` §4.3）会被打破。该选型列为**待定决策**（§9.2）。
## 5. 关键流程与状态机
### 5.1 七步流水线
```
① 读行 photos.findOriginalById(id, userId)：无行或 deleted_at 非空 → 404 NOT_FOUND；kind != 'original' → 400 INVALID_PARAM（不返回 403 以避免探测，API-04）
② 读文件 getStorage().read(row.storage_key)：失败 → STORAGE_ERROR（文件是唯一存储介质，spec/04-技术基线与目录结构.md §4.5）
③ 方向校正 .rotate()（无参数 = 按 EXIF Orientation 自动旋转）：必须在 ④⑤ 之前，否则旋转后宽高互换会把归一化尺寸算错
④ 色彩空间统一 .pipelineColourspace('srgb16').toColourspace('srgb')：源图可能是 CMYK / Display P3 / 无 profile，统一后读图与生图模型的颜色判断才一致
⑤ 尺寸归一 long = max(w, h)；long >= 1600 → scale = 1600 / long、target = round(w*scale) × round(h*scale)；long < 1600 不 resize；.resize({ width, height, fit: 'inside', kernel: 'lanczos3', withoutEnlargement: true })（withoutEnlargement 是"绝不放大"的硬保护）
⑥ jpeg 编码 .jpeg({ quality: 92, chromaSubsampling: '4:4:4', mozjpeg: false })：4:4:4 保住肤色与老年斑的颜色边界（2x2 会抹掉细小色差）；mozjpeg: false 保证跨机器输出字节稳定（E2E-07 依赖确定性）
⑦ 构造评分输入并落库（§4.1、§3.3）：对 ⑥ 的 jpeg 缓冲再构造一次 sharp(buf)，.greyscale().resize({ width: 1024, height: 1024, fit: 'inside', withoutEnlargement: true }).raw() 取 gray1024、同一实例 .stats() 取 stats；histogram 由 histogram256(gray1024) 逐字节统计（256 桶，本模块算、不来自 sharp）；width / height 取 ⑤ 归一化后经 probe.ts 复核的实际像素；faceBox 取 §4.2 选定方案（退化路径下恒为 null）→ scoreQuality(input) 得 Quality，随后单事务内经 photos.insertPreprocessed(...) 写 photos 并写 audit_logs（§3.3）
```
**元数据剥离不需要额外一步**：sharp 默认**不**保留元数据，只有显式 `.withMetadata()` / `.keepMetadata()` 才会写回——因此本模块**禁止调用这两个方法**，这就是"剥离 EXIF/ICC/IPTC/XMP"的实现方式。`.resize()` **不做裁剪**（`fit: 'inside'` 而非 `'cover'`），裁剪会改构图（§1.3）。
### 5.2 归一化函数契约（纯函数：不读库、不写盘、不看环境变量；测试直接喂 Buffer）
```ts
// src/server/images/preprocess.ts
export interface NormalizeResult {
  buffer: Buffer;                  // 归一化后的 jpeg
  width: number; height: number;   // probe.ts 复核后的实际宽高
  resized: boolean;                // false 表示长边本就 < 1600，未做任何缩放
}
export async function normalize(input: Buffer): Promise<NormalizeResult>;
```
### 5.3 幂等语义
```
POST /api/photos/:id/preprocess
  ├─ 已有 preprocessed 行（source_photo_id = :id, deleted_at IS NULL）→ 直接返回该行 + 该行 quality_json 反序列化出的 Quality（不重算、不落新行、不写审计）
  └─ 无 → 执行 §5.1 七步 → 单事务内 `photos.insertPreprocessed(...)` + `audit.insert('photo.preprocess')` → 返回新行
```
判重必须在**取到原图行之后、读文件之前**，避免无谓 IO；同一进程内并发同一 `:id` 用模块级单飞表去重 `Map<number, Promise<PreprocessResult>>`（dev server 单进程，本期不引入分布式锁）。`preprocessed` 行**没有状态列**，本端点是同步的——`spec/01-领域模型与数据库.md` §2.3 的照片生命周期（`deleted_at` 软删 + 清理 worker 物理删除）就是它唯一的状态机；原图被删时本模块产出的行由级联软删一并标记，不需要本模块主动处理。
## 6. 边界与错误
### 6.1 `usable` 与 `advice` 判定阈值表（顺序即优先级，第一个命中的行决定二者）
| 序 | 条件 | `usable` | `advice`（原文） |
|---|---|---|---|
| 1 | `faceDetected = false && faceCount = 0` | `false` | `照片里没找到人脸，换一张人物正脸、别太小的试试` |
| 2 | `readability < 0.35` | `false` | `这张照片太模糊或者太暗，人物特征看不清，建议换一张更清楚的` |
| 3 | `damageLevel > 0.60` | `false` | `这张照片褪色或者破损得比较厉害，可能认不准长相，建议换一张保存得更好的` |
| 4 | `min(width, height) < 320` | `false` | `这张照片太小了，放不进面部细节，建议换一张大一点的` |
| 5 | 其余 | `true` | `null`，`warnings` 按 §6.2 累计 |
`usable=false` **不阻断流程**：仍返回 `200` 与完整 `Quality`；前端展示 `advice` 与一个"仍然用这张"的次级按钮，点了继续走 `POST /api/anchors`（`spec/03-接口契约.md` §3.3）。服务端**不**在预处理阶段拒绝——最终裁判是用户点"这就是他"的那一下（`spec/00-总纲.md` §3 铁律）。第 4 条必须存在：`usable=true` 而 `min(width,height) = 180` 会让锚点提取在模型侧直接失败。
### 6.2 `warnings` 取值集合（固定文案，不自由拼接）
| 触发条件 | 文案 |
|---|---|
| 长边原本 < 1600（`resized = false`） | `原图分辨率偏低，面部细节可能不足`（与 `spec/03-接口契约.md` §3.2 示例逐字符一致） |
| `faceCount >= 2` | `照片里有 N 个人，系统会以画面中间那个人为准` |
| `readability ∈ [0.35, 0.50)` | `这张照片不算清楚，认特征可能会有点偏差` |
| `damageLevel ∈ (0.40, 0.60]` | `照片有褪色或者小破损，已经按原样保留，没有修` |
| 退化人脸检测路径启用（§4.2） | `本地没启用人脸检测，人脸判断是估算的` |
| `sharpness ∈ [SHARP_FLOOR, 5.0)` | `照片有点糊，人物特征可能不够准` |
文案约束：第二人称、平实、不煽情（`pages/P00-设计基准与路由.md` §9），且**不得出现"修复""变清晰"这类承诺**（`docs/prd/README.md` §0.1）。
### 6.3 错误码映射
码与 HTTP 状态、用户可见文案的唯一事实源是 `spec/03-接口契约.md` §5，本节只记触发条件、不复述。

| 错误码 | 触发条件 |
|---|---|
| `UNAUTHENTICATED` | 未登录 |
| `NOT_FOUND` | `:id` 不存在 / 属他人 / `deleted_at` 非空 |
| `INVALID_PARAM` | `:id` 非整数；`kind != 'original'`（含 `generated` 与 `preprocessed`） |
| `INVALID_FILE_TYPE` | `sharp` 解不开文件（无法识别的格式 / 解码器打不开）——判据与上传侧共用同一张失败分类表：`modules/M01-照片资产与存储.md` §6.4（本文件不复述） |
| `STORAGE_ERROR` | 读原文件失败 / 写归一化结果失败（磁盘满、文件丢失）/ 其它 `sharp` 失败（磁盘、内存） |
| `INTERNAL` | 未预期异常（**不透传原始 message**） |

**不在此处使用**的码：`ANCHOR_LOW_QUALITY`（`422`，提取阶段的拒绝信号，由 `modules/M03-身份锚点提取.md` 抛）、`FILE_TOO_LARGE`（上传阶段 `POST /api/photos`）、`CONTENT_REJECTED`（审核）。本模块不得抛这三个码。

## 7. 配置与环境变量
本模块**不引入任何新环境变量**，也不把评分常数做成环境变量（它们是产品判定标准，不允许按环境漂移，否则 `API-02` 与人工验收无法复现）。全部评分常数（`SHARP_FLOOR`、`SHARP_CEIL`、`HF_REFERENCE`、`CENTER_FACE_FLOOR`、`FALLBACK_FACE_SIZE_SCORE`、权重、阈值）以 `const` 定义在 `src/server/images/quality.ts`；本模块会读到的已有变量（`spec/04-技术基线与目录结构.md` §4.5、`spec/08-本地开发指南.md` §4）；`MAX_UPLOAD_MB` **不在本模块读取**（它只约束 `POST /api/photos`）：

| 变量 | 本模块用途 |
|---|---|
| `DATABASE_PATH` | 经 `getDb()` 间接使用，本模块不直接读 |
| `STORAGE_DIR` | 经 `getStorage()` 读原文件、写归一化结果，本模块不直接读 |

本模块**没有专属的 B 层检查项**——`spec/07-验收标准.md` §2 未给预处理单列 ID，其正确性通过下列检查项的前置条件体现：`E2E-04` 是**直接前置**（`generations.reference_photo_ids` 里那恰好 1 个 id 的 `photos.kind` 必须为 `'preprocessed'`，这一行**只能**由 `POST /api/photos/:id/preprocess` 产生，`spec/03-接口契约.md` §3.5）；`E2E-01` 第 2 步即 `preprocess`；`API-02` 用 `src/shared/types.ts` 的 `Quality` zod schema 校验本端点响应（`PRE-12` 是单元级护栏）；`API-03` / `API-04` 对应 §6.3 的 `UNAUTHENTICATED` / `NOT_FOUND`；`SEC-06` 的"生成图不得再作输入"在预处理侧即 §3.1 的 kind 校验；`E2E-07` 依赖 §5.1 步⑥的"同输入同输出字节"（`PRE-06`）。`E2E-04` 的完整前置链：`pnpm migrate && pnpm seed` → 登录 → 上传（`docs/老照片/1b26e45303c7321fa589d4525b43aa0.jpg`）→ 本端点产出 `kind='preprocessed'` 行 → 建锚点 → 确认 → 生成；任何一步失败，`E2E-04` 都无法判定。
## 9. 非目标与待定决策
### 9.1 非目标（本期）
任何形态的图像增强 provider（见 §1.3，`spec/00-总纲.md` §6.2 已列）；跨图排序（服务端不做，前端可对每张原图各调一次本端点再比 `readability`）；多张原图融合成一张预处理图（`identity_anchors.input_photo_ids` 支持多个 id，但 `preprocessed_photo_id` 只有一个，`spec/01-领域模型与数据库.md` §3.5，融合留待 F3）；损坏检测与定位（§4.1 只做全局统计）；图像方向以外的几何校正（透视纠正、倾斜拉直，属"修复"范畴）；结果缓存与 CDN（本地单机）。
### 9.2 待定决策（必须由 `tickets/T04-预处理与质量评分.md` 在 `## Comments` 补齐）
1. **人脸检测选型**：`@vladmandic/face-api` / `onnxruntime-node` / 中心高频能量退化（§4.2）。不引入新依赖会导致 `faceCount` 恒为 0 或 1（多人照无法识别）。
2. **评分常数标定**：§4.1 与 §6.1 的数字是**量级合理的估计值，尚未实测**；标定样本 = `docs/老照片/*.jpg` 2 张 + `fixtures/images/*` 3 张 + 4 个程序构造样本（全黑、纯模糊、高对比、极小）。
3. **`sharp.stats().sharpness` 可用性**：需在实现时确认本机 sharp 版本返回该字段；不返回则退回 `convolve({ width: 3, height: 3, kernel: [0,1,0, 1,-4,1, 0,1,0] })` 后取 `stats().channels[0].stdev`，语义等价。
4. **`chromaSubsampling: '4:4:4'` 的体积代价**：需比对与 `2x2` 的实际文件大小差异；若超过 `MAX_UPLOAD_MB` 的 1/4，重新评估该常数。
5. **并发单飞表的生命周期**：`Map` 何时清理（完成后立即 `delete` vs 进程内常驻）。单进程本地环境两种都可，需选定一种写进代码并在测试里断言。
6. ~~**`AnalysisInput` 的字段与评分伪代码里的未定义符号**（`stats()` / `st` / `L` / `hi` / `lo`）~~ **已收口**：`AnalysisInput` 已显式声明 `gray1024` / `stats` / `histogram` / `width` / `height` / `faceBox` 六个字段并写明各自由谁计算（§4.1），伪代码改引 `a.stats` 与在片内就地定义的本地量（`L` / `sd` / `hi` / `lo`），不再有未定义符号；这是命名与签名修复，公式含义、阈值与标定常数一字未动（`spec/09-施工纪律.md` D5）。
