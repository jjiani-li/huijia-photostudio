# 09 · 施工纪律

> **层级**：规范层 · 全局约束（不可违背）
> **上游**：`spec/00-总纲.md` §3、§7 ／ `README.md` §3
> **下游**：全部 `tickets/T*.md`、全部下游文档

本文件规定"动代码之前必须知道什么、不能做什么、遇到歧义怎么办"。**违反本文件的改动一律返工。**

---

## 1. 权威性顺序

出现冲突时，以下列顺序为准，**上位否定下位**：

1. `spec/00-总纲.md` §4 真实感定义（最高优先级，任何功能与之冲突都以它为准）
2. `spec/` 其余文档（数据模型、接口契约、Prompt 工程、合规、验收）
3. `modules/` 后端实现规格、`pages/` 前端实现规格
4. 当前 `tickets/T*.md` 工单
5. `docs/raw/AIGC_PRD.md`（**仅为输入材料**，与本目录冲突一律以本目录为准）

代码与文档冲突时，**改代码，不改文档**——除非先在 `spec/` 里改好文档再改代码。

## 2. 开工前必读（按顺序）

1. `README.md`（索引与硬约束速查）

## 3. 取票规则

- 按 `tickets/README.md` §1 依赖图的顺序取票，**一次只做一条**，做完再做下一条。
- 一条 ticket 的「完成判定」全部通过之前，不得开始下一条。
- 不得跨 ticket 顺手重构：看到别处的坏代码，记进当前 ticket 的 `## Comments`，不要动它。

## 4. 禁令（硬约束）

| # | 禁止 | 违反后果 |
|---|---|---|
| D1 | **自创表、字段、索引、端点、错误码、检查项 ID** | 冻结的契约失效，前后端无法并行 |
| D2 | **在业务代码里内联 prompt 字符串** | prompt 必须由 `spec/05-Prompt工程.md` 的模板 + `eras` / `scenes` / `era_scene_profiles` 数据拼装 |
| D3 | **引入 `negative_prompt` 或 `guidance_scale`** | Seedream lite 不支持，调用必失败（`README.md` §4.1） |
| D4 | **在业务代码里写"禁止项"的负向措辞** | lite 无负向通道，一切约束必须**正向改写**（`spec/05-Prompt工程.md` §3） |
| D5 | **改动数字阈值与标定常数** | `size` 下限 3,686,400、相似度 0.55、年龄偏差 5 岁等，改动等于改验收标准 |
| D6 | **绕过或跳过验收检查**（删检查项、改期望值、`skip`） | `pnpm check:acceptance` 是"完成"的唯一自动化判据 |
| D7 | **把真实感相关的行为做成开关或降级路径** | 「宁可丑一点、旧一点、有点糊，也绝不允许完美」 |
| D8 | **引入本契约未列明的依赖** | 见 `spec/04-技术基线与目录结构.md` §2；不用 ORM、不用 Redis/BullMQ、不用 axios |
| D9 | **改动 `spec/` 内章节的编号与顺序** | 全部交叉引用依赖它。确需删节，先改所有引用方 |
| D10 | **裸编号引用文档**（`` `01` ``、`` `14` ``、`` ticket 06 ``） | 一律写完整路径，见 §6 |
| D11 | **使用禁令措辞**：「复活」「重生」「让 ta 回来」 | `spec/06-合规与风控.md` |
| D12 | **把 mock 生成的图当作样片或验收样本** | 样片只能用真实留存图，见 `spec/era-scene-seed.json` 的 `samplePhoto` |

## 5. 遇到文档没写到的地方

1. 选**最小实现**——能通过当前 ticket 的「完成判定」即可，不做通用化设计。
2. 在当前 ticket 文件末尾的 `## Comments` 追加一条记录，格式：

   ```
   - [待定决策] <问题一句话> → 选 <方案>，理由：<一句话>。影响面：<文件/表/端点>
   ```

3. **不要扩散改动面**：不新增配置项、不新增抽象层、不改接口形状。
4. 若该问题**阻塞**当前 ticket 的完成判定（例如缺一个字段就写不出端点），则停下，把问题写进 `## Comments` 并在回复里明确指出阻塞点——**不要自己发明字段绕过**。

---

## 6. 引用与文件规范

1. 文档间引用写**相对 `docs/prd/` 的完整路径**，例如 `spec/03-接口契约.md` §3.5、`modules/M05-年代场景配置与Prompt拼装.md` §5.2、`tickets/T08-年代场景配置与Prompt拼装.md`。改完文档先跑 `pnpm check:docs`（`spec/08-本地开发指南.md` §3.3），破损引用与索引漂移由它拦下。
2. 引用 `docs/prd/` 之外的文件写仓库根相对路径，例如 `docs/老照片/`、`.scratch/anchor.json`。
3. 每份 `spec/`、`modules/`、`pages/` 文档保留标题下方的 3 行元信息块（层级 / 上游 / 下游），改动内容时同步更新。
4. ticket 编号与文档编号是两套编号：`tickets/T06` 是工单，`modules/M03` 是模块文档，不可混用。

---

## 7. 完成判定怎么跑

```bash
pnpm test                 # A 层：单元测试
pnpm check:acceptance     # B 层：契约与链路检查（PROVIDER=mock，必须全绿）
pnpm check:blind          # C 层：人工质量验收材料（产出 sheet.html / report.md，不需实时跑）
pnpm typecheck            # 类型检查
```

- 当前 ticket 的「完成判定」章节列出的命令**必须逐条实际执行**，不能只做静态检查。
- `pnpm check:acceptance` 的红灯**不允许**用改期望值、删检查项、`skip` 的方式压掉（见 §4 D6）。
- `PROVIDER=real` 路径**不纳入自动检查**，只在人工冒烟时跑（`spec/08-本地开发指南.md` §5）。

---

## 8. 提交前自查

1. 当前 ticket 的「完成判定」全部命令实跑通过。
2. `pnpm typecheck` 无错误。
3. 本 ticket 涉及的所有检查项 ID（见 `spec/07-验收标准.md` §2）都能在输出里看到通过记录。
4. 未新增表/字段/端点/错误码/ID；如确有必要，已在 `## Comments` 说明并更新对应 `spec/` 文档。
5. 未改动任何数字阈值。
6. 交付物里没有 `docs/prd/` 之外的临时文件（`.scratch/` 下的可以保留）。
