## 1. 技术基线

**进程模型**：**单仓、两个进程** —— `pnpm dev`（Next.js 前端 + Route Handlers 后端）与 `pnpm worker`（异步任务），缺一不可（安装、启动与 `.env` 实操见 `spec/08-本地开发指南.md` §2–§4）。

| 项 | 选择 |
|---|---|
| 运行时 / 框架 | Node.js ≥ 20.11、TypeScript strict ／ Next.js 15 App Router（Route Handlers 作后端，React 作前端） |
| 数据库 / 校验 | SQLite + `better-sqlite3`（同步 API）、手写 SQL，无 ORM ／ `zod`（请求解析 + 响应断言 + fixture 校验） |
| 图像处理 / 测试 / 样式 | `sharp`（预处理、质量评分、缩略图）／ `vitest` ／ Tailwind CSS |

**不使用**：Prisma / Drizzle（避免 schema 双源）、Redis / BullMQ（SQLite 表即队列）、axios（用内置 `fetch`）。

## 3. 模块边界与依赖方向

```
app/api/**/route.ts        只做：鉴权 → zod 解析 → 调 service → 封装响应
        ▼
domain/*Service            编排与规则；唯一允许跨 repository 的地方；下一层 security/ · auth/ · prompt/ · ark/ · images/
        ▼  只允许向下调用 repository
db/repositories/*  ←→  db/connection ／ storage/local
```

### 3.1 依赖方向铁律

1. **`app/api/**` 不允许直接调用 repository**，必须经过 `domain/*Service`（简单查询除外：`/api/me`、`/api/history`、`/api/photos`、`/api/config/era-scene`、`/api/health` 可直接调 repository）；
2. **repository 层不允许调用 `ark/`、`images/`、`storage/`**，它只做 SQL；
3. **`prompt/build.ts` 不允许访问数据库**，它接收已查好的 `era` / `scene` / `profile` 对象；
4. **`shared/types.ts` 不允许 import 任何 `server/` 下的东西**（它会被前端打包）；
5. `jobs/handlers/*` 可以调用 `domain/*Service` 与 repository，但不允许调用 `app/api`。

## 4. 跨模块约定

### 4.1 错误处理

`src/server/domain/errors.ts` 定义唯一错误类型，并持有 `code → HTTP 状态码` 的映射；`code → 用户可见中文文案` 的**唯一代码侧镜像**是 `src/shared/error-message.ts` 的 `ERROR_MESSAGE`（前后端共用这一份，服务端只是把它转出来，避免同一张表出现两个版本）。`code` 见 `spec/03-接口契约.md` §5：

```ts
export class AppError extends Error {
  constructor(public code: ErrorCode, message: string, public status: number, public details?: unknown) {
    super(message);
  }
}
```

- Route handler 不得自行组装错误 JSON，**一律 `throw new AppError(...)`**，由 `http/respond.ts` 的 `withErrorHandling()` 包装器转换；
- `withErrorHandling()` 捕获顺序：`AppError` → 按 `status` 返回；`ZodError` → `INVALID_PARAM`；其他 → 记日志并返回 `INTERNAL`（**不把原始 message 透给用户**）；
- worker handler 不得抛 `AppError` 出去，必须捕获并写入任务的 `error_code` / `error_message`。

### 4.2 时间

- 唯一入口 `src/server/domain/time.ts`：`nowIso(): string` 返回 UTC ISO-8601（毫秒精度，`Z` 结尾）；禁止在业务代码里用其他方式生成时间字符串，禁止本地时区格式；"今天"（额度日）用 UTC 日期：`dayKey(): string` → `YYYY-MM-DD`。

### 4.3 数据库

- **进程模型提醒**：`pnpm dev` 与 `pnpm worker` 是**两个进程，共享同一个 SQLite 文件**（§1），两边写入同一个库，因此必须有 busy 处理（见下）。
- `getDb()` 返回单例 `Database`，在**事务之外**执行连接级 PRAGMA：`journal_mode=WAL`、`foreign_keys=OFF`（软删除语义靠应用层，见 `spec/01-领域模型与数据库.md` §2.3）、`synchronous=NORMAL`、`busy_timeout=5000`（`better-sqlite3` 的 `timeout` 选项，等价）。
  **这些 PRAGMA 不得写进 `migrations/*.sql`**：SQLite 禁止在事务内切换 `journal_mode`，而 `migrate.ts` 对每个迁移文件单事务执行，写在迁移里会直接报错或静默失效（`spec/01-领域模型与数据库.md` §5.1）。
- **所有写操作必须包在事务里**（`db.transaction(...)`），跨表写（如"建锚点 + 写审计"）必须在同一事务；涉及"读判 → 写"的排他性事务（如生成入队的非终态检查）一律用 `db.transaction(...).immediate()`（`BEGIN IMMEDIATE`），不用 `.exclusive()`；
- SQLite 返回 `SQLITE_BUSY` / `SQLITE_BUSY_SNAPSHOT` 时按可重试的 `STORAGE_ERROR` 处理（映射见 `spec/03-接口契约.md` §5.1）；
- repository 函数签名遵循：接收**原子值或 DTO**，返回**领域对象**（camelCase），永不返回数据库原始行；所有 JSON 列：写入前 `JSON.stringify`，读取后立即 `JSON.parse` 并在 repository 边界用 zod 校验。

### 4.4 响应

```ts
export const ok = <T>(data: T, status = 200) => NextResponse.json(data, { status });
export const withErrorHandling = (handler) => async (req, ctx) => { /* 见 spec/04-技术基线与目录结构.md §4.1 */ };
```

### 4.5 上传与文件

- 文件系统是唯一存储介质；`storage_key` 由 `storage/index.ts` 的 `buildKey(userId, ext)` 生成：`u{userId}/{uuid}.{ext}`；
- 任何直接拼 `path.join` 的地方都要经过 `LocalStorageProvider`，禁止业务代码散落路径逻辑；
- 写文件用"先写 `.tmp` 再 rename"的原子方式。

### 4.6 异步任务（worker 契约的唯一事实源）

> **本节是 worker 契约的唯一事实源**：任务来源、拉取顺序、claim 原子性、handler 结构、心跳、启动自检、回收、超时与自动重试只在这里定义。`spec/03-接口契约.md` §2、`modules/M06-生成编排.md`、`modules/M08-账号历史与彻底删除.md`、`modules/M09-图片反推提示词.md` 一律引用本节，不复述。

**任务来源（三张表）**：`identity_anchors(status='queued')`、`prompt_reverse_jobs(status='queued')` 与 `generations(status='queued')`，与 `spec/03-接口契约.md` §2 的三类异步操作一一对应。**拉取（轮转，不许固定顺序）**：worker 维护一个游标，**每次迭代只取一行**——`SELECT id FROM <当前表> WHERE status = 'queued' ORDER BY created_at LIMIT 1`——取完把游标推进到下一张表；取不到行（该表队列空）也推进到下一张表。三张表按 `identity_anchors` → `prompt_reverse_jobs` → `generations` 循环，**任何一张都不会被另一张的长队列饿死**：这是公平性契约，固定顺序（每次迭代都从第一张开始）会让排在最后的表永远排不上。游标是主循环里的内存变量，进程重启回到 `identity_anchors` 重新开始（无状态恢复，不影响公平性）。`WORKER_CONCURRENCY`（默认 1）是**同时执行的 handler 数上限**，默认 1 即完全串行；本期不考虑高并发，正确性优先。worker 与 web 是**两个进程共享同一个 SQLite 文件**（§1、§4.3）。

**claim 原子性**——不依赖内存状态，三张表同一写法：

```sql
UPDATE <表> SET status = 'running', started_at = :startedAt WHERE id = :id AND status = 'queued';
```

靠 `changes` 判断：`const { changes } = db.prepare(CLAIM_SQL).run({ id, startedAt: nowIso() }); if (changes !== 1) return;`——没抢到（已被处理或状态已变）直接放弃本轮。`attempt` **不在 claim 阶段自增**，只由自动重试自增。

**主循环每轮三件事**：回收（仅进程启动后第一轮）、拉取、执行；无可领取任务时等待 ≤ 1 秒再进入下一轮。**handler 结构固定**：`claim → 置 running → 执行 → 写结果 → 置终态`；handler 内部必须捕获全部异常（**不得把 `AppError` 抛给主循环**），任何失败都要落到终态——写 `failed`，或按下文规则重新入队。

**心跳**：worker 启动即 `setInterval(5_000)`，把 `nowIso()` 写入 `.<DATA_DIR>/worker-heartbeat`（`<DATA_DIR>` = `dirname(DATABASE_PATH)`，默认 `./data`）；等待任务时不阻塞该定时器。`GET /api/health` 读其 mtime，超过 **15 秒**未更新即 `worker.alive=false`（`ERR-04`），前端据此提示"后台还没启动，图片处理会卡住"并给出命令 `pnpm worker`。

**启动自检（`dev` 侧）**：在**启动时**与**每次入队前**读同一心跳文件、同一 15 秒阈值，超过即**明确报错**，**禁止把"任务不执行"变成静默行为**（`spec/08-本地开发指南.md` §3.1）：

```
[FATAL] worker 未启动：找不到心跳文件 ./data/worker-heartbeat
        异步任务不会被执行，锚点提取与生图会一直停在 queued
```

**启动时回收**（进程启动后执行一次，三张任务表各一条）：把 `status='running'` 且 `started_at` 早于 `nowIso() − WORKER_STALE_MINUTES`（默认 10 分钟）的行置回 `queued`、`started_at = NULL`；`attempt` **保持不变**、`error_code` 不写（`ERR-02`）。

**超时**：handler 用 `AbortController` 包裹，超过 `JOB_TIMEOUT_SECONDS`（默认 120 秒）即中止，按 `PROVIDER_TIMEOUT` 处理（可重试）；上游单次调用的超时另由 `ARK_TIMEOUT_SECONDS` 控制（`modules/M06-生成编排.md` §9）。

**自动重试**：执行失败、**本次零产出**、错误码属于瞬时集合 `['PROVIDER_TIMEOUT', 'PROVIDER_ERROR', 'STORAGE_ERROR']`、且 `attempt < 1` → 置回 `queued` 并 `attempt = attempt + 1`（`error_code` / `error_message` 一并写库）；否则直接写终态 `failed`。**错误码的逐条可重试性以 `modules/M06-生成编排.md` §5.8 的 `可重试` 列为准**：同一错误码在不同上游情形下可重试性不同时，以该列为准（例如 `ModelNotOpen` 虽落 `PROVIDER_ERROR`，但该列标 ❌，即不重试）；两者不一致时按该列收窄，不因错误码在集合内就重试。`attempt ≥ 1` 后不再自动重试，交由用户走新建行重试（`spec/03-接口契约.md` §1.5）。规则对三张任务表一致；`SQLITE_BUSY` / `SQLITE_BUSY_SNAPSHOT` 已映射为 `STORAGE_ERROR`（`spec/03-接口契约.md` §5.1），因此本就在瞬时集合内，按可重试处理。

**与任务表无关的维护任务**：主循环可在当前没有 `running` 任务时按间隔执行（如 `modules/M08-账号历史与彻底删除.md` §5.3 的 purge）；这类任务**不进入任何任务表**、不新增任务类型，异常必须被捕获并记日志，绝不中断主循环。
