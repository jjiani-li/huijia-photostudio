# 08 · 本地开发指南

> **层级**：规范层 · 全局约束（不可违背）
> **上游**：`spec/04-技术基线与目录结构.md` §4.6 ／ `spec/03-接口契约.md` §2 ／ `docs/火山引擎接口文档.md`
> **下游**：`tickets/T01`、`tickets/T05`、`tickets/T20`，以及各 `modules/` 与 `pages/` 文档的本地跑通步骤

> 目标：**本地零外部依赖跑通全链路**；真实 Ark 调用是可切换的增强路径，不是前置条件。

## 1. 环境要求

| 项 | 要求 |
|---|---|
| Node.js | ≥ 20.11（`better-sqlite3` 与 Next.js 15 需要）；包管理器 pnpm ≥ 9 |
| 操作系统 | Windows / macOS / Linux（开发主力为 Windows） |
| 外部服务 | **无**。SQLite 是文件库，存储是本地目录，Ark / 短信 / 实名核验都有本地实现 |

## 2. 一次性初始化

```bash
pnpm install
cp .env.example .env      # Windows: copy .env.example .env
pnpm migrate              # 建库 + 建表（执行 migrations/*.sql）
pnpm seed                 # 写入 4 个年代 / 5 个场景 / 20 组组合档案；结束断言 eras=4, scenes=5, era_scene_profiles=20，不符则非零退出
```

## 3. 日常开发

**单仓、两个进程，缺一不可**——开两个终端：

```bash
pnpm dev        # 终端 A：前端 + 后端（Next.js dev server，默认 http://localhost:3000）
pnpm worker     # 终端 B：异步任务 worker（另一个终端，缺一不可）
pnpm test       # 单元测试（vitest）
pnpm test:watch # 单元测试（watch 模式）
pnpm check      # 类型检查 + lint
pnpm build      # 生产构建（本地一般不用；start 起构建产物）
pnpm check:docs # 文档一致性闸门（注册表与 docs/prd/ 文档树自洽，见 §3.3）
pnpm test:docs  # 闸门自身的回归网（夹具文档树，node --test）
```

**为什么缺一不可**：锚点提取与生图都只入队（`identity_anchors` / `generations` 的 `queued` 行），由 `pnpm worker` 执行；没有 worker 时任务永远停在 `queued`（`spec/04-技术基线与目录结构.md` §4.6）。

### 3.1 启动自检（worker 心跳）

worker 每 5 秒把当前时间写进心跳文件 `.<DATA_DIR>/worker-heartbeat`（`<DATA_DIR>` = `dirname(DATABASE_PATH)`，默认 `./data`）。`dev` 侧在**启动时**与**每次入队前**读该文件 mtime，超过 15 秒未更新即判定 worker 未存活并**明确报错**——不允许把"任务不执行"变成静默行为：

```
[FATAL] worker 未启动：找不到心跳文件 ./data/worker-heartbeat
        异步任务不会被执行，锚点提取与生图会一直停在 queued
```

排查：① 另开终端跑 `pnpm worker`，等 5 秒（首个心跳随后写入）；② 两个终端必须用**同一份 `.env`**（`DATABASE_PATH` 不同 → 心跳路径不同，自检必报错）；③ 看 worker 终端启动日志（`better-sqlite3` 未编译 / 依赖缺失 / 端口占用）；④ `pnpm db:reset` 后重跑 `pnpm migrate && pnpm seed`；⑤ `GET /api/health` 的 `worker.alive=false` 即心跳仍缺失（`spec/03-接口契约.md` §2.3）。前端另有温和提示"后台还没启动，图片处理会卡住"与命令 `pnpm worker`（同上）。

### 3.2 M1/M2 期间的"当前用户"

M1/M2 没有真实登录流程：`tickets/T02` 的种子数据植入固定 `DEV_USER`（**已实名，`verified_at` 非空**），它即当前会话用户，使 `tickets/T03`–`tickets/T11` 能直接跑通。真实登录与实名门槛在 `tickets/T12-账号、会话与额度.md`、`tickets/T19-实名、用户资料与生成门槛.md` 落地后接管（`spec/00-总纲.md` §6.3）。

### 3.3 文档一致性闸门（`pnpm check:docs`）

改完 `docs/prd/` 的任何一份文档后先跑它：

```bash
pnpm check:docs                    # 只读文档树；不需要 .env、数据库、worker 或 ARK_API_KEY
pnpm check:docs -- --write-index   # 额外按各工单表头重写 tickets/README.md 的检查项列
pnpm test:docs                     # 闸门自身的回归网：每条断言一份夹具文档树（node --test）
```

检查项 ID 的机器可读副本是 `spec/check-registry.json`（每条 `{ id, layer, owner, path, assertedBy, tickets[] }`；**ID 的权威定义仍在 `spec/07-验收标准.md` §2**）。脚本 `scripts/check-docs.mjs` 断言十三条，失败时逐条打印 `[断言] 文件:行 — 原因` 并以退出码 1 结束：

| 断言 | 拦下的问题 |
|---|---|
| `ids-unique` | 同一个检查项 ID 被注册两次（一号两义） |
| `single-owner` | 一个 ID 有两个归属或两条工单同时认领（双 owner） |
| `no-orphan` | 注册表里有 ID 没有任何工单表头认领 |
| `declared-ids-exist` | 文档里引用了未注册的 ID，或引用了已退役的 ID |
| `single-new` | 同一份文件被两条工单同时声明「新建」；声明路径不是完整仓库相对路径；「新建/修改」未二选一 |
| `refs-resolve` | 引用了不存在的文档、章节，或注册表的 `owner` 指向不存在的文档 |
| `index-matches-headers` | `tickets/README.md` 的检查项列与各工单表头不一致（索引是派生物，不手工维护） |
| `counts-match-registry` | 文档里写出的检查项计数与注册表派生值不一致 |
| `error-single-source` | 模块或页面文档里又出现一张错误码表（首列是错误码却带「HTTP / 状态」列或「文案」列），或某个单元格写成「状态码 + 错误码」（`401 UNAUTHENTICATED`）——错误码只在 `spec/03-接口契约.md` §5 定义 |
| `threshold-single-source` | 除 `spec/07-验收标准.md` 的 `PR-07` 之外又写了一遍 prompt 长度区间 |
| `task-source-single-count` | 任务来源被写成三张表之外的张数（「与上游文档的差异」章节里的引述不算） |
| `retired-terms` | 裸写了已退役的旧词（退役词表在 `CONTEXT.md` 的 `_Avoid_` 行与 `scripts/check-docs.mjs` 的 `RETIRED_TERMS`：术语别名、`suggestSceneId` 的旧措辞、`anchor_text` 的旧区间），或两个判定（`eraCheckVerdict` / `moderationVerdict`）在定义处与归属模块里没有被分别点名 |
| `unverified-caps` | 未验证的上游能力没有集中登记在 `spec/07-验收标准.md` §6（登记表缺行、或某行漏了「未验证」标记），或别的文档里又在本地重复一句「某能力还没取证」这类一次性对冲（具体措辞表见 `scripts/check-docs.mjs` 的 `HEDGE_RE`） |

**它不查什么**：指向 `docs/raw/`、`docs/火山引擎接口文档.md` 等上游输入文件的引用（编号不归本仓库管）；`§N.M` 也可能表示「第 N 节第 M 条」，那种写法无法静态判定，只在第 N 节确实有 `### N.x` 编号子节时才校验；代码路径（`src/**`、`app/**`、`fixtures/**`）由产品工单声明、本期尚未实现，因此只查声明唯一，不查存在；`unverified-caps` 的扫描范围是 `docs/prd/`（上游输入文件里的 ✅ 标注不归它管），且整份 `spec/07-验收标准.md` 是它的豁免区（登记块就在那里，措辞表见 `scripts/check-docs.mjs` 的 `HEDGE_RE`）；其余单点化断言按**已知写法**判定——错误码表看「首列是反引号包的错误码」与「单元格等于状态码 + 码」，阈值看几个固定字面写法，张数看「任务来源 / 任务表」所在行（并跳过「与上游文档的差异」章节里的上游引述）——换一种写法能绕过，但改契约的写法本身就是改契约。

## 5. 本地替身（mock）策略

**验收有两条路径，只有 `mock` 那条是自动判据**——**没有 `ARK_API_KEY` 时不要改任何开关，第一步就是跑 `PROVIDER=mock pnpm check:acceptance`**（`pnpm dev` / `pnpm smoke` 同样默认 mock；见 `spec/07-验收标准.md` §1、`spec/09-施工纪律.md` §7）：

| 路径 | 开关 | 命令 | 判定方式 |
|---|---|---|---|
| **mock（权威）** | `PROVIDER=mock`（默认） | `pnpm check:acceptance` | **必须全绿**；离线、可复现、无 `ARK_API_KEY` 也能跑，这是"完成"的唯一自动化判据 |
| **real（手动冒烟）** | `PROVIDER=real` + `ARK_API_KEY` | `PROVIDER=real pnpm smoke -- --real` | 产出与截图**人工确认**，消耗真实额度，**不纳入自动检查** |

四个外部依赖都有本地实现，**默认全部走本地实现**：

| 依赖 | 抽象 | 本地实现 | 真实实现 | 切换 |
|---|---|---|---|---|
| Ark 模型（读图/生文/生图） | `ArkProvider` | `MockArkProvider`：回放 `fixtures/ark/*.json` + `fixtures/images/*` | `RealArkProvider`：直连 `chat/completions` 与 `images/generations` | `PROVIDER` |
| 短信验证码 | `SmsSender` | `ConsoleSmsSender`：打到终端，且在响应里返回 `devCode` | （本期不实现） | `SMS_PROVIDER` |
| 实名核验 | `IdVerifyProvider` | 格式校验 + 唯一性校验（`id_hash` 只存哈希，不存明文） | （生产留空位） | `ID_VERIFY_PROVIDER` |
| 图片存储 | `StorageProvider` | `LocalStorageProvider`：`./storage/` | （本期不实现） | 无开关，仅一个实现 |

### 5.1 Fixtures 目录

基底 = 两份**真实留存**的上游报文，mock 的返回形态必须与之一致，不得自造形状：`.scratch/api_image_response.json`（生图真实返回，含 `data[].url` 签名链 —— 86400s 过期、`data[].size`）与 `.scratch/api_chat_response.json`（对话/读图真实返回，含 `choices[0].message.content` 与 `reasoning_content`）。

```
fixtures/
├── ark/anchor-extract.json        ← 锚点提取响应（形状同 /api/anchors/:id 的 anchor）
├── ark/anchor-extract-fail.json   ← 触发 ANCHOR_LOW_QUALITY 的样本
├── ark/image-generation.json      ← 生图响应（url 指向 fixtures/images/）
├── ark/invalid-size.json          ← 回放 InvalidParameter：size 低于下限 3,686,400（→ INTERNAL，ERR-03）
├── ark/model-not-open.json        ← 回放 ModelNotOpen（→ PROVIDER_ERROR，不可重试）
├── ark/timeout.json               ← 回放超时（→ PROVIDER_TIMEOUT，可自动重试 1 次，ERR-01）
├── ark/era-check.json             ← 穿帮复核结果（含一个穿帮样本）
├── ark/safety-review.json         ← 内容审核结果
└── images/generated-01.png … generated-03.png  ← 从 docs/output/ 的真实样片复制，见 §7
```

mock 必须覆盖的真实形态至少四项：**签名 URL 转存**（下载失败映射 `STORAGE_ERROR`）、`InvalidParameter`（尺寸低于下限 3,686,400）、`ModelNotOpen`、**超时**。

`MockArkProvider` 的行为规则：

- 读图类调用：返回 `anchor-extract.json`，但把 `features.ageRange` 与 `anchorText` 中的年龄替换为**可从文件名推断的稳定伪随机值**（同一输入文件永远得到同一输出，保证测试可重复）；
- 生图类调用：按 `(anchorId + eraCode + sceneId + ordinal)` 的哈希在 `fixtures/images/` 中**确定性选图**，写入本地存储后返回本地 URL；
- 每次调用固定 `sleep 300–800ms`，模拟异步感，避免前端轮询逻辑在 mock 下从未被真正测过；
- 传入 `fixtures` 中不存在的场景时抛 `PROVIDER_ERROR`，便于测试失败路径；失败分支（`invalid-size` / `model-not-open` / `timeout`）由用例显式指定回放目标后生效，供 `ERR-01` / `ERR-03` 与重试路径使用（上游错误 → 本项目错误码的映射见 `modules/M06-生成编排.md` §5.8）。

### 5.2 切换到真实调用

```bash
# .env: PROVIDER=real、ARK_API_KEY=<你的 key>
pnpm dev
pnpm worker
```

真实调用走**直连 HTTP + 模型名**（`docs/火山引擎接口文档.md` §2.3 / §1 已验证可用）。**不要**改造成 arkcli 或 `ep-...` Endpoint 方式——那条路只在 arkcli 的 platform profile 下必需，直连 HTTP 不需要（`modules/M06-生成编排.md` §5.8 映射表第 3 行）。`GET /api/health` 的 `provider.mode` 会反映当前模式，前端在标题栏以一行小字显示（便于避免误用真实额度）。

## 7. 用仓库里的真实素材验证

素材只有两个来源，**样片只能是 `spec/era-scene-seed.json` 中 `samplePhoto` 非 null 的项**：

| 来源 | 文件 | 用途 |
|---|---|---|
| `docs/老照片/` | `1b26e45303c7321fa589d4525b43aa0.jpg`、`907e482a190c6fd14e7c648d6ba8819.jpg` | 输入素材（上传 → 锚点 → 生成），兼评分常数标定样本。**这是仓库里唯一的真实留存照片** |
| `docs/output/` | 7 张 PNG（`era-scene-*`、`pipeline-*`、`arkcli-*`、`seedream-lite-*`） | **均不可作样片**（见下） |

**为什么 `docs/output/` 一张都不能当样片**：目录下 7 张图实测全部是 **2048×2048**，恰等于各年代的 `defaultSize`，且命名与生成链路一致（`era-scene-E2-S1-old-studio.png`、`pipeline-1990s-studio-portrait.png`）——它们是**本项目自身用 Seedream 生成的输出**，不是真实留存的老照片。其中 `arkcli-01/02`、`seedream-lite-01/02` 是模型与 CLI 的能力测试图（笔记本、柴犬）。

因此**本期 `samplePhoto` 全部为 `null`、`public/samples/` 为空**，前端一律按"暂无示例"降级为纯文字卡片（禁止用占位图、模型图或 mock 图凑数——见 `spec/09-施工纪律.md` D12）。将来拿到真实留存照片时，按 seed 的 `samplePhoto` 字段放图即可，不改代码。`tickets/T14-前端基础：设计基调、布局与通用组件.md` 负责该目录的建立与降级呈现（见 §9）。

```bash
pnpm smoke                           # 上传 docs/老照片/ 的样例走完整链路（mock，默认）
PROVIDER=real pnpm smoke -- --real   # 真实调用一次（约 1 张图，人工确认产出与截图）
```

`pnpm smoke` 的实现见 `spec/07-验收标准.md` §2（检查 `E2E-01`）。

## 8. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 任务一直停在 `queued`，或启动即报 `[FATAL] worker 未启动` | worker 没启动，或两终端 `DATABASE_PATH` 不同（心跳路径不同） | 见 §3.1 自检与排查 |
| `pnpm seed` 退出码非零 | 种子文件被改动导致数量不为 4/5/20 | 检查 `spec/era-scene-seed.json` |
| `GET /api/health` 的 `ok=false` | 未执行 migrate/seed | `pnpm migrate && pnpm seed` |
| 上传 heic 报 `INVALID_FILE_TYPE` | `sharp` 未编译 heif 支持 | 本地先用 jpg 验证；heic 支持列为已知限制 |
| `better-sqlite3` 安装失败 | 无当前 Node 版本的预编译产物 | 升级 Node 到 LTS，或本地有 C++ 工具链时从源码编译 |
| 生图报 `InvalidParameter`（size） | `eras.default_size` 低于 3,686,400 像素 | 改回 `2048x2048` |
| 真实模式下图片 URL 下载 403 | 签名 URL 过期（86400s） | 这是 worker 转存失败导致；检查 worker 日志 |
| 生成结果全是同一张图 | mock provider 选图哈希实现有误 | 见 §5.1 确定性选图规则 |
