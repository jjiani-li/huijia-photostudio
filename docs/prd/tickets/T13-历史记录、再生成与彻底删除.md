## 4. 实现要点
1. 级联解析顺序固定：目标 → 受影响锚点 → 受影响 `generations` → 受影响 generated 照片 → 受影响反推任务，全部在**单个 `db.transaction()`** 内；`cascaded` 键名与 `spec/03-接口契约.md` §3.2 / §3.3 完全一致，**不新增键**。
2. `consents` 只写 `revoked_at`（**不删行**）；`identity_anchors` / `generations` / `prompt_reverse_jobs` 物理 DELETE；`generation_results` **随 `generations` 在同一事务内物理 DELETE**（`spec/01-领域模型与数据库.md` §2.3、`modules/M08` §9 第 4 条已收口），`runPurge()` 的孤儿清理只作兜底。
3. 幂等：重复删除返回 `200` 且 `cascaded` 全零——**含已被 `runPurge()` 物理清理的行**（`spec/03-接口契约.md` §1.5、`modules/M08` §9 第 2 条、`modules/M04-身份确认与授权.md` §5.4）；目标行存在但属于其他用户 → `404`（照片 `NOT_FOUND` / 锚点 `ANCHOR_NOT_FOUND`，不返 403）。`cascaded.preprocessed` = 被标记的 `kind='preprocessed'` 行数（`preprocessed` 目标**含其自身**）。
4. `runPurge()`：单行失败只记 `failed` 并保留 `photos` 行（下轮重试），不整批失败；批满 `PURGE_BATCH_SIZE` 立即续批；异常必须捕获、绝不中断 worker。
5. **历史范围**：`GET /api/history` 只覆盖走完的链路（`status='succeeded'` 的锚点）；`GET /api/photos`（`spec/03-接口契约.md` §3.2）补上**没走完流程的照片**（还没提取、提取失败、提取成功但没确认），**独立游标、不与链路分页混用**（`modules/M08-账号历史与彻底删除.md` §3.2 的互补查询）；前端在 `/history` 用同一个 `ConfirmDialog` 与 `DELETE /api/photos/:id` 让它们可见可彻底删除。
