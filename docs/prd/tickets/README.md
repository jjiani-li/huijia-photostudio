## 3. 为什么是这 20 条

拆解粒度遵循一条规则：**一条 ticket 应该是一个 AI 会话能做完、且能被独立验证的工作单元。**

- **按"可验证的交付物"切，不按"技术层"切**。所以"上传"与"预处理"分开（后者有独立的质量评分逻辑与检查项），而不是合成一条"照片处理"。
- **契约类工作单独成条**（`T02` 数据层、`T05` Provider 抽象、`T08` Prompt 引擎）。它们是后面所有工作的地基，一旦返工代价最大。
- **合规拒绝路径不单独成条**，而是分散到对应 ticket 的检查项（`SEC-` / `DEL-` / `CMP-` / `RN-`）。它们是各自功能的边界条件，单独做一条会做成"事后补丁"。
- **实名单独成条**（`T19`），因为它跨 schema + 新 Provider + 生成门槛三处，塞进任何一条都会让它变成隐性依赖。
- **前端按用户旅程切**（上传/确认、选择、结果），不按组件切。
- **`T20` 最后一条是验收工具**，因为它需要所有端点就位才能写。

### 3.1 明确没有单独成条的东西（以及为什么）

| 没单独成条 | 落在哪 |
|---|---|
| 数据库连接池 / ORM 配置 | `T02`（无 ORM，连接就是几行） |
| 内容审核 | `T11`（审核是生成流程的组成部分，不是独立功能） |
| 审计日志 | `T07` + `T12`（跟着各自的动作写） |
| 隐式标识写入 | `T10`（在结果转存那一步，与 `photos` 落库同一事务序列） |
| 缩略图 / 图片流优化 | `T03`（`?w=` 参数是上传模块的一部分） |
| 错误码常量表 | `T01`（一个文件的事） |
| 样片静态资源目录 | `T14`（`public/samples/`，**本期为空**——`spec/era-scene-seed.json` 的 `samplePhoto` 全为 `null`，见 `spec/08-本地开发指南.md` §7） |
| 部署 / CI | 本期不做（`spec/00-总纲.md` §6.2） |

## 4. Ticket 文件格式（强制骨架）

文件名：`T<两位编号>-<标题>.md`，例如 `T06-身份锚点提取.md`。标题内不得出现 `/`、`:` 等文件系统保留字符。**每条 ≤ 65 行。**

````markdown
# T06 · 身份锚点提取

| 项 | 值 |
|---|---|
| 阶段 | M1 |
| 依赖 | `T04`、`T05` |
| 必读文档 | `modules/M03-身份锚点提取.md`、`spec/05-Prompt工程.md` §4 |
| 检查项 | `E2E-02`、`PR-04` |

## 1. 目标
（一句话：做完这条，什么能力从"不存在"变成"可用且可验证"）

## 2. 不做（边界）
（列出本 ticket 不碰的东西，防止范围蔓延）

## 3. 要交付的文件
（表格：路径 | 新建/修改 | 职责 | 依据章节）

## 4. 实现要点
（按实现顺序列步骤；凡上游已给签名/SQL/常数的，直接引用章节号，不复制）

## 5. 完成判定
（可执行：命令 + 期望输出。必须包含 `spec/07-验收标准.md` §5 的通用完成判定与本条「检查项」列出的全部 ID）

## 6. 待定决策
（本 ticket 必须在开发中回填的开放问题）

## Comments
（由实现者在开发过程中填写：实际选型、偏离规格之处、未解决的问题）
````

### 4.1 写作约束

1. **不复制上游内容**：字段表、SQL、TS 签名、阈值一律写"见 `<路径>` §N"。ticket 的职责是**执行指令**，不是规格副本。
2. **完成判定必须可执行**：写具体命令（`pnpm test -- <file>`、`pnpm check:acceptance`）与期望结果，不写"确保功能正常"。
3. **检查项必须点名**：完成判定里要出现本条「检查项」列出的每个 ID，并说明该 ID 由哪一步满足。
4. **引用一律写完整路径**（`spec/09-施工纪律.md` §6）。
