# 「回家照相馆」PRD 拆解索引

> **产品一句话**：用户上传一张（模糊的）旧照片，系统提取人物**面部特征锚点**，再按用户选择的【年代 × 场景】生成该人物在**全新场景**下的真实感照片。
>
> **这不是一个"老照片修复"产品。** 见 §0.1。

| 项 | 值 |
|---|---|
| 文档版本 | v2.0（拆解版） |
| 上游输入 | `docs/raw/AIGC_PRD.md`、`docs/raw/火山引擎接口文档.md` |
| 权威性 | **本目录是唯一权威**。`docs/raw/` 仅为输入材料，其中与本目录冲突的表述一律以本目录为准 |
| 交付目标 | 颗粒度足以让 AI 完成全部编码，本地（SQLite + 单进程 Next.js）即可跑通前后端 |

## 0. 相对 `docs/raw/AIGC_PRD.md` 的修正

### 0.1 F1 的定位被改写

**旧表述（错误）**：F1 = 模糊照片修复与增强（去噪去划痕、分辨率提升、面部细节还原）。

**新表述（权威）**：F1 = **关键特征提取与预处理**。

F1 **不负责**把人脸修得好看、修得清楚、修得完整。F1 的唯一责任是：

1. 把上传的旧照片整理成**模型可稳定读取**的形态（归一化、格式/方向/尺寸统一）；
2. 从中提取出**准确的面部特征锚点**（`anchor_text` + `features_json`），并给出可信度判断；
3. 保证**不能长得像别人**——锚点失真的话，后面整条链路全废。

因此：

- ❌ F1 不承诺"修复效果"，不承诺"变清楚"；
- ❌ F1 不做美颜、不做减龄、不做面部重建；
- ❌ `sharp` 级别的处理只服务于"让视觉模型读得准"，不服务于"让用户看着好看"；
- ✅ F1 的输出是**文本锚点**（主产物）+ 预处理图（辅助产物，用于后续作参考图）。

### 0.2 核心链路被改写

```
上传旧图 → 预处理与质量评分 → 【特征锚点提取】→ 用户确认"这就是他" + 授权勾选
   → 选择【年代 × 场景】→ 拼装 Prompt → 生成新照片 → 生成后复核 → 挑选/下载
```

关键变化：**锚点提取是主链路的第二个环节，而不是"修复完之后的一个附加步骤"**。链路里没有任何一步叫"修复"。

### 0.3 「防 AI 过度美化」被提升为链路级约束

提取锚点时必须显式声明**不要美化、不要减龄**，并写出皱纹深度、老年斑、皮肤松弛的具体位置与程度。这条约束同时存在于三处，缺一不可：

| 位置 | 载体 | 见 |
|---|---|---|
| 锚点提取的 system prompt | `06-后端-身份锚点提取.md` | ticket 06 |
| 生成 prompt 的【年龄保真】段 | `12-Prompt工程规范.md` §2 | ticket 08 |
| 生成后自动年龄偏差检查 | `09-后端-生成后复核与内容审核.md` | ticket 11 |

### 0.4 其余保留不变

`docs/raw/AIGC_PRD.md` 的以下内容被完整继承（并在本目录细化）：§2 绝对真实感（最高优先级）、§5 年代 × 场景匹配矩阵、§5.8 正向化约束、§7 Prompt 工程、§8.1 设计基调。

## 1. 拆解维度

一份"能直接喂给 AI 开工"的 PRD，必须让 AI 在每个 ticket 上都能回答四个问题：**改哪些文件？读写哪些表？调哪些接口？怎么算做完？**

因此按下面 **9 个维度**拆解。每个维度解决一类问题，彼此不重叠：

| # | 维度 | 回答的问题 | 目录/文件 |
|---|---|---|---|
| 1 | **总纲** | 做什么、不做什么、对谁做、什么算成功 | `00-总纲.md` |
| 2 | **领域与数据** | 有哪些实体、什么状态、落到哪张表哪个字段 | `01-领域模型与数据库.md`、`02-schema.sql` |
| 3 | **后端模块** | 每块逻辑的输入输出、边界、错误、状态机 | `03`–`10-后端-*.md` |
| 4 | **Prompt 工程** | 文本资产本身（这是本产品的核心竞争力） | `12-Prompt工程规范.md`、`13-era-scene-seed.json` |
| 5 | **接口契约** | 前后端之间唯一的约定 | `14-接口契约.md` |
| 6 | **前端** | 页面、路由、状态、视觉与文案规范 | `15-前端-设计基准与路由.md`、`16-前端-页面规格.md` |
| 7 | **验收** | 什么算做完、怎么自动验证 | `17-验收标准与自动化检查.md` |
| 8 | **本地开发** | 怎么跑起来、外部依赖怎么替身 | `18-本地开发指南.md` |
| 9 | **合规** | 哪些是法律/伦理硬约束，代码里落在哪 | `19-合规与风控.md` |

前端与后端**分别按维度拆**，而不是按"页面 → 接口"混着拆——因为 AI 可以并行开发前端与后端，只要 `14-接口契约.md` 冻结。

## 3. 给 AI 开发者的使用方式

1. **先读** `README.md` → `00-总纲.md` → `01-领域模型与数据库.md` → `14-接口契约.md`。这四份是全局契约。
2. **按 `tickets/README.md` 的依赖图顺序**取 ticket，一次只做一条。
3. 每条 ticket 的正文会告诉你：读哪些文档、改哪些文件、验收怎么跑。**不要自行发明接口或表**——一律回到 `01` / `14` / `12`。
4. 遇到文档没写到的细节，选择**最小实现**并在该 ticket 文件末尾 `## Comments` 追加一条"待定决策"，不要扩散改动面。

### 4.2 产品红线（来自 §2，最高优先级）

- 必须保留：面部身份特征、真实皮肤纹理（毛孔/细纹/老年斑）、年代感。
- 严禁出现：塑料感、蜡像感、过度磨皮、3D 渲染感、**把老人磨年轻**、与年代不符的现代物件。
- 验收口诀：*宁可丑一点、旧一点、有点糊，也绝不允许"完美"。*

### 4.3 工程约束

- 本地**零外部依赖**可跑：SQLite 文件库 + 本地文件存储 + mock provider。
- 真实 Ark 调用必须可切换（`PROVIDER=real`）且是**唯一**的外部网络依赖。
- 所有时间戳 UTC ISO-8601；所有生图任务参数（prompt/seed/参考图 id/锚点 id/年代/场景）**必须落库**以保证可复现。
