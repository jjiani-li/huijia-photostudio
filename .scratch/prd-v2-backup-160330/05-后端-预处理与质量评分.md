# 05 · 后端 · 预处理与质量评分

> F1 的前半段：把上传的旧照片**整理成模型读得准的形态**，并给出可读性判定——**不修复、不美化、不放大**。

---

## 1. 职责与边界

### 1.1 做什么

| # | 职责 | 产物 |
|---|---|---|
| 1 | 方向校正（按 EXIF Orientation 旋转到正向） | 像素已摆正 |
| 2 | 色彩空间统一到 sRGB | 下游读图/生图配色一致 |
| 3 | 剥离 EXIF / ICC / IPTC / XMP 元数据 | 无隐私残留、无方向歧义 |
| 4 | 尺寸归一：长边目标 1600px，**不足时绝不放大** | 尺寸确定 |
| 5 | 统一输出 `image/jpeg`，质量 92 | 单一路径的编码 |
| 6 | 质量评分 → `quality_json` | `Quality` 对象（8 键） |
| 7 | 落库 `photos(kind='preprocessed')`，`source_photo_id` 指向原图 | 后续作**参考图** |

输出物只有一个用途：作为 `identity_anchors.preprocessed_photo_id`（读图输入）与 `generations.reference_photo_ids`（生图参考图）。见 `14-接口契约.md` §3.2、§3.3、§3.5。

### 1.2 为什么这里没有"修复"

见 `00-总纲.md` §1.3。用户那张旧照片的价值在于**它是这个人的唯一证据**。如果第一步是"用 AI 把照片重画清楚"，后续所有锚点提取与生成锚定的都是一张 **AI 想象的脸**——身份保真从根上断了，`00-总纲.md` §4.4 的"面部相似度 ≥ 0.55"从第一条就无解。

所以本模块做的是**读得像**（让多模态模型与 Seedream 能稳定读取），不是**看着好看**。`README.md` §0.1 的"F1 不承诺修复效果"在这里落地为具体禁令（§1.3）。

### 1.3 明确不做

| 不做 | 理由 |
|---|---|
| 超分 / 分辨率提升 / 放大（含 2x、4x） | 放大 = 用插值或模型**编造**像素；编造的像素会进入锚点与参考图 |
| 去噪 / 去划痕 / 去灰尘 / 去网纹 | 同上：抹掉的细节位置无法还原，属于"画"而非"读" |
| 锐化（`unsharp`/`sharpen`）/ 提高对比度 / 直方图拉伸 | 会改变皱纹、老年斑的可辨识边界，直接与 `00-总纲.md` §4.2 冲突 |
| 美颜 / 磨皮 / 减龄 / 提亮肤色 | `README.md` §0.4 红线 |
| 人脸裁剪 / 人脸对齐 / 换脸预处理 | 会改变脸型比例与构图；构图继承是 `docs/raw/AIGC_PRD.md` §5.7 已记录的坑 |
| 基于 AI 的重绘或"修复 provider" | `00-总纲.md` §6.2 已列为本期不做；扩展位 `EnhanceProvider` 保留 |
| 缩略图 | 走 `GET /api/photos/:id/file?w=`，由存储层按需生成（见 `03-后端-模块总览.md` §2 的 `file/route.ts`） |
| 阻断流程 | `usable=false` 仍返回 `200`，由前端决定是否放行（§6） |
| 隐式标识写入 | `src/server/images/mark.ts` 只对 `kind='generated'` 生效（见 `19-合规与风控.md`） |

## 3. 数据读写

### 3.1 读

| 表 | 字段 | 条件 |
|---|---|---|
| `photos` | `id, user_id, kind, storage_key, mime, bytes, width, height, sha256, deleted_at` | `id = :id AND user_id = :userId AND deleted_at IS NULL` |

`kind` 校验：

- `kind = 'generated'` → `400 INVALID_PARAM`（同一张生成图不得再作输入，`01-领域模型与数据库.md` §3.4 硬约束、`SEC-06`）；
- `kind = 'preprocessed'` → `400 INVALID_PARAM`（本端点只接受 `kind='original'`）。

### 3.2 幂等键查询（本模块的核心 SQL）

```sql
SELECT id, storage_key, mime, bytes, width, height, sha256, quality_json, created_at
FROM photos
WHERE source_photo_id = :sourcePhotoId
  AND kind = 'preprocessed'
  AND deleted_at IS NULL
ORDER BY created_at DESC
LIMIT 1;
```

命中即**直接返回该行**（§5.3）。注意去重键是 `source_photo_id`，**不是** `sha256`——`photos.sha256` 的重用规则只属于 `POST /api/photos`（`14-接口契约.md` §1.5）。

### 3.3 写

```sql
INSERT INTO photos (user_id, kind, storage_key, mime, bytes, width, height,
                    sha256, source_photo_id, quality_json, deleted_at, created_at)
VALUES (:userId, 'preprocessed', :storageKey, 'image/jpeg', :bytes, :width, :height,
        :sha256, :sourcePhotoId, :qualityJson, NULL, :nowIso);
```

| 字段 | 取值规则 |
|---|---|
| `kind` | 固定 `'preprocessed'` |
| `storage_key` | `buildKey(userId, 'jpg')` → `u{userId}/{uuid}.jpg`，**相对路径**，不写公网 URL |
| `mime` | 固定 `'image/jpeg'` |
| `width` / `height` | 归一化后实际像素（`probe.ts` 复核值，**不是**计算值） |
| `sha256` | 归一化后**文件内容**的 sha256 |
| `source_photo_id` | 入参原图的 `photos.id` |
| `quality_json` | `JSON.stringify(Quality)`，键名与 `14-接口契约.md` §4 的 `Quality` 逐字段一致（camelCase，不做 snake 转换，因为它是 JSON 列而非列名） |

同事务内追加 `audit_logs`：

```sql
INSERT INTO audit_logs (user_id, action, target, meta_json, created_at)
VALUES (:userId, 'photo.preprocess', 'photo:' || :newPhotoId,
        '{"sourcePhotoId":12,"usable":true,"readability":0.78}', :nowIso);
```

`action` 取值来自 `01-领域模型与数据库.md` §3.14 的固定清单。

### 3.4 不写

- 不写 `identity_anchors.quality_json`——那是 `06-后端-身份锚点提取.md` 在创建锚点行时对本模块 `Quality` 的**快照复制**；
- 不写 `content_reviews`——上传阶段的审核行由 `POST /api/photos` 写（`14-接口契约.md` §3.2）。

## 4. 对外接口

只有一个端点，定义见 `14-接口契约.md` §3.2：

```
POST /api/photos/:id/preprocess
```

- 受保护端点（`requireUser()`；未登录 → `401 UNAUTHENTICATED`）；
- 同步执行，预期 < 2s，成功返回 `200`；
- 响应形状：`{ photo: Photo, quality: Quality }`，**不新增字段、不新增端点**；
- `usable = false` 时**同样返回 `200`**（原文："若 `usable = false` 仍返回 `200`，由前端决定是否放行"）；
- 幂等：同一 `sourcePhotoId` 已存在 `preprocessed` 行则直接返回该行（§5.3）。

`quality` 的 8 个键**顺序与含义照抄** `14-接口契约.md` §4 的 `Quality`，本模块是它的唯一生产者：

| 键 | 类型 | 范围 | 含义 |
|---|---|---|---|
| `usable` | `boolean` | — | 可用性终判，见 §6 阈值表 |
| `faceDetected` | `boolean` | — | 是否检出人脸（或退化模式下是否有中心高频能量，见 §4.2） |
| `faceCount` | `number` | ≥ 0 整数 | 检出的人脸数；退化模式下为 `faceDetected ? 1 : 0` |
| `sharpness` | `number` | [0, 1] | 清晰度，见 §4.1 |
| `readability` | `number` | [0, 1] | 综合可读性，见 §4.1 |
| `damageLevel` | `number` | [0, 1] | 破损/褪色程度，见 §4.1 |
| `warnings` | `string[]` | 可空数组 | 不阻断的提示，见 §6.2 |
| `advice` | `string \| null` | — | `usable=false` 时的换图建议；`usable=true` 恒为 `null` |

所有浮点值在写库前 `Math.round(v * 1000) / 1000` 取三位小数（与 `docs/raw/AIGC_PRD.md` §9 的 `quality_score NUMERIC(4,3)` 精度一致），保证 `API-02` 的响应断言稳定。

### 4.1 评分算法（可实现形式）

**分析副本**：对归一化结果（§5.2 的 jpeg Buffer）再构造一次 `sharp()`，缩到长边 ≤ 1024 的灰度图，得到：

```ts
// src/server/images/quality.ts
interface AnalysisInput {
  gray1024: Buffer;       // sharp(buf).greyscale().resize({ width, height, fit: 'inside', withoutEnlargement: true }).raw().toBuffer()
  width: number;          // 归一化后整图宽（整图，不是分析副本）
  height: number;
  faceBox: { x: number; y: number; w: number; h: number } | null;
}

export function scoreQuality(a: AnalysisInput): Quality;
```

统计量：

```ts
const st = await sharp(a.gray1024).stats();
const L  = st.sharpness;              // Laplacian 卷积的标准差（sharp.stats() 已提供，见下方注）
const sd = st.channels[0].stdev;      // 亮度标准差
const raw = await sharp(a.gray1024).raw().toBuffer(); // 单通道 uint8
// 直方图尾部质量占比
const hi = raw.filter(v => v >= 250).length / raw.length;  // 高光截断
const lo = raw.filter(v => v <= 5).length / raw.length;    // 暗部压死
```

> 注：`sharp.stats()` 的 `sharpness` 字段定义为"基于 Laplacian 卷积标准差的灰度清晰度估计"（[sharp API · stats](https://sharp.pixelplumbing.com/api-input)）。若某版本不返回该字段，退回用 `sharp(gray1024).convolve({ width: 3, height: 3, kernel: [0,1,0, 1,-4,1, 0,1,0] })` 后取 `stats().channels[0].stdev`，语义等价。这一步的实现选择作为**待定决策**记录（§9）。

**sharpness**（`SHARP_FLOOR = 3.0`、`SHARP_CEIL = 15.0` 为标定常数）：

```ts
const sharpness = clamp01((L - SHARP_FLOOR) / (SHARP_CEIL - SHARP_FLOOR));
const clamp01 = (v: number) => Math.min(1, Math.max(0, v));
```

`L < 3` 视为完全糊，`L ≥ 15` 视为足够清晰。**这两个常数必须用 `docs/老照片/*.jpg` 与 `fixtures/` 样本标定**，标定值写回常量并在 ticket 04 的 `## Comments` 记录实测表。

**readability**（四个子分加权，权重之和 = 1）：

```ts
const resScore   = clamp01(Math.min(a.width, a.height) / 1000);      // 短边 1000px 记满分
const contrastScore = clamp01(sd / 64);                              // 亮度标准差 64 记满分
const blurScore  = sharpness;                                        // 复用同一量
const faceSizeScore = a.faceBox
  ? clamp01((Math.max(a.faceBox.w, a.faceBox.h) / Math.max(a.width, a.height) - 0.05) / (0.30 - 0.05))
  : FALLBACK_FACE_SIZE_SCORE;                                        // 0.6，见 §4.2

const readability = 0.35 * resScore + 0.25 * contrastScore + 0.25 * blurScore + 0.15 * faceSizeScore;
```

| 子分 | 权重 | 常数 | 依据 |
|---|---|---|---|
| `resScore` | 0.35 | `1000` | 分辨率是"面部细节够不够"的第一决定项 |
| `contrastScore` | 0.25 | `64` | 正常曝光 jpeg 的亮度标准差量级；褪色照显著偏低 |
| `blurScore` | 0.25 | 同 `sharpness` | 焦不实/抖动直接毁掉特征 |
| `faceSizeScore` | 0.15 | `0.05` / `0.30` | 人脸长边占整图长边 5% 以下基本不可读，30% 以上充分 |

**damageLevel**（亮度直方图尾部 + 高频能量缺失，两项各 0.5）：

```ts
const tailScore = clamp01((hi + lo) / 0.08);              // 尾部像素合计 8% 视为严重损坏
const hfLoss    = clamp01(1 - L / HF_REFERENCE);           // HF_REFERENCE = 20.0
const damageLevel = 0.5 * tailScore + 0.5 * hfLoss;
```

- `tailScore` 抓的是**高光溢出 / 暗部压死**（过曝的白脸、发黑的脸）；泛黄褪色**不触发**它——本产品生成的目标质感本来就允许泛黄，不该因此判不可用；
- `hfLoss` 抓的是高频能量整体缺失（糊 + 脏），与 `sharpness` 同源但取相反方向，故给 0.5 权重而非常量权重；
- 本模块**不做划痕/破损检测**（`docs/raw/AIGC_PRD.md` 的"破损程度"在此只降级为尾部+高频两项），因为任何"破损位置"结论都会诱导后续做修复——那正是 `00-总纲.md` §1.3 禁止的。差异见 §10。

### 4.2 人脸检测方案选型（含退化路径）

| 优先级 | 方案 | 产出 | 依赖成本 |
|---|---|---|---|
| 1 | `@vladmandic/face-api`（Node 版，TFJS CPU） | `faceDetected` / `faceCount` / `faceBox` | 新依赖 + 模型权重文件（数 MB，需落 `fixtures/` 或本地缓存） |
| 2 | `onnxruntime-node` + 现成人脸检测 onnx 模型 | 同上 | 新依赖 + 模型文件，native 模块在 Windows 上需预编译产物 |
| 3（退化） | **中心区域高频能量估计** | `faceDetected`（阈值判定）、`faceCount ∈ {0,1}`、`faceBox = null` | 零新依赖，复用 §4.1 已有的拉普拉斯统计 |

退化路径的定义（必须确定性可复现）：

```ts
// 取中心区域：宽高各 60%，居中
const center = sharp(gray1024).extract({ left: 0.2 * w, top: 0.2 * h, width: 0.6 * w, height: 0.6 * h });
const centerL = (await sharp(await center.png().toBuffer()).stats()).sharpness;
const faceDetected = centerL >= CENTER_FACE_FLOOR;   // CENTER_FACE_FLOOR = 6.0
```

当 `faceDetected = true` 时 `faceCount = 1`、`faceSizeScore = FALLBACK_FACE_SIZE_SCORE = 0.6`，并在 `warnings` 追加 §6.2 的"未启用本地人脸检测"提示。

**三个方案任选其一是允许的，但必须在 ticket 04 的 `## Comments` 写明选了哪一个**：不选方案 1/2 时，`usable` 判定不得因此收紧（`faceDetected` 只在退化模式下参与判定，见 §6.1），否则本地零外部依赖的约束（`README.md` §4.3）会被打破。该选型正式列为**待定决策**（§9）。

## 5. 关键流程与状态机

### 5.1 七步流水线

```
① 读行 → ② 读文件 → ③ 方向校正 → ④ 色彩空间统一 → ⑤ 尺寸归一 → ⑥ jpeg 编码 → ⑦ 评分+落库
```

| 步 | 操作（sharp 调用） | 每步的理由 |
|---|---|---|
| ① 读行 | `photos.findOriginalById(id, userId)`；`deleted_at` 非空或不存在 → `404 NOT_FOUND`；`kind != 'original'` → `400 INVALID_PARAM` | 不返回 403 以避免探测（`API-04`） |
| ② 读文件 | `getStorage().read(row.storage_key)`；失败 → `STORAGE_ERROR` | 文件是唯一存储介质（`03` §4.5） |
| ③ 方向校正 | `.rotate()`（无参数 = 按 EXIF Orientation 自动旋转） | 手机/扫面仪的老照片常带 Orientation；不校正会让"脸跑偏"，且旋转后宽高可能互换。**必须在 resize 之前**，否则旋转会把归一化尺寸算错 |
| ④ 色彩空间统一 | `.pipelineColourspace('srgb16').toColourspace('srgb')` | 源图可能是 CMYK / Display P3 / 无 profile；统一到 sRGB 后，读图模型与生图模型的颜色判断才一致 |
| ⑤ 尺寸归一 | `long = max(w, h)`；`long >= 1600` 时 `scale = 1600 / long`，`target = round(w*scale) × round(h*scale)`；`long < 1600` 时**不 resize**。`.resize({ width, height, fit: 'inside', kernel: 'lanczos3', withoutEnlargement: true })` | 长边 1600 是"面部细节足够且文件不过大"的折中；**绝不放大**：`withoutEnlargement: true` 是硬保护，放大只会产生插值像素（§1.3） |
| ⑥ jpeg 编码 | `.jpeg({ quality: 92, chromaSubsampling: '4:4:4', mozjpeg: false })` | 92 在"肉眼无块效应"与"体积可控"之间；`4:4:4` 保住肤色与老年斑的颜色边界（`2x2` 会把细小色差抹掉）；固定 `mozjpeg: false` 保证跨机器输出字节稳定（`E2E-07` 依赖确定性） |
| ⑦ 评分+落库 | 见 §4.1、§3.3 | — |

**元数据剥离不需要额外一步**：sharp 默认**不**保留元数据，只有显式 `.withMetadata()` / `.keepMetadata()` 才会写回。因此本模块**禁止调用**这两个方法——这就是"剥离 EXIF/ICC/IPTC/XMP"的实现方式，也是它必须被写成一条禁令而不是一步操作的原因。

宽高不匹配的处理：`.resize()` 只保证不放大；**不做裁剪**（`fit: 'inside'` 而非 `'cover'`），因为裁剪会改构图（§1.3）。

### 5.2 归一化函数契约

```ts
// src/server/images/preprocess.ts
export interface NormalizeResult {
  buffer: Buffer;                 // 归一化后的 jpeg
  width: number;                  // probe.ts 复核后的实际宽
  height: number;                 // probe.ts 复核后的实际高
  resized: boolean;               // false 表示长边本就 < 1600，未做任何缩放
}
export async function normalize(input: Buffer): Promise<NormalizeResult>;
```

纯函数：不读库、不写盘、不看环境变量。测试可以直接喂 Buffer（`preprocess.test.ts`）。

### 5.3 幂等语义

```
POST /api/photos/:id/preprocess
  │
  ├─ 已有 preprocessed 行（source_photo_id = :id, deleted_at IS NULL）
  │     → 直接返回该行 + 该行 quality_json 反序列化出的 Quality   （不重算、不落新行、不写审计）
  │
  └─ 无 → 执行 §5.1 七步 → 事务内 INSERT photos + INSERT audit_logs → 返回新行
```

- 判重必须在**取到原图行之后、读文件之前**，避免无谓 IO；
- 同一进程内并发同一 `:id` 用模块级单飞表去重：`Map<number, Promise<PreprocessResult>>`（Next.js dev server 单进程；本期不引入分布式锁）；
- `preprocessed` 行**没有状态列**，不存在 `queued/running`——本端点是同步的，因此 `01-领域模型与数据库.md` §2.3 的照片生命周期（`deleted_at` 软删 + 清理 worker 物理删除）就是它唯一的"状态机"。原图被删时，本模块产出的行由级联软删一并标记（`01` §2.3），不需要本模块主动处理。

## 6. 边界与错误

### 6.1 `usable` 与 `advice` 判定阈值表

判定**顺序即优先级**：从上到下第一个命中的行决定 `usable` 与 `advice`。

| 序 | 条件 | `usable` | `advice`（原文） | 其他输出 |
|---|---|---|---|---|
| 1 | `faceDetected = false && faceCount = 0` | `false` | `照片里没找到人脸，换一张人物正脸、别太小的试试` | — |
| 2 | `readability < 0.35` | `false` | `这张照片太模糊或者太暗，人物特征看不清，建议换一张更清楚的` | — |
| 3 | `damageLevel > 0.60` | `false` | `这张照片褪色或者破损得比较厉害，可能认不准长相，建议换一张保存得更好的` | — |
| 4 | `min(width, height) < 320` | `false` | `这张照片太小了，放不进面部细节，建议换一张大一点的` | — |
| 5 | 其余 | `true` | `null` | `warnings` 按 §6.2 累计 |

`usable=false` **不阻断流程**：仍返回 `200` 与完整 `Quality`。前端在"预览 + 这就是他"页展示 `advice` 与一个"仍然用这张"的次级按钮；点了就继续走 `POST /api/anchors`（`14-接口契约.md` §3.3）。服务端**不**在预处理阶段拒绝，因为最终裁判是用户点"这就是他"的那一下（`00-总纲.md` §3 铁律）。

第 4 条只在退化模式下可能被第 1/2 条提前命中之外单独出现（例如非常小的、中心高频很强的截图），它必须存在，因为 `usable=true` 而 `min(width,height) = 180` 会让锚点提取在模型侧直接失败。

### 6.2 `warnings` 取值集合（固定文案，不自由拼接）

| 触发条件 | 文案 |
|---|---|
| 长边原本 < 1600（`resized = false`） | `原图分辨率偏低，面部细节可能不足`（与 `14-接口契约.md` §3.2 示例逐字符一致） |
| `faceCount >= 2` | `照片里有 N 个人，系统会以画面中间那个人为准` |
| `readability ∈ [0.35, 0.50)` | `这张照片不算清楚，认特征可能会有点偏差` |
| `damageLevel ∈ (0.40, 0.60]` | `照片有褪色或者小破损，已经按原样保留，没有修` |
| 退化人脸检测路径启用（§4.2） | `本地没启用人脸检测，人脸判断是估算的` |
| `sharpness ∈ [SHARP_FLOOR, 5.0)` | `照片有点糊，人物特征可能不够准` |

文案约束：第二人称、平实、不煽情（`15-前端-设计基准与路由.md` §5），且**不得出现"修复""变清晰"这类承诺**（`README.md` §0.1）。

### 6.3 错误码映射

| 错误码 | HTTP | 触发条件 | 用户可见文案 |
|---|---|---|---|
| `UNAUTHENTICATED` | 401 | 未登录 | 请先登录 |
| `NOT_FOUND` | 404 | `:id` 不存在 / 属他人 / `deleted_at` 非空 | 这张照片找不到了 |
| `INVALID_PARAM` | 400 | `:id` 非整数；`kind != 'original'`（含 `generated` 与 `preprocessed`） | 这张照片不能再做这个处理，换一张原图试试 |
| `STORAGE_ERROR` | 500 | 读原文件失败 / 写归一化结果失败（磁盘满、文件丢失） | 保存失败，请重试 |
| `INTERNAL` | 500 | sharp 解码失败或未预期异常（**不透传原始 message**） | 出了点小问题，请重试 |

**不在此处使用**哪个码：`ANCHOR_LOW_QUALITY`（`422`）属于提取阶段的拒绝信号，由 `06-后端-身份锚点提取.md` 抛；`INVALID_FILE_TYPE` / `FILE_TOO_LARGE` 属于上传阶段（`POST /api/photos`）；`CONTENT_REJECTED` 属于审核。本模块不得抛这四个码。

## 7. 配置与环境变量

本模块**不引入任何新环境变量**。`03-后端-模块总览.md` §4.5 与 `18-本地开发指南.md` §4 已有的、本模块会读到的：

| 变量 | 本模块用途 |
|---|---|
| `DATABASE_PATH` | 经 `getDb()` 间接使用，本模块不直接读 |
| `STORAGE_DIR` | 经 `getStorage()` 读原文件、写归一化结果，本模块不直接读 |

`MAX_UPLOAD_MB` **不在本模块读取**（它只约束 `POST /api/photos`）。所有评分常数（`SHARP_FLOOR`、`SHARP_CEIL`、`HF_REFERENCE`、`CENTER_FACE_FLOOR`、`FALLBACK_FACE_SIZE_SCORE`、权重、阈值）以 `const` 定义在 `src/server/images/quality.ts`，**不做成环境变量**——它们是产品判定标准，不允许按环境漂移（否则 `E2E-04` 与人工验收无法复现）。

### 8.2 与 B 层检查项的对齐

本模块**没有专属的 B 层检查项**——`17-验收标准与自动化检查.md` §2 未给预处理单列 ID。它的正确性通过下列检查项的前置条件体现：

| 检查项 | 与本模块的关系 |
|---|---|
| `E2E-01` | 第 2 步即 `preprocess`，必须返回 `200` 且产出可被后续 `POST /api/anchors` 使用的行 |
| **`E2E-04`** | **本模块的直接前置**：`generations.reference_photo_ids` 里那恰好 1 个 id，其 `photos.kind` 必须为 `'preprocessed'`——这一行**只能**由 `POST /api/photos/:id/preprocess` 产生（`14-接口契约.md` §3.5：`reference_photo_ids = [preprocessedPhotoId]`） |
| `API-02` | `/api/photos/:id/preprocess` 的响应用 `src/shared/types.ts` 的 `Quality` zod schema 校验，§8.1 的 `U-05-12` 是它的单元级护栏 |
| `API-03` / `API-04` | §6.3 的 `UNAUTHENTICATED` / `NOT_FOUND` 分支 |
| `SEC-06` | `kind='generated'` 走本端点 → `400 INVALID_PARAM`；同时验证 §3.1 的 kind 校验 |
| `E2E-07` | 依赖 §5.1 步⑥的"同输入同输出字节"（`U-05-06`）与 mock 确定性选图共同成立 |

`E2E-04` 的完整前置链：`pnpm migrate && pnpm seed` → 登录 → 上传（`docs/老照片/1b26e45303c7321fa589d4525b43aa0.jpg`）→ 本端点产出 `kind='preprocessed'` 行 → 建锚点 → 确认 → 生成。**这四步里任何一步失败，`E2E-04` 都无法判定。**

## 9. 非目标与待定决策

### 9.1 非目标（本期）

| 非目标 | 说明 |
|---|---|
| 任何形态的图像增强 provider | 见 §1.3；`00-总纲.md` §6.2 已列 |
| 跨图排序（"哪张更适合作为基准"） | 服务端不做；前端可对每张原图各调一次本端点再比 `readability`（§10） |
| 多张原图融合成一张预处理图 | `identity_anchors.input_photo_ids` 支持多个 id，但 `preprocessed_photo_id` 只有一个（`01` §3.5）；融合留待 F3 |
| 损坏检测与定位（划痕、折痕、霉斑） | §4.1 只做全局统计 |
| 图像方向以外的几何校正（透视纠正、倾斜拉直） | 属于"修复"范畴 |
| 结果缓存与 CDN | 本地单机 |

### 9.2 待定决策（必须由 ticket 04 在 `## Comments` 补齐）

1. **人脸检测选型**：`@vladmandic/face-api` / `onnxruntime-node` / 中心高频能量退化（§4.2）。影响：`faceCount`、`faceSizeScore`、`faceBox` 的有无与 `radius` 判定精度。不引入新依赖会导致 `faceCount` 恒为 0 或 1（多人照无法识别）。
2. **评分常数标定**：`SHARP_FLOOR = 3.0`、`SHARP_CEIL = 15.0`、`HF_REFERENCE = 20.0`、`CENTER_FACE_FLOOR = 6.0`、`FALLBACK_FACE_SIZE_SCORE = 0.6`，以及 §6.1 的 `0.35 / 0.60 / 320`。这些数字是**量级合理的估计值，尚未实测**；标定样本 = `docs/老照片/*.jpg` 2 张 + `fixtures/images/*` 3 张 + 4 个程序构造样本（全黑、纯模糊、高对比、极小）。
3. **`sharp.stats().sharpness` 可用性**：需在实现时确认本机 sharp 版本返回该字段；不返回则用 §4.1 的 `convolve` 内核替代。
4. **`chromaSubsampling: '4:4:4'` 的体积代价**：需比对 `2x2` 的实际文件大小差异；若超过 `MAX_UPLOAD_MB` 的 1/4，重新评估该常数（不影响 §5.1 其他步骤）。
5. **并发单飞表的生命周期**：`Map` 何时清理（完成后立即 `delete` vs 进程内常驻）。单进程本地环境两种都可，需选定一种写进代码并在测试里断言。
