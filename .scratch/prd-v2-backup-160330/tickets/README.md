## 3. 为什么是这 18 条

拆解粒度遵循一条规则：**一条 ticket 应该是一个 AI 会话能做完、且能被独立验证的工作单元。**

- **按"可验证的交付物"切，不按"技术层"切**。所以"上传"与"预处理"分开（后者有独立的质量评分逻辑与检查项），而不是合成一条"照片处理"。
- **契约类工作单独成条**（`02` 数据层、`05` Provider 抽象、`08` Prompt 引擎）。它们是后面所有工作的地基，一旦返工代价最大。
- **合规拒绝路径不单独成条**，而是分散到对应 ticket 的检查项（`SEC-01`~`SEC-08`）——因为它们是各自功能的边界条件，单独做一条会做成"事后补丁"。
- **前端按用户旅程切**（上传/确认、选择、结果），不按组件切。
- **`18` 最后一条是验收工具**，因为它需要所有端点就位才能写。

### 3.1 明确没有单独成条的东西（以及为什么）

| 没单独成条 | 落在哪 |
|---|---|
| 数据库连接池/ORM 配置 | `02`（无 ORM，连接就是 3 行） |
| 内容审核 | `11`（审核是生成流程的组成部分，不是独立功能） |
| 审计日志 | `07`+`12`（跟着各自的动作写） |
| 缩略图/图片流优化 | `03`（`?w=` 参数是上传模块的一部分） |
| 错误码常量表 | `01`（一个文件的事） |
| 部署/CI | 本期不做（见 `00-总纲.md` §6.2） |
