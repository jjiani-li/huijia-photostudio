### 1.1 做什么

### 1.2 为什么确认节点是强制的

`spec/00-总纲.md` §3 把 ③④ 之间定义为强制节点，四条硬约束：

1. **错误锚点的成本是乘性的**：一次 `POST /api/generations` 产出 2–4 张图（`count ∈ {2,3,4}`，落库为 `requested_count`），锚点错了错的是整批，确认节点是乘数之前的唯一闸门。
2. **链路里没有人工复核环**：`anchor_text` 会**原样**进入 prompt 的【身份锚点】段（`spec/05-Prompt工程.md` §2.1，缺失即拒绝生成），系统没有任何一步能自动判断"这段文本描述的是不是照片里的那个人"，只有用户知道。
3. **情感伤害不可逆**：`spec/00-总纲.md` §2 的两类用户都在处理逝者照片，生成出"长得像别人的人"是二次伤害。
4. **确认也是法律行为**：点"这就是他"= 对身份的**主张**，勾选两项授权 = 对使用权的**声明**，两者共同固定责任归属，并把当时所用的锚点写进 `consents.anchor_id`，可追溯"哪一次确认时勾的"。

**确认 ≠ 认可画质。** 确认只回答"这描述的是他吗"，不回答"这张照片修得好不好"——产品里没有"修复"这一步（`README.md` §0.1）；与 `modules/M02-预处理与质量评分.md`、`modules/M03-身份锚点提取.md` 的边界即在此。

### 1.3 明确不做什么

- ❌ 不做实名认证、身份证校验、人脸比对（`spec/07-验收标准.md` §6 明确面部相似度本期不实现）；不做授权书上传、亲属关系证明、多方签名；
- ❌ 不做吊销 UI 与吊销端点（`spec/03-接口契约.md` 无此端点，不得自行发明）；
- ❌ 不在前端做"可否生成"的权威判断（`spec/03-接口契约.md` §6.2）；
- ❌ 不在 confirm 里顺带触发提取或生成；confirm 只做状态与授权写入；
- ❌ 不删改 `consents` 历史行（§5.4、§5.5）。

### 3.3 关键 SQL

有效授权判定（生成前置校验用，按**用户级**判定，理由见 §9 待定决策 3）：

```sql
SELECT 1 FROM consents
 WHERE user_id = ? AND scope = 'photo_usage' AND revoked_at IS NULL
 LIMIT 1;
```

confirm 的幂等复用判定：

```sql
SELECT id FROM consents
 WHERE user_id = ? AND anchor_id = ? AND scope = ? AND revoked_at IS NULL
 ORDER BY id DESC LIMIT 1;
```

确认写入（`COALESCE` 保证重复确认不改首次确认时间；`WHERE confirmed_by_user = 0` 同时给出"本次是否真的发生了状态变化"）：

```sql
UPDATE identity_anchors
   SET confirmed_by_user = 1, confirmed_at = COALESCE(confirmed_at, ?)
 WHERE id = ? AND confirmed_by_user = 0;
```

## 5. 关键流程与状态机

### 5.1 confirm：单事务

```ts
// src/server/domain/anchorService.ts
export function confirmAnchor(
  userId: number,
  anchorId: number,
  consents: ConsentScope[],
): { anchor: Anchor; consents: ConsentScope[] };
```

同步函数（`better-sqlite3` 为同步 API），固定顺序：

```ts
const db = getDb();
return db.transaction(() => {
  // ① 归属与存在性
  const row = anchorsRepo.findByIdForUser(db, anchorId, userId);
  if (!row) throw new AppError('ANCHOR_NOT_FOUND', '这次的人物特征记录找不到了', 404);
  // ② 可用性：仅 succeeded 且 anchor_text 非空
  if (row.status !== 'succeeded' || !row.anchorText) {
    throw new AppError('ANCHOR_NOT_CONFIRMED', '需要先确认"这就是他"，才能开始生成', 409);
  }
  // ③ 授权项完整性：两项必须同时提交
  const missing = CONSENT_SCOPES.filter((s) => !consents.includes(s));
  if (missing.length > 0) {
    throw new AppError('INVALID_PARAM', '选择有误，请重新选一下', 400, { fields: { consents: missing } });
  }
  // ④ 时间戳只取一次：consents.agreed_at 与 audit_logs.created_at 必须逐字符相等
  const at = nowIso();
  // ⑤ 幂等写 consents 两行：同 anchorId + scope 未吊销则复用，否则插新行
  for (const scope of CONSENT_SCOPES) consentsRepo.ensureActive(db, userId, anchorId, scope, at);
  // ⑥ 写确认字段（confirmed_at 仅 0→1 时落值）
  anchorsRepo.markConfirmed(db, anchorId, at);
  // ⑦ 审计两条
  audit({ userId, action: 'anchor.confirm', target: `anchor:${anchorId}`,
          meta: { attempt: row.attempt, promptVersion: row.promptVersion } }, at);
  audit({ userId, action: 'consent.agree', target: `anchor:${anchorId}`,
          meta: { scopes: CONSENT_SCOPES } }, at);
  return { anchor: anchorsRepo.toAnchorDto(db, anchorId, userId), consents: [...CONSENT_SCOPES] };
})();
```

`CONSENT_SCOPES = ['photo_usage', 'family_agreement'] as const`，定义在 `src/shared/types.ts`，与 `spec/01-领域模型与数据库.md` §3.11 的 `scope` 取值一致。

**状态机（confirm 视角）**

```
succeeded, anchor_text != null, confirmed_by_user = 0
      │ ① ② ③ 通过
      ▼
confirmed_by_user = 1, confirmed_at = 首次确认时间
      │
      ├─ 重新提取 → POST /api/anchors/:id/retry → 新行（旧行确认状态保留，供历史追溯）
      ├─ 重复 confirm → 仍 200；consents 复用不新增；confirmed_at 不变；审计每次请求都写
      └─ 授权被吊销 → confirmed_by_user 仍为 1，但生成前置校验的 ② 会拦下（§5.3）
```

③ 失败时 `confirmed_by_user` 必须仍为 0：③ 在 ⑥ 之前抛错，`db.transaction` 整体回滚（`spec/04-技术基线与目录结构.md` §4.3）——这是 `SEC-02` 的机器可验证形式，结构上写不进去。重复 confirm 仍写审计：每次点击都是一次真实的授权意思表示，而 `confirmed_at` 不变使审计成为唯一的"来看过并再次确认"的证据（§9 待定决策 1）。

### 5.2 retry：新建行，旧行不动

```ts
// src/server/domain/anchorService.ts
export function retryAnchor(userId: number, anchorId: number): Anchor;
```

| 步骤 | 内容 |
|---|---|
| ① | 读旧行 `findByIdForUser`，缺失 → `404 ANCHOR_NOT_FOUND` |
| ② | 旧行 `status` 必须为终态（`succeeded` / `failed`）；`queued` / `running` → `409 ANCHOR_NOT_CONFIRMED`（复用同一码，语义同 `spec/03-接口契约.md` §3.3 的"锚点不可用"，见 §9 待定决策 2） |
| ③ | `INSERT` 新行（`status='queued'`） |
| ④ | 写审计 `anchor.extract`，`target = anchor:{新 id}`，`meta = { retryOf: 旧 id, attempt: 新 attempt }` |

新行字段清单：

| 字段 | 取值 | 理由 |
|---|---|---|
| `input_photo_ids` | **逐字符继承**旧行 JSON 文本 | 用户没有换照片，重试的是提取，不是选图 |
| `preprocessed_photo_id` | 继承旧行（可能为 `NULL`） | 同一张预处理图输入；为 `NULL` 时由 `modules/M03-身份锚点提取.md` 的规则对 `input_photo_ids[0]` 触发预处理 |
| `attempt` | `旧行.attempt + 1` | `spec/03-接口契约.md` §3.3 |
| `model` / `prompt_version` | `ARK_VISION_MODEL` 与 `ANCHOR_PROMPT_VERSION`（`anchor-v1`）的**当前**值 | 重试就是用当前模型与规范再提一次；旧行保留旧版本号，历史仍可复现（`spec/05-Prompt工程.md` §7.1） |
| `quality_json` | 继承旧行快照 | 预处理图未变，评分结论不变，省一次 `sharp` 计算 |
| `confirmed_by_user` / `confirmed_at` | `0` / `NULL` | 新锚点是新主张，必须重新确认（§1.2） |
| `anchor_text` / `features_json` / `error_code` / `error_message` / `started_at` / `finished_at` | `NULL` | 由 worker 重新提取；新行从零开始 |
| `created_at` | `nowIso()` | 新行在 `/api/history` 里按 `created_at DESC` 排在最前 |

**旧行与旧结果不被修改**：① 可追溯——`spec/01-领域模型与数据库.md` §4 明确"重新提取 = 插入新行"，旧 `anchor_text` 是"用户当时看到并确认过的文本"，覆盖后历史链路无法解释当时为什么生成出那张图；② 可复现——`generations.anchor_id` 指向旧行，改写会破坏 `E2E-03`（`generations.prompt` 与 `buildPrompt` 输出逐字符相等）；③ 合规——`consents.anchor_id` 指回旧行，授权留痕所依附的锚点记录必须保持当时的样子。

### 5.3 生成前置校验：两步的顺序与位置

实现位置：`src/server/domain/generationService.ts` 的 `createGeneration()`，严格按 `spec/03-接口契约.md` §3.5 的表格顺序。与本文件相关的两行是第 4、5 步：

```ts
// 前置：count / eraCode / sceneId 校验（modules/M06-生成编排.md）；锚点归属 → 404 ANCHOR_NOT_FOUND
// ① 锚点可用性（先）
if (anchor.status !== 'succeeded' || anchor.confirmedByUser !== 1) {
  throw new AppError('ANCHOR_NOT_CONFIRMED', '需要先确认"这就是他"，才能开始生成', 409);
}
// ② 授权（后）
if (!consentsRepo.hasActiveScope(db, userId, 'photo_usage')) {
  throw new AppError('CONSENT_REQUIRED', '需要先确认照片使用授权', 403);
}
```

**为什么 CONFIRMED 必须先于 CONSENT 判定**：

1. **归因必须指向最近的可执行动作**。锚点未确认时，"这就是他"按钮与两项勾选框在**同一次提交**里发出（§5.1），此时报 `CONSENT_REQUIRED` 会把用户引向与当前阻塞点无关的解释。
2. **依赖方向是单向的**。`consents` 行是 confirm 的副产物（§5.1 ④⑤⑥），"未确认"在正常链路里**蕴含**"无有效授权"；先判授权等于把这个蕴含关系反过来用，得到错误的第一因。
3. **检查项独立性**。顺序固定后 `SEC-01` 不依赖测试数据里是否存在 `consents` 行——把 `confirmed_by_user` 置 0 即可稳定得到 409，否则会被 ② 提前截获成 403。
4. **整段顺序 404 → 409 → 403**：存在性先于权限，避免用 403 泄漏"这个锚点存在但不属于你"（`spec/07-验收标准.md` `API-04`）。

### 5.4 DELETE 的调用点

```ts
// app/api/anchors/[id]/route.ts
export const DELETE = withErrorHandling(async (_req, ctx) => {
  const user = await requireUser();
  const anchorId = parseId(ctx.params.id);         // 非法 → INVALID_PARAM
  return ok(await deletionService.cascadeFromAnchor(user.id, anchorId));
});
```

- 级联标记的**范围与顺序**见 `modules/M08-账号历史与彻底删除.md`；本文件只负责调用点与响应形状（`{ ok: true, cascaded: { generations, results } }`）；
- **幂等**：重复删除返回 `200`（`spec/03-接口契约.md` §1.5）；锚点已软删除时 `cascaded` 全为 0；
- 他人锚点 → `404 ANCHOR_NOT_FOUND`；
- 写审计 `anchor.delete`，`target = anchor:{id}`，`meta` 为 `cascaded` 计数快照；
- **不触碰 `consents`**：见 §5.5 末段。

### 5.5 授权吊销：`revoked_at` 语义与入口

| 状态 | 含义 | 判定结果 |
|---|---|---|
| `revoked_at IS NULL` | 授权有效 | 可用于 `photo_usage` 判定 |
| `revoked_at` 非空 | 该行授权自该时刻起失效 | 一律视为不存在 |

所有判定必须带 `revoked_at IS NULL`（`spec/01-领域模型与数据库.md` §3.11 的索引 `(user_id, scope)` 命中后再过滤此列）；**吊销不删行、不改 `agreed_at`**（表中无 `updated_at` 列），失效时刻只有 `revoked_at` 一个来源；吊销后**不自动恢复**——用户重新确认（§5.1）会插入**新的** `consents` 行（`revoked_at = NULL`），旧行的 `revoked_at` 永久保留，形成"同意 → 吊销 → 再同意"的完整轨迹。

服务端入口（本期无 UI、无端点）：

```ts
// src/server/domain/anchorService.ts
/** 吊销该用户某授权项的全部有效行，返回被吊销的行数。 */
export function revokeConsents(userId: number, scope: ConsentScope): number;
// UPDATE consents SET revoked_at = ? WHERE user_id = ? AND scope = ? AND revoked_at IS NULL
```

调用点只有三处：`scripts/acceptance.ts` 的 `SEC-03`（吊销 `photo_usage` 后发起生成必须得 `403 CONSENT_REQUIRED`）；将来的投诉/下架流程（`docs/raw/AIGC_PRD.md` §12 提到，本期不做）；账号处置流程（`modules/M08-账号历史与彻底删除.md`）。**不新增端点**，也不在测试之外自动调用。

**`DELETE /api/anchors/:id` 与 `DELETE /api/photos/:id` 都不写 `consents.revoked_at`、都不删 `consents` 行**：删除是"我不要再看到这些图"，吊销是"我当初的同意撤销了"；两者混在一个动作里，审计就无法区分"用户清理了历史"与"用户撤回了授权"——而后者才是必须被看见的法律事件。

## 6. 边界与错误

| 错误码 | HTTP | 触发条件 | 用户可见文案 |
|---|---|---|---|
| `UNAUTHENTICATED` | 401 | confirm / retry / DELETE 未登录或会话过期（`requireUser()` 抛出） | 请先登录 |
| `ANCHOR_NOT_FOUND` | 404 | 锚点不存在、已软删除、或属于他人（三者不区分） | 这次的人物特征记录找不到了 |
| `ANCHOR_NOT_CONFIRMED` | 409 | confirm 时 `status != 'succeeded'` 或 `anchor_text` 为空；retry 时旧行非终态；生成时 `status != 'succeeded'` 或 `confirmed_by_user != 1` | 需要先确认"这就是他"，才能开始生成 |
| `INVALID_PARAM` | 400 | confirm 的 `consents` 未同时包含两项；`confirmed` 不为 `true`；路径 `:id` 非整数；生成时 `count` 不在 {2,3,4} | 选择有误，请重新选一下 |
| `CONSENT_REQUIRED` | 403 | 生成时 `photo_usage` 无 `revoked_at IS NULL` 的行 | 需要先确认照片使用授权 |
| `INTERNAL` | 500 | 事务内未预期异常（含审计写入失败，`spec/04-技术基线与目录结构.md` §4.1） | 出了点小问题，请重试 |

约定：`INVALID_PARAM` 的具体缺失项**不新增错误码**，一律走 `details.fields`（前端据此高亮复选框，见 §12）；`message` 使用上表的通用文案（`spec/03-接口契约.md` §5）。

## 8. 测试要点

### 8.1 单元测试（`pnpm test`，`vitest`）

`confirmAnchor`：

1. `status='succeeded'` 且两项齐全 → `confirmedByUser: true`、`confirmedAt` 非空；`consents` 恰好 2 行且 `revoked_at IS NULL`；`audit_logs` 恰好 2 条（`anchor.confirm` / `consent.agree`），其 `created_at` 与 `consents.agreed_at` 逐字符相等；
2. `status` 为 `failed` / `running` / `queued`，或 `succeeded` 但 `anchor_text` 为 `NULL` → `ANCHOR_NOT_CONFIRMED` / 409，且 `confirmed_by_user` 仍为 0、`consents` 0 行、`audit_logs` 0 行（事务原子性）；
3. `consents` 只缺一项（两个方向各测一次）→ `INVALID_PARAM` / 400，`details.fields.consents` 恰好列出缺失项，且 DB 无任何写入（**`SEC-02` 的单元形态**）；
4. 连续调用两次 → 均 200；`consents` 行数仍为 2；`confirmed_at` 与首次相同；`audit_logs` 为 4 条（§9 待定决策 1）；
5. 他人锚点 → `ANCHOR_NOT_FOUND` / 404（不是 403）；
6. 先 `revokeConsents(userId, 'photo_usage')` 再 confirm → `consents` 新增 1 行，旧行 `revoked_at` 仍非空。

`retryAnchor`：

7. 新行 `attempt === 旧行.attempt + 1`；`input_photo_ids` 与 `preprocessed_photo_id` 与旧行**逐字符相等**；`status='queued'`；`confirmed_by_user = 0`；旧行全部字段（`anchor_text` / `features_json` / `confirmed_by_user` / `finished_at` / `error_code`）在 retry 前后逐字段相等；
8. 旧行 `queued` / `running` → `ANCHOR_NOT_CONFIRMED` / 409，且不产生新行；
9. `audit_logs` 新增 `anchor.extract` 一条，`meta_json.retryOf === 旧 id`。

`createGeneration` 顺序（**`SEC-01` / `SEC-03`**）：

10. `confirmed_by_user = 0` **且没有任何 `consents` 行** → 409 `ANCHOR_NOT_CONFIRMED`（不得是 403）；
11. `confirmed_by_user = 1`，`photo_usage` 行 `revoked_at` 非空 → 403 `CONSENT_REQUIRED`，且**不产生** `generations` 行。

`audit()`：

12. 在已开启的事务内抛错 → 整个事务回滚，`audit_logs` 无残留行；`meta` 经 `JSON.stringify` 写入后读回为对象；`target` 形如 `anchor:3`。

### 8.2 契约与链路检查（`pnpm check:acceptance`）

| 检查项 | 本模块的实现要求 |
|---|---|
| `SEC-01` | 未确认锚点（`confirmed_by_user=0`）发起生成 → `409 ANCHOR_NOT_CONFIRMED`。依赖 §5.3 的**判定顺序**，测试数据无需预置 `consents` |
| `SEC-02` | confirm 时 `consents` 缺 `family_agreement` → `400 INVALID_PARAM`，并复查数据库：`identity_anchors.confirmed_by_user` 仍为 0、`consents` 无新增行 |

| # | 问题 | 本文的选择 | 备注 |
|---|---|---|---|
| 1 | 重复 confirm 是否重复写审计 | **每次请求都写**（两条），`confirmed_at` 不变 | 契约未规定 confirm 的幂等语义；选择"状态幂等、留痕不幂等" |

| 5 | retry 新行的 `model` / `prompt_version` | 取**当前**常量，不复制旧行；缺一项授权时的文案走 `details.fields.consents` 而非新错误码 | §5.2、§12；若将来要求严格复现旧提取，改为复制旧行 |
| 6 | 吊销是否写审计 | 15 个 action 中**没有**吊销项，故 `revokeConsents` 不写审计 | 若合规要求留痕，需先按 `spec/01-领域模型与数据库.md` §3.14 增补 action 名 |

## 11. 审计写入约定

### 11.1 `src/server/security/audit.ts`

```ts
export type AuditAction =
  | 'auth.code_sent' | 'auth.login' | 'auth.logout'
  | 'photo.upload' | 'photo.preprocess' | 'photo.delete' | 'photo.purge'
  | 'anchor.extract' | 'anchor.confirm' | 'anchor.delete' | 'consent.agree'
  | 'generation.create' | 'generation.finish' | 'moderation.reject';

export interface AuditEntry {
  userId: number | null;                 // 匿名操作（发码前）为 null
  action: AuditAction;
  target?: string | null;                // 'anchor:3' / 'photo:12' / 'generation:7'
  meta?: Record<string, unknown> | null; // 只放原子值
}

/** 唯一业务入口。必须在调用方已开启的事务内调用。 */
export function audit(entry: AuditEntry, at?: string): void;
```

- 默认时间取 `nowIso()`；传 `at` 时用于让 `audit_logs.created_at` 与同事务内业务写入的时间戳**逐字符相等**（§5.1 ④）；
- 落库只有一句 `INSERT INTO audit_logs (user_id, action, target, meta_json, created_at) VALUES (?,?,?,?,?)`，SQL 在 `src/server/db/repositories/audit.ts`，`meta_json` 由 `JSON.stringify` 序列化；
- `AuditAction` 的 15 个取值与 `spec/01-领域模型与数据库.md` §3.14 的清单**完全一致**，不增不减；本文件写其中 4 个：`anchor.confirm`、`consent.agree`、`anchor.extract`（retry）、`anchor.delete`。

### 11.2 写入约定

| 约定 | 内容 |
|---|---|
| 事务归属 | `audit()` **不允许**在业务事务外调用；跨表写必须同事务（`spec/04-技术基线与目录结构.md` §4.3） |
| 失败语义 | 审计写入失败**不回吞**：抛出异常 → 整个事务回滚。这些 action 是合规证据，宁可让请求失败也不留半截记录 |
| 调用点 | 仅 `src/server/domain/*`、`src/server/auth/*`、`src/jobs/handlers/*`；`app/api/**/route.ts` **不得**直接调 `audit()`（`spec/04-技术基线与目录结构.md` §3.1） |
| `meta` 内容 | 只放 id、`attempt`、`scope` 数组、`cascaded` 计数。禁止放 prompt 全文（`generations.prompt` 已落库），禁止放手机号/邮箱明文（用 `src/server/auth/mask.ts`） |

## 12. 两个授权勾选框的逐字文案

| `scope` | 勾选框文案（逐字，建议采用） |
|---|---|
| `photo_usage` | `我确认我手上有这张照片的使用权，也确认照片里的人是我认识的人。` |
| `family_agreement` | `我已经和家里其他亲属说过这件事，他们同意我用这张照片来做。` |

同页面的辅助与操作文案（非授权项）：

| 位置 | 文案 |
|---|---|
| 勾选框下方小字（**默认可见、不可折叠**） | `如果家里有不同意见，请先沟通好再来做。` |
| 提交按钮 / 未勾齐时的行内提示 | `这就是他，开始生成` / `需要两项都勾上才能开始` |

约定：

- 两项**都必须显式勾选**，前端**不得**预勾选，不得用一个"同意以上全部"的合并框代替；
- 复选框的 `name` 直接取 `scope` 值（`photo_usage` / `family_agreement`），提交给 `POST /api/anchors/:id/confirm` 的 `consents` 数组顺序与文案顺序无关；
- 缺项时后端返回 `400 INVALID_PARAM`，`details.fields.consents` 列出缺失项，前端据此高亮对应复选框（`spec/03-接口契约.md` §1.3 允许前端读 `details.fields`）；
- 页面位置与视觉见 `pages/P01-页面规格.md`、`pages/P00-设计基准与路由.md`；本文件是这两句文案的**权威来源**。
