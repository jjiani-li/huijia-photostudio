> 本文件规定三件事：验证码账号与会话（`auth/`）、历史链路读取（`/api/history`）、级联软删除与延迟物理清理（`deletionService` 与 `jobs/handlers/purge.ts`）。接口形状见 `spec/03-接口契约.md` §3.1 / §3.6 / §3.2，字段名见 `spec/01-领域模型与数据库.md` §3。

## 1. 职责与边界

**做**：

1. 账号：验证码下发（归一化、10 分钟过期、同 `identifier` 60 秒节流）、登录建号、会话签发与吊销、`requireUser()` 鉴权、手机号/邮箱脱敏。
2. 历史：按 `identity_anchors.created_at DESC` 分组返回「原图 → 预处理图 → 生成图」链路，游标分页，只暴露未软删除的照片。
3. 彻底删除：`DELETE /api/photos/:id` 与 `DELETE /api/anchors/:id` 的级联语义（软删除 + 撤销授权），以及 `deleted_at` 到期后的物理清理（磁盘文件、`generation_results`、`photos` 行）。

**不做**：

- ❌ 密码、社交登录、一键登录、注册表单、找回密码（`spec/00-总纲.md` §6.1 F5 只要求验证码登录）；
- ❌ 真实短信通道：`SMS_PROVIDER=real` 路径本期不实现（`spec/08-本地开发指南.md` §5）；
- ❌ 文件加密存储、HTTPS、对象存储、外链签名（`spec/00-总纲.md` §6.2）；
- ❌ 历史导出、分享、跨用户查询；
- ❌ 用户自助注销/清空全部数据：本期"彻底删除"粒度是单张照片与单个锚点；
- ❌ 金额计费，只有 `usage_counters` 计数。

归属 ticket：`tickets/T12`（账号、会话与额度，覆盖本文件 §1–3、§7、§8.1）与 `tickets/T13`（历史记录、再生成与彻底删除，覆盖 §4–6、§8.2），见 `tickets/README.md` §2。

| 表 | 操作 | 条件 |
|---|---|---|
| `photos` | UPDATE `deleted_at` | 见 §5.2 级联表；`WHERE deleted_at IS NULL` 保证幂等 |

### 3.4 关键 SQL

发码节流：

```sql
SELECT id FROM login_codes
WHERE identifier = :identifier AND consumed_at IS NULL AND created_at > :nowMinus60s
ORDER BY created_at DESC LIMIT 1;
```

历史分页（`json_each` 展开 `input_photo_ids`；行值比较需要 SQLite ≥ 3.15，`better-sqlite3` 已满足）：

```sql
SELECT a.id, a.anchor_text, a.confirmed_at, a.created_at, a.input_photo_ids, a.preprocessed_photo_id
FROM identity_anchors a
WHERE a.user_id = :userId
  AND a.status = 'succeeded'
  AND EXISTS (
    SELECT 1 FROM json_each(a.input_photo_ids) je
    JOIN photos p ON p.id = je.value
    WHERE p.user_id = a.user_id AND p.deleted_at IS NULL
  )
  AND (:cursorCreatedAt IS NULL OR (a.created_at, a.id) < (:cursorCreatedAt, :cursorId))
ORDER BY a.created_at DESC, a.id DESC
LIMIT :limit + 1;
```

每锚点最近 10 条生成（SQLite ≥ 3.25 窗口函数）：

```sql
SELECT * FROM (
  SELECT g.*, ROW_NUMBER() OVER (PARTITION BY g.anchor_id ORDER BY g.created_at DESC, g.id DESC) AS rn
  FROM generations g
  WHERE g.user_id = :userId AND g.anchor_id IN (:anchorIds)
) WHERE rn <= 10;
```

级联标记（同一事务内的三条批量语句）：

```sql
UPDATE photos SET deleted_at = :now WHERE id IN (:photoIds) AND deleted_at IS NULL;
UPDATE consents SET revoked_at = :now WHERE anchor_id IN (:anchorIds) AND revoked_at IS NULL;
DELETE FROM generations WHERE id IN (:generationIds);
DELETE FROM identity_anchors WHERE id IN (:anchorIds);
-- generation_results 不在本事务内删除，由 runPurge() 按 photo_id 清理，见 §3.3
```

物理清理扫描（`idx_photos_deleted` 覆盖）：

```sql
SELECT id, user_id, storage_key, bytes FROM photos
WHERE deleted_at IS NOT NULL AND deleted_at < :threshold
ORDER BY deleted_at ASC LIMIT :batchSize;
```

## 5. 关键流程与状态机

### 5.1 账号与会话

**标识归一化**（`normalizeIdentifier(raw, channel?)`）：`trim`；含 `@` 或显式 `channel='email'` → 邮箱：转小写，须匹配 `/^[^@\s]+@[^@\s]+\.[^@\s]+$/`；否则手机号：去掉空格、`-`、`(`、`)`，再依次剥离 `+86` / 前导 `86`，最终必须是 11 位 `1[3-9]\d{9}`。失败 → `400 INVALID_PARAM`。归一化结果即 `login_codes.identifier` 与 `users.phone` / `users.email` 的写入值。

**发码**（`requestLoginCode`）：

```
归一化 → 节流查询命中 → 429 CODE_RATE_LIMITED
      → 生成 code = crypto.randomInt(0, 1_000_000).toString().padStart(6, '0')
      → INSERT login_codes(expires_at = now + 10min)
      → getSmsSender().send(identifier, code)
      → INSERT audit_logs(action='auth.code_sent')
      → 返回 { sent: true, expiresInSec: 600, devCode? }
```

`ConsoleSmsSender` 打印一行到终端：`[SMS] 138****8000 验证码 000000（10 分钟内有效）`（手机号经 `maskPhone`）。`exposeDevCode()` 返回 `process.env.SMS_PROVIDER === 'console'`；route handler 只在为真时给响应对象加 `devCode`，并调用 `assertDevCodeAllowed(payload)` 做实现层断言（断言失败抛 `INTERNAL`，**不把 code 透出**）。`SMS_PROVIDER=real` 时 `getSmsSender()` 抛 `AppError('INTERNAL', '验证码发送服务未配置', 500)`——本期无真实通道（`spec/08-本地开发指南.md` §5）。

**登录**（`loginWithCode`，单事务）：

```
1. 取该 identifier 最近一条 purpose='login' 的 login_codes
   ├─ 无行 或 consumed_at 非空          → 400 CODE_INVALID
   ├─ expires_at < now                  → 400 CODE_EXPIRED
   └─ 码不匹配（且非 console 万能码）    → 400 CODE_INVALID
2. UPDATE login_codes SET consumed_at = now WHERE id = :id
3. 按 phone/email 查 users，无则 INSERT（`nickname` 先写占位值）
   → UPDATE users SET nickname = '用户' || printf('%04d', id % 10000)
      -- 等价于 TS: `用户${String(id).padStart(4, '0').slice(-4)}`，id=1 → '用户0001'，id=12345 → '用户2345'
4. UPDATE users SET last_login_at = now
5. INSERT sessions(token_hash = sha256hex(token), expires_at = now + 30 天)
6. INSERT audit_logs(action='auth.login')
```

码比对用 `crypto.timingSafeEqual`，比较前校验两者长度均为 6。`SMS_PROVIDER=console` 时 `DEV_LOGIN_CODE`（默认 `000000`）可作为"万能码"通过第 1 步的码值比对，**但仍要求存在未消费且未过期的记录**。

**会话 cookie**：`token = crypto.randomBytes(32).toString('base64url')`（43 字符），`Set-Cookie` 属性逐项固定为：

| 属性 | 值 |
|---|---|
| 名称 | `sid`（常量 `SID_COOKIE`） |
| 值 | base64url 编码的 32 字节随机串，**明文只在响应里出现一次** |
| `HttpOnly` | 是 |
| `SameSite` | `Lax` |
| `Path` | `/` |
| `Max-Age` | `2592000`（30 天，与 `sessions.expires_at` 一致） |

不设 `Secure`、不设 `Domain`（本地 http 开发；生产要求见 §9 待定决策）。`sessions.token_hash` = `sha256(token)` 十六进制小写，明文不落库。

**登出**（`logout`）：`UPDATE sessions SET revoked_at = now WHERE token_hash = :hash AND revoked_at IS NULL`，清 cookie（同名 `Max-Age=0`），写 `audit_logs(action='auth.logout')`，返回 `{ ok: true }`。

**鉴权**（`session.ts`）：

```ts
export const SID_COOKIE = 'sid';
export interface SessionUser { id: number; phone: string | null; email: string | null; nickname: string; status: number }
export function getSessionUser(): SessionUser | null;   // 读 cookie → sha256 → sessions 查活跃行 → users.status=1
export function requireUser(): SessionUser;             // 失败 throw new AppError('UNAUTHENTICATED', '请先登录', 401)
export function createSession(userId: number): { token: string; expiresAt: string };
export function destroySession(token: string | null): void;
```

`getSessionUser()` 的顺序：cookie 缺失或不符合 `^[A-Za-z0-9_-]{43}$` → `null`（不查库）；查 `sessions` 命中条件为 `token_hash = ? AND revoked_at IS NULL AND expires_at > nowIso()`；再查 `users`，`users.status = 0` 视为不可用 → `null`。每个受保护端点在 handler 第一行调用 `requireUser()`（`spec/03-接口契约.md` §1.2 的受保护清单）。

**会话状态机**：

```
active ── 登出 ──▶ revoked  (revoked_at 非空)
      └─ expires_at < now ──▶ expired（不做定时清理，查询时判定）
```

**脱敏**（`mask.ts`）：

```ts
export function maskPhone(phone: string | null): string | null;   // '13800138000' → '138****8000'
export function maskEmail(email: string | null): string | null;   // 'abcd@x.com' → 'a***@x.com'；local 长度 1 → '***@x.com'
export function maskIdentifier(identifier: string): string;       // 含 '@' 走 maskEmail，否则 maskPhone
```

规则：手机号保留前 3 与后 4 位，中间固定 4 个 `*`（长度不足 7 时整串替换为等长 `*`）；邮箱保留本地部分首字符 + `***` + `@` + 域名原文。两个函数对 `null` 输入返回 `null`。`GET /api/me` 的 `user.phone` / `user.email` 必须经过 `maskPhone` / `maskEmail`，`API-05` 据此断言响应含 `*`。

### 5.2 级联软删除

`deletePhoto(userId, photoId)` 与 `deleteAnchor(userId, anchorId)` 先做归属校验：`photos.user_id = userId` / `identity_anchors.user_id = userId`，否则 `404 NOT_FOUND`（不返回 403，`spec/03-接口契约.md` §5 `API-04`）。级联解析顺序：目标 → 受影响锚点 → 受影响 generations → 受影响 generated 照片，然后**单个 `db.transaction()`** 内批量执行 §3.4 的语句并写审计。

**`DELETE /api/photos/:id` 级联规则表**（按目标照片的 `kind`）：

| 目标 `kind` | `photos` 被 UPDATE `deleted_at` 的行 | `identity_anchors` | `generations` | `generation_results` | `consents` |
|---|---|---|---|---|---|
| `original` | 该行 + `source_photo_id = :id AND kind='preprocessed'` 的派生图 + 受影响 generations 下 `generation_results.photo_id` 指向的 `kind='generated'` 图 | 物理 DELETE：`preprocessed_photo_id = :id` **或** `json_each(input_photo_ids)` 含 `:id` 的锚点 | 物理 DELETE：`anchor_id IN (受影响锚点)` | 保留（`runPurge()` 按 `photo_id` 清理） | UPDATE `revoked_at`：`anchor_id IN (受影响锚点) AND revoked_at IS NULL` |
| `preprocessed` | 该行 + 受影响 generations 下的 generated 图（其 `source_photo_id` 指向的 original **不动**） | 物理 DELETE：仅 `preprocessed_photo_id = :id` 的锚点 | 同上 | 同上 | 同上 |
| `generated` | 该行（不含其他） | 不动 | 不动 | 保留 | 不动 |

**`DELETE /api/anchors/:id` 级联规则表**：

| 表 | 操作 | 条件 |
|---|---|---|
| `identity_anchors` | 物理 DELETE | `id = :id AND user_id = :userId`（仅该行） |
| `generations` | 物理 DELETE | `anchor_id = :id AND user_id = :userId` |
| `photos` | UPDATE `deleted_at` | 上述 generations 的 `generation_results.photo_id` 指向的 `kind='generated'` 图 |
| `generation_results` | 保留 | 由 `runPurge()` 清理 |
| `consents` | UPDATE `revoked_at` | `anchor_id = :id AND revoked_at IS NULL` |

关键语义：**删除锚点不删除原图与预处理图**；**删除生成图不影响其 `generations` 行与锚点**。

**为什么 `identity_anchors` / `generations` 是物理 DELETE**：两张表无 `deleted_at` 列（`spec/02-schema.sql`、`spec/01-领域模型与数据库.md` §3.5 / §3.9），而 `anchor_text` / `prompt` 含人物面部特征描述，走软删除会在「彻底删除」后长期留存，故在同一事务内物理删除；`photos` / `consents` 有标记列，走软删除与吊销。

**响应计数**：`cascaded.preprocessed` = 被标记的 `kind='preprocessed'` 行数；`cascaded.anchors` = 被物理删除的锚点数；`cascaded.generations` = 被物理删除的 generations 数；`cascaded.results` = 这些 generations 名下 `generation_results` 的行数（删除前记数）。键名与 `spec/03-接口契约.md` §3.2 / §3.3 完全一致，**不新增键**。

**幂等**：目标行存在且 `deleted_at` 非空（照片）或已被物理删除的链路上重复调用 → 返回 `200 { ok: true, cascaded: 全零 }`；目标行完全不存在（已被 `runPurge()` 清理）或属于其他用户 → `404 NOT_FOUND`。

### 5.3 物理清理

```ts
// src/jobs/handlers/purge.ts
export const PURGE_INTERVAL_MS = 10 * 60 * 1000;   // worker 触发间隔
export const PURGE_GRACE_MINUTES = 10;             // deleted_at 早于该阈值才可清理
export const PURGE_BATCH_SIZE = 200;
export interface PurgeResult { scanned: number; purged: number; failed: number; deletedResults: number }
export async function runPurge(now?: string): Promise<PurgeResult>;
```

`runPurge()` 单批流程：

1. 按 §3.4 的扫描 SQL 取 `deleted_at < now - PURGE_GRACE_MINUTES` 的照片（`now` 缺省用 `nowIso()`）。
2. 逐行 `getStorage().delete(storage_key)`；文件不存在视为成功（幂等，记 `logger.warn`）；单行删除失败记 `failed` 并**跳过该行**（保留 `photos` 行，下轮重试），不整批失败。
3. 单个 `db.transaction()`：`DELETE FROM generation_results WHERE photo_id IN (:batchIds)`；`DELETE FROM photos WHERE id IN (:batchIds)`；逐行 INSERT `audit_logs(action='photo.purge', user_id, target = 'photo:' + id, meta_json = { bytes, storageKey })`。
4. 若 `scanned === PURGE_BATCH_SIZE`，立即再跑一批，直到不足一批。

**触发方式**（`src/jobs/worker.ts`）：`purge` **不进入任务表**（`spec/04-技术基线与目录结构.md` §4.6 的任务来源只有 `identity_anchors(status='queued')` 与 `generations(status='queued')`），由 worker 主循环定时调用：

- worker 启动时先执行一次 `recoverStale()` 回收（见 `spec/03-接口契约.md` §2.2），随后立即 `runPurge()`；
- 主循环每轮（无任务时等待 ≤1s）检查 `Date.now() - lastPurgeAt >= PURGE_INTERVAL_MS`，且当前无 `running` 任务时执行；
- `runPurge()` 的异常必须被捕获并记日志，**绝不中断 worker**；
- `src/jobs/registry.ts` 中不注册 `purge` 类型（它不是可领取任务）。

`spec/07-验收标准.md` 的 `DEL-03` 由 `scripts/acceptance.ts` 直接 `import { runPurge }` 后调用一次实现"手动触发"，**不新增 `pnpm` 脚本**。

**照片生命周期**：

```
active (deleted_at IS NULL)
  │ DELETE /api/photos/:id  →  deleted_at = now（立即从 /api/history、/api/photos/:id/file 消失）
  │                            audit: photo.delete
  ▼
soft-deleted
  │ runPurge()：deleted_at < now - 10min  →  删磁盘文件 → 删 generation_results → 物理 DELETE photos 行
  │                                          audit: photo.purge
  ▼
purged（行不存在；重复 DELETE 返回 404）
```

## 6. 边界与错误

| 错误码 | 触发条件 | 用户可见文案 |
|---|---|---|
| `UNAUTHENTICATED` | cookie 缺失/格式非法、`sessions` 无活跃行、`expires_at` 已过、`revoked_at` 非空、`users.status=0` | 请先登录 |
| `NOT_FOUND` | `DELETE /api/photos/:id` / `DELETE /api/anchors/:id` 目标不存在（含已被 `runPurge()` 清理）或属于其他用户；`GET /api/photos/:id/file` 命中软删除行 | 这张照片找不到了 |
| `INVALID_PARAM` | `identifier` 归一化失败；`cursor` 非法或 base64 解码后不匹配 `^\d{4}-\d{2}-\d{2}T.*\|\d+$`；`limit` 不在 `[1,50]` | 选择有误，请重新选一下 |
| `CODE_INVALID` | 无 `login_codes` 行、`consumed_at` 非空、或码值与记录不符（非 console 万能码） | 验证码不对，再试一次 |
| `CODE_EXPIRED` | 记录存在且未消费，但 `expires_at < now` | 验证码过期了，重新获取一个 |
| `CODE_RATE_LIMITED` | 同 `identifier` 60 秒内已有 `consumed_at IS NULL` 的记录 | 刚刚已经发过了，稍等一下 |
| `INTERNAL` | `SMS_PROVIDER=real`（本期无真实通道）；`assertDevCodeAllowed` 断言失败 | 出了点小问题，请重试 |

边界细节：

- 校验顺序固定为「存在/已消费 → 过期 → 码值」，避免用过期状态探测码值；
- 归一化后的 `identifier` 才写库与查库，`users.phone` 恒为 11 位纯数字，`users.email` 恒为小写，因此 `API-05` 的脱敏断言不受输入大小写影响；
- 历史游标是**不透明串**：`base64url(createdAt + '|' + id)`，前端只回传不解析（`spec/03-接口契约.md` §6.4）；
- `GET /api/history` 中只要某锚点的原图全部软删除，该锚点就不出现（§3.4 的 `EXISTS` 子句），这是 `DEL-01` 的直接实现；
- 照片清理失败只影响该行，`photos.deleted_at` 保持原值，下一轮继续尝试。

## 9. 非目标与待定决策

**待定决策**（均为最小实现选择，`spec/`、`modules/`、`pages/` 各文档均未冻结）：

1. `identity_anchors` / `generations` 无 `deleted_at` 列，本文件选择物理 DELETE（§5.2）。若将来需要「回收站」或审计追溯，需先加列，届时 `DELETE` 语义要重定。
2. `PURGE_INTERVAL_MS` / `PURGE_GRACE_MINUTES` / `PURGE_BATCH_SIZE` 目前是模块常量。若需按环境调整，必须先同步 `spec/08-本地开发指南.md` §4 再使用。
3. `runPurge()` 后照片行消失，重复 `DELETE` 返回 `404`，与 `spec/03-接口契约.md` §1.5「重复删除返回 200」存在张力——契约的 200 承诺只覆盖软删除阶段。若要求全程幂等，需要「删除墓碑」表或保留照片行。
4. cookie 未设 `Secure`（本地 http）。生产部署需加 `Secure` 并复核 `SameSite=Lax` 是否满足分享场景。
5. 过期/吊销的 `sessions` 行不做定时清理，只靠查询条件排除；长期运行会累积。
6. `SMS_PROVIDER=real` 无实现，届时抛 `INTERNAL`。真实通道接入后需定义发送失败的错误码（当前错误码表无对应项）。
7. 手机号统一归一为 11 位本地格式，未采用 `users.phone` 允许的 E.164 形式；跨区号/国际号码本期不支持。
8. 账号相关 route handler 直接调用 `src/server/auth/session.ts`，而 `spec/04-技术基线与目录结构.md` §3.1 要求非例外端点必须经过 `domain/*Service`。`auth/` 已在 `spec/04-技术基线与目录结构.md` §3.2 的模块表中归属 `tickets/T12`，本文件不为它新增 `domain/accountService.ts`；若后续要严格分层，需在该 §3.1 的例外清单中把 `auth/` 列入。
9. `generation_results` 在软删除阶段保留，因此 `GET /api/generations/:id` 的 `results` 数组也**必须**按 `photos.deleted_at IS NULL` 过滤，否则会返回 404 图片链接。该过滤属 `tickets/T10` / `tickets/T11` 的跨模块不变式，尚未在 `modules/M06-生成编排.md` 写明。
10. `GET /api/history` 只返回 `status='succeeded'` 的锚点（因 `HistoryItem.anchorText` 不可空）；失败锚点是否有历史展示需求未定。
