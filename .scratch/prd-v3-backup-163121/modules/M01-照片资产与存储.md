# M01 · 照片资产与存储

> **层级**：实现规格层 · 后端模块
> **上游**：`docs/raw/AIGC_PRD.md` §104、§129、§706、§713 ／ `spec/00-总纲.md`、`spec/01-领域模型与数据库.md`、`spec/03-接口契约.md`
> **下游**：`modules/M02-预处理与质量评分.md`、`modules/M06-生成编排.md`、`modules/M07-生成后复核与内容审核.md`、`modules/M08-账号历史与彻底删除.md`、`tickets/T03`

> 一句话职责：把用户上传的旧照片安全落到本地磁盘并写进 `photos` 表，再以「只属于当前用户」的方式把它读回来。

---

## 1. 职责与边界

### 1.1 做什么

1. 定义 `StorageProvider` 抽象与唯一实现 `LocalStorageProvider`（内容以文件存在本地目录，`photos.storage_key` 存相对路径）；
2. 实现 `POST /api/photos`：multipart 解析、mime 白名单、大小上限、sha256 内容去重、宽高探测、落盘 + 落库 + 审核/审计三写；
3. 实现 `GET /api/photos/:id/file`：归属与软删除校验、`?w=` 缩放、AIGC 标识响应头、缓存头；
4. 实现 `DELETE /api/photos/:id`：只做**软删除标记**，级联规则委托给 `domain/deletionService`（见 `modules/M08-账号历史与彻底删除.md` §4–6）；
5. 提供 `photos` 表的 repository 函数（字段以 `spec/01-领域模型与数据库.md` §3.4 为准）。

### 1.2 明确不做什么

| 不做 | 落在哪 |
|---|---|
| 归一化、方向校正、EXIF 剥离、质量评分 | `modules/M02-预处理与质量评分.md`（`src/server/images/`） |
| 物理删除磁盘文件与行 | purge worker（`src/jobs/handlers/purge.ts`，见 `modules/M08-账号历史与彻底删除.md`） |
| 隐式标识写入（AIGC 元数据） | `src/server/images/mark.ts`（见 `spec/06-合规与风控.md`） |
| 对象存储 / CDN / 公网 URL | `spec/00-总纲.md` §6.2；契约里不存在任何外部图片地址 |
| 从上游签名 URL 下载图片并转存 | `modules/M06-生成编排.md` §5（生成结果的转存走同一套 `StorageProvider`，但入口不同） |
| 上传阶段的图像内容审核模型调用 | 本模块只**写** `content_reviews(stage='upload')` 一行；判定规则见 `modules/M07-生成后复核与内容审核.md` |
| 缩略图预生成/缓存目录 | `?w=` 每次实时缩放，不落旁路文件 |

## 3. 数据读写

### 3.1 `photos`（读写）

字段以 `spec/01-领域模型与数据库.md` §3.4 为准。上传写入：

| 字段 | 写入值 |
|---|---|
| `user_id` | `requireUser()` 得到的 `userId` |
| `kind` | 固定 `'original'`（本模块只产 `original`；`preprocessed` 由 `modules/M02-预处理与质量评分.md`、`generated` 由 `modules/M06-生成编排.md` 产生） |
| `storage_key` | `buildKey(userId, ext)` → `u{userId}/{uuid}.{ext}`，**相对路径**，绝不存 URL |
| `mime` | 规范化后的四选一：`image/jpeg` / `image/png` / `image/webp` / `image/heic` |
| `bytes` | `Buffer.byteLength(buffer)` |
| `width` / `height` | `probeImage()` 结果，探测失败写 `NULL` |
| `sha256` | 文件字节的 sha256（小写十六进制），用于同用户内去重 |
| `source_photo_id` | `NULL`（`original` 无来源） |
| `quality_json` | `NULL`（仅 `preprocessed` 写） |
| `deleted_at` | `NULL` |
| `created_at` | `nowIso()`（UTC ISO-8601，见 `spec/04-技术基线与目录结构.md` §4.2） |

读：`GET /api/photos/:id/file` 只读单行；`DELETE` 写 `deleted_at`。

查询模式（对应 `spec/02-schema.sql` 索引）：

| 查询 | 走哪个索引 |
|---|---|
| `WHERE user_id = ? AND sha256 = ? AND kind = 'original' AND deleted_at IS NULL` | `idx_photos_sha256` + `idx_photos_user_created` |
| `WHERE id = ? AND user_id = ? AND deleted_at IS NULL` | 主键 |
| `WHERE source_photo_id = ? AND deleted_at IS NULL` | 无专用索引，数据量小可接受（见 §10.2 待定决策 2） |

### 3.2 `content_reviews`（写）

一次成功的上传（含命中去重复用）写**恰好一行**：

```sql
INSERT INTO content_reviews (user_id, stage, target_type, target_id, verdict, reason, model, created_at)
VALUES (?, 'upload', 'photo', ?, ?, ?, ?, ?);
```

- `verdict ∈ {'pass','reject','review'}`；上传阶段 MVP 默认 `'pass'`，`reason` / `model` 可为 `NULL`（`model` 仅在调用模型审核时写）；
- `target_type` 固定 `'photo'`，`target_id` = `photos.id`（去重命中时写**被复用的那一行**的 id）。

### 3.3 `audit_logs`（写）

```sql
INSERT INTO audit_logs (user_id, action, target, meta_json, created_at)
VALUES (?, 'photo.upload', 'photo:' || ?, ?, ?);
```

`meta_json` 固定形状：`{ "mime": string, "bytes": number, "sha256": string, "deduped": boolean }`。
`DELETE /api/photos/:id` 的 `action='photo.delete'` 由 `deletionService` 写（见 `modules/M08-账号历史与彻底删除.md`）。

### 3.4 事务边界

`spec/04-技术基线与目录结构.md` §4.3 要求所有写操作包在事务里。上传是**先写磁盘、后写事务**：校验 → 读 buffer → sha256 → 查去重（命中即返回已有行）→ 落盘（`storage.save`，原子 rename）→ 单事务内 `INSERT photos` → `INSERT content_reviews` → `INSERT audit_logs`；事务失败则 `storage.delete(key)` 回滚磁盘并抛 `STORAGE_ERROR`（完整流程见 §6.1）。

去重命中时**不落盘、不新增行**，但仍在同一个事务里补写一行 `content_reviews` 与一条 `audit_logs`（`deduped: true`），保证"每次上传都有审计"。

### 4.1 `StorageProvider` 接口（`src/server/storage/types.ts`）

```ts
import type { Iso } from '@/shared/types';

export type StorageKey = string;                 // 形如 'u12/3f9a2c1e-....jpg'，相对存储根
export type ImageExt = 'jpg' | 'png' | 'webp' | 'heic';

export interface SaveResult {
  key: StorageKey;
  bytes: number;
}

export interface StoredStat {
  key: StorageKey;
  bytes: number;
  modifiedAt: Iso;                               // 文件 mtime，UTC ISO-8601
}

export interface StorageProvider {
  /** 原子写：先写同目录 `<key>.<uuid>.tmp`，fsync 后 rename 覆盖目标 */
  save(key: StorageKey, data: Buffer): Promise<SaveResult>;
  /** 读全文；key 不存在抛 AppError(NOT_FOUND)；其他 IO 错误抛 AppError(STORAGE_ERROR) */
  read(key: StorageKey): Promise<Buffer>;
  /** 删除；不存在返回 false（幂等），不抛错 */
  delete(key: StorageKey): Promise<boolean>;
  exists(key: StorageKey): Promise<boolean>;
  /** 不存在返回 null，不抛错 */
  stat(key: StorageKey): Promise<StoredStat | null>;
  /** 相对 key → 绝对路径；只做纯函数换算与安全校验，不触盘 */
  resolveAbs(key: StorageKey): string;
}
```

`src/server/storage/index.ts`：

```ts
export function buildKey(userId: number, ext: ImageExt): StorageKey;  // `u${userId}/${randomUUID()}.${ext}`
export function getStorage(): StorageProvider;                        // 进程内单例，当前恒为 LocalStorageProvider
```

### 4.2 `LocalStorageProvider` 实现要点（`src/server/storage/local.ts`）

1. **根目录**：`path.resolve(process.env.STORAGE_DIR ?? './storage')`，首次使用时 `mkdir(root, { recursive: true })`。
2. **key 生成**：调用方只允许用 `buildKey(userId, ext)`；`u{userId}/` 即按用户分片的目录，purge 时按目录删除。
3. **path traversal 防护**（每个方法入口第一行执行 `assertSafeKey(key)`）：
   - key 必须匹配 `/^u[1-9]\d*\/[A-Za-z0-9._-]+$/`；
   - 显式拒绝：包含 `..`、包含 `\` 或 `:`（Windows 盘符/ADS）、以 `/` 开头、`path.isAbsolute(key)` 为真；
   - `resolveAbs` 内二次确认：`const abs = path.resolve(root, key)`，若 `abs !== root && !abs.startsWith(root + path.sep)` 则抛 `AppError('STORAGE_ERROR', '保存失败，请重试', 500)`；
   - 违反任一条 → 抛 `AppError('STORAGE_ERROR', ...)`，**不**回落到"就近目录"，避免竞态下写错位置。
4. **原子写**：`tmp = abs + '.' + randomUUID() + '.tmp'`（与目标同目录，保证同文件系统 rename 原子）；`fs.writeFile(tmp, data)` → `fs.rename(tmp, abs)`；任一步失败 `unlink(tmp)` 后抛 `STORAGE_ERROR`。成功后 `save` 再 `stat` 一次，用**实际落盘字节数**返回 `bytes`（与 `photos.bytes` 的一致性由调用方断言）。
5. **错误映射**：`ENOENT` → `AppError('NOT_FOUND', '这张照片找不到了', 404)`；`EACCES` / `ENOSPC` / `EISDIR` / 其他 → `AppError('STORAGE_ERROR', '保存失败，请重试', 500)`。映射后日志保留原始 errno，但绝不进用户可见文案。
6. `resolveAbs` 只做换算、不做 IO：`GET /api/photos/:id/file` 不需要它，它只服务于 purge worker 的日志与运维排查。

## 6. 关键流程与状态机

### 6.1 `POST /api/photos`

```
requireUser() ──失败──▶ 401 UNAUTHENTICATED
   │
   ├─ await req.formData()；取字段 'file'（必须存在且为 File）  缺失 → 400 INVALID_PARAM
   ├─ file.size > MAX_UPLOAD_MB * 1024 * 1024                  → 413 FILE_TOO_LARGE
   ├─ file.type ∈ {image/jpeg, image/png, image/webp, image/heic} → 否则 400 INVALID_FILE_TYPE
   ├─ buffer = Buffer.from(await file.arrayBuffer())；再查一次长度（防 size 不可信）→ 超限同上
   ├─ sha256 = createHash('sha256').update(buffer).digest('hex')
   ├─ dedup = findActiveOriginalBySha256(userId, sha256)
   │     命中 → 事务：content_reviews(pass) + audit_logs{depuped:true} → 201 返回已有行
   └─ 未命中
         ├─ ext = MIME_EXT[file.type]（jpeg→jpg, png→png, webp→webp, heic→heic）
         ├─ key = buildKey(userId, ext)；storage.save(key, buffer)
         ├─ { width, height } = await probeImage(buffer)     探测失败 → 均为 NULL，不阻断上传
         ├─ 事务：insertPhoto → content_reviews(stage='upload') → audit_logs{'photo.upload'}
         └─ 201 { photo: { id, kind:'original', url, mime, bytes, width, height, sha256, createdAt } }
```

`kind` 恒为 `'original'`：`preprocessed` 只能由 `POST /api/photos/:id/preprocess` 产生（`modules/M02-预处理与质量评分.md`），本端点**不得**接受 `kind` 参数。

### 6.2 `GET /api/photos/:id/file`

```
requireUser() ──▶ 401
photo = findActivePhotoForUser(id, userId) —— 不属于当前用户 或 已软删除 或 不存在 → 404 NOT_FOUND
   （三种情况共用同一个 404，不回 403：对齐 API-04 的反探测要求）
buffer = storage.read(photo.storageKey) —— 文件缺失 → 404 NOT_FOUND（行与盘不一致）
w 未传：Content-Type = photos.mime；body = buffer 原样
w 已传：w 解析为整数且 ∈ [16, 2048]，否则 400 INVALID_PARAM
        buffer = await sharp(buffer).resize({ width: w, withoutEnlargement: true }).jpeg({ quality: 80 }).toBuffer()
        Content-Type = 'image/jpeg'
公共响应头：Cache-Control: private, max-age=3600
           Content-Length: <最终字节数>
           X-AIGC-Generated: true    ← 仅当 photo.kind === 'generated' 时附加；其余 kind 不带该头
```

- `withoutEnlargement: true`：小图请求大 `w` 时**不放大**（`spec/00-总纲.md` §4 红线，不做超分）；
- `kind='generated'` 的隐式标识元数据由生成侧写入（`src/server/images/mark.ts`），本端点只负责这个显式响应头；
- 路由文件需声明 `export const runtime = 'nodejs'` 与 `export const dynamic = 'force-dynamic'`（二进制响应不参与静态化）。

### 6.3 `DELETE /api/photos/:id`

```
requireUser() ──▶ 401
deletionService.deletePhoto({ photoId: id, userId })   ← 归属校验 + 级联软删除，细节见 modules/M08-账号历史与彻底删除.md §4
   ├─ 不属于当前用户 → 404 NOT_FOUND
   ├─ 已软删除 → 200（幂等，cascaded 计数为 0）
   └─ 首次删除 → 写 deleted_at + audit_logs('photo.delete')，返回级联计数
物理文件与行由 purge 任务延迟清理（`modules/M08-账号历史与彻底删除.md` §5），本模块的 handler 不做任何 unlink。
```

### 6.4 `photos` 生命周期（承接 `spec/01-领域模型与数据库.md` §2.3）

```
active ──DELETE /api/photos/:id──▶ soft-deleted（deleted_at 非空，立即从所有读取路径消失）
soft-deleted ──purge worker（deleted_at 早于 N 分钟）──▶ 磁盘文件删除 + 行物理删除
```

## 7. 边界与错误

| 错误码 | HTTP | 触发条件 | 用户可见文案 |
|---|---|---|---|
| `UNAUTHENTICATED` | 401 | 无会话或会话过期 | 请先登录 |
| `INVALID_PARAM` | 400 | multipart 里没有 `file` 字段 / 值不是文件 / `?w=` 不是 [16,2048] 的整数 | 选择有误，请重新选一下 |
| `INVALID_FILE_TYPE` | 400 | `file.type` 不在白名单；或 heic 在本机 `sharp` 无 heif 解码能力导致探测失败 | 暂时只支持 jpg、png、webp、heic |
| `FILE_TOO_LARGE` | 413 | 字节数 > `MAX_UPLOAD_MB` | 这张照片太大了，换一张小一点的 |
| `NOT_FOUND` | 404 | 照片不存在 / 属于他人 / 已软删除 / 行存在但磁盘文件缺失 | 这张照片找不到了 |
| `STORAGE_ERROR` | 500 | 落盘、rename、读取、路径校验失败（含 path traversal 被拒） | 保存失败，请重试 |
| `INTERNAL` | 500 | 兜底（`spec/04-技术基线与目录结构.md` §4.1） | 出了点小问题，请重试 |

**heic 的已知限制（必须显式暴露，不要静默降级）**：

- 白名单接受 `image/heic`，但 `sharp` 能否解码 heif 取决于本机 libvips 构建（`spec/08-本地开发指南.md` §8 已列为已知限制）；
- 探测/读取失败返回 `400 INVALID_FILE_TYPE`，**不做**"转成 jpg 再存"的兜底——那会篡改用户原始字节，违反 `spec/00-总纲.md` §1.3「保留唯一证据」的定位；
- `file.type` 为空字符串（部分客户端不发 Content-Type）时，**不**按扩展名猜测，直接 `INVALID_FILE_TYPE`。

## 10. 非目标与待定决策

### 10.1 非目标（本期不做）

1. 断点续传、分片上传、并发上传队列；
2. 图片格式转换（heic → jpg 的落盘转换）、上传时的尺寸归一（那是 `modules/M02-预处理与质量评分.md` 的职责）；
3. 内容审核模型调用（上传阶段只落 `content_reviews` 一行；判定策略见 `modules/M07-生成后复核与内容审核.md`）；
4. 磁盘用量配额与清理策略（`users.daily_image_quota` 只约束**生成**张数，不约束上传）；
5. `ETag` / `If-None-Match` / Range 请求（`spec/04-技术基线与目录结构.md` §5 未要求，前端也未用）。

### 10.2 待定决策

1. **去重的 `kind` 范围**：`spec/03-接口契约.md` §3.2 只写「同用户内 `sha256` 命中未删除行则直接返回已有行」，未限定 `kind`；本文件限定为 `kind='original'`，否则会把 `preprocessed` / `generated` 行的 `id` 当作新上传的原图返回，污染只接受 `original` 的 `POST /api/anchors`。需在 ticket 03 的 `## Comments` 里确认。
2. **`source_photo_id` 缺索引**：`spec/02-schema.sql` 只为 `photos` 建了 `(user_id, created_at DESC)`、`(sha256)`、`(deleted_at)` 三个索引，`findPreprocessedBySource` 走全表扫描。MVP 数据量下可接受，暂不加迁移；若 `modules/M02-预处理与质量评分.md` 要求索引，需新增 `002-*.sql`。
3. **上传阶段的审核判定**：本模块只固定 `content_reviews(stage='upload')` 的写入形状（`verdict='pass'` 默认），实际判定规则依赖 `modules/M07-生成后复核与内容审核.md`；届时若需要在上传同步调用审核模型，`POST /api/photos` 的耗时与失败语义（是否阻断上传）需重新定义。
4. **测试文件位置约定**：`spec/04-技术基线与目录结构.md` 未规定测试文件路径，本文件采用 co-located `*.test.ts`（vitest 默认 `include` 可匹配）；若 ticket 01 建立了独立 `tests/` 目录，需统一改名。
5. **环境变量读取位置**：`spec/04-技术基线与目录结构.md` 的目录结构里没有 `env.ts` / `config.ts`，本模块直接读 `process.env.STORAGE_DIR` 与 `process.env.MAX_UPLOAD_MB`；若 ticket 01 建立集中式 env 解析，应改为经该模块读取，并保留 `STORAGE_DIR` 默认值 `./storage` 的行为不变。
6. **`X-Content-Type-Options: nosniff`**：`spec/03-接口契约.md` 未要求该响应头，本文件不加，避免发明契约；可提出给 `spec/06-合规与风控.md` 作为增强项。
