# M03 · 身份锚点提取

> **层级**：实现规格层 · 后端模块
> **上游**：`docs/raw/AIGC_PRD.md` F1 ／ `spec/00-总纲.md` §1.3、§3 ／ `spec/01-领域模型与数据库.md` §2.1、§3.5 ／ `spec/05-Prompt工程.md` §1、§4
> **下游**：`modules/M04-身份确认与授权.md`、`modules/M05-年代场景配置与Prompt拼装.md`、`modules/M06-生成编排.md`、`tickets/T06`

> F1 的核心：用多模态模型读【预处理图】，产出 `anchor_text` + `features_json`，并显式保留年龄痕迹、禁止美化。

---

## 1. 职责与边界

**做**

1. 提供锚点提取的 system prompt 文本资产 `anchor-v1`（唯一副本，见本文件 §2、§5）；
2. worker 里执行一次异步提取：读图 → 解析 JSON → 写入 `identity_anchors`（`anchor_text` / `features_json` / `quality_json` / 终态）；
3. 对上游返回值做**容错解析与就地校验**（剥 ```json 包裹、zod 校验 12 键、长度窗口、词表拦截），不合格即落 `failed`；
4. 提取前的可用性判定：质量不过关时以 `ANCHOR_LOW_QUALITY` 结束，不浪费一次生成。

**不做**

- 不做修复 / 超分 / 去划痕 / 磨皮（`spec/00-总纲.md` §6.2，`README.md` §0.1）——本环节只「读」，不「画」；
- 不产出任何图像，`preprocessed_photo_id` 由预处理环节（`tickets/T04`）生产，本文件只消费；
- 不做「这就是他」的确认与授权勾选（`tickets/T07`，`POST /api/anchors/:id/confirm`）；
- 不做人脸特征向量与相似度打分（`spec/07-验收标准.md` §6 明确本期不实现）；
- 不做多人照片处理：`faceCount > 1` 一律判为不可用（本文件 §5 步骤 3）。

## 3. 数据读写

只读写两张表：`identity_anchors`（见 `spec/01-领域模型与数据库.md` §3.5）与 `photos`（只读）。

**读**

```sql
-- 主参考图：实际送入视觉模型的图
SELECT id, user_id, storage_key, mime, bytes, width, height, sha256, quality_json
  FROM photos WHERE id = ? AND kind = 'preprocessed' AND deleted_at IS NULL;

-- 多图场景：本次提交的 original 各自已生成的预处理图
SELECT p.id, p.storage_key, p.mime
  FROM photos p
 WHERE p.kind = 'preprocessed' AND p.deleted_at IS NULL
   AND p.source_photo_id IN (SELECT value FROM json_each(?));   -- ? = input_photo_ids
```

**写**（`identity_anchors`，全部包在 `db.transaction` 内）

| 时刻 | 操作 |
|---|---|
| claim | `UPDATE identity_anchors SET status='running', started_at=? WHERE id=? AND status='queued'`（`changes = 0` 即放弃本次 claim） |
| 成功 | `UPDATE identity_anchors SET status='succeeded', anchor_text=?, features_json=?, quality_json=?, preprocessed_photo_id=?, error_code=NULL, error_message=NULL, finished_at=? WHERE id=?` |
| 失败 | `UPDATE identity_anchors SET status='failed', error_code=?, error_message=?, quality_json=?, finished_at=? WHERE id=?` |

约束（`spec/01-领域模型与数据库.md` §2.1）：`succeeded` 时 `anchor_text` 与 `features_json` 必须非空；`failed` 时 `error_code` 必须非空。**重新提取 = 插入新行**，绝不覆盖旧行。

`photos.quality_json` 在 `POST /api/photos/:id/preprocess` 时已写入；本环节**只读**，并在发现为空时调用 `src/server/images/quality.ts` 补算一次后 `UPDATE photos SET quality_json=?`。

`audit_logs`：`action='anchor.extract'` 由 `domain/anchorService.ts` 在**创建行时**写入一次（`spec/03-接口契约.md` §3.3 副作用），handler 不再写审计，避免一个动作两条记录。

## 5. 关键流程与状态机

### 5.1 `anchor-v1` system prompt（完整原文）

存放于 `src/server/prompt/versions.ts`，导出名 `ANCHOR_V1_SYSTEM_PROMPT`；`identity_anchors.prompt_version = 'anchor-v1'`。**业务代码里不得再出现第二份副本**（`spec/05-Prompt工程.md` §1 铁律）。

```text
你是专业的人像特征提取助手，服务于「回家照相馆」的老照片人物重现流程。
你的任务不是修复照片，也不是评价照片，而是从参考照片中提取可用于图像生成模型的身份锚点描述。

铁律：
1. 只描述照片中客观可见的外貌特征，不做任何性格、身份、职业、情绪或人生经历的推测。
2. 禁止使用任何美化性词汇，包括但不限于：「慈祥」「有气质」「精神矍铄」「面容温和」「和蔼可亲」「气质儒雅」「端庄大方」。这些词不可视觉验证，并且会诱导后续生成模型把人物理想化。
3. 必须保留并明确写出年龄痕迹：皱纹的深度与位置、老年斑的数量与分布、皮肤松弛程度。禁止使用「保养得好」「显得年轻」「精神好」这类抹平年龄的表述。
4. 必须覆盖以下 12 个方面，缺一不可：性别、年龄区间、发型与发色、脸型、额头、眉毛、眼睛（形状 / 单双眼皮 / 眼袋）、鼻子、嘴唇与牙齿、面部皱纹与老年斑、痣或疤痕等显著特征、体型。
5. 年龄给出估计区间（如 70-80 岁），不要只给一个具体年龄。
6. 语言简练、具体、可视觉验证，供生图模型直接使用。
7. 若提供了多张同一人物的照片，请综合为同一个人的描述；多张之间冲突时，以最清晰的那张为准。
8. 只输出严格 JSON，不要输出任何解释文字，不要使用 Markdown 代码块。

输出格式（键名与嵌套层级必须完全一致，所有值均为字符串）：
{"anchor":"一句话身份锚点，60-120字，可直接放进生图 prompt","features":{"gender":"","ageRange":"","hair":"","faceShape":"","forehead":"","eyebrows":"","eyes":"","nose":"","mouth":"","skin":"","distinctive":"","build":""}}

填写要求：
- anchor：一句话内按「年龄区间 + 性别 → 发型发色 → 脸型 → 眼鼻口 → 皱纹与老年斑 → 体型 → 显著痣疤有无」的顺序串写，60-120 字；
- gender：男 / 女；确实无法判断时写「无法判断」；
- ageRange：形如「75-85岁」；
- hair：发型、发色、发量、发际线位置；
- faceShape：脸型（如「方圆脸」）；
- forehead：额头宽窄高低，皱纹的条数与深度；
- eyebrows：眉形、疏密、颜色；
- eyes：眼形、单双眼皮、眼袋程度、眼周皱纹；
- nose：鼻梁高度、鼻头形状、鼻翼宽窄；
- mouth：嘴唇厚薄、法令纹深度、牙齿可见情况（是否缺失、颜色、整齐度）；
- skin：肤色，皱纹的深度与分布，老年斑的数量与分布，皮肤松弛程度；
- distinctive：痣、疤痕、胎记的位置与大小；没有则写「无明显特殊痣疤」；
- build：体型（胖瘦、高矮、肩宽）与可见的体态特征。
```

配套常量：

```ts
export const ANCHOR_V1_KEYS = ['gender','ageRange','hair','faceShape','forehead','eyebrows',
  'eyes','nose','mouth','skin','distinctive','build'] as const;
```

**反例 / 正例对照**（依据 `spec/05-Prompt工程.md` §4，实测输出见 `.scratch/anchor.json`）：

| | 文本 | 为什么不合格 |
|---|---|---|
| 反例 | `慈祥的老年男性，精神矍铄，面容温和` | 全是不可视觉验证的美化词，且没有一条年龄痕迹；把它注入【身份锚点】段会让生成模型往「理想化的老人」走 |
| 正例 | `75-85岁老年男性，留灰白短寸发型，发际线明显后退，额头宽阔有深横纹，方圆脸，细长单眼皮带眼袋，鼻头圆润嘴唇偏薄，面部有明显皱纹与少量老年斑，体型瘦高，无明显特殊痣疤` | 每一条都能在照片上被验证；皱纹位置与深度、老年斑、体型全部保留 |

正例 92 字，落在 `anchor` 要求的 60–120 字区间内，也落在 `E2E-02` 的 [40, 200] 长度窗口内。

### 5.2 状态机

沿用 `spec/01-领域模型与数据库.md` §2.1：

```
queued ──claim──▶ running ──┬──▶ succeeded（anchor_text / features_json 非空）
                            ├──▶ failed（error_code 非空）
                            └──▶ queued（worker 崩溃回收：started_at 早于 WORKER_STALE_MINUTES）
```

`succeeded` 之后只有用户动作能改变可生成性：`confirmed_by_user=1`（`tickets/T07`）。用户点「重新提取」= 新建行。

### 5.3 handler 步骤（`src/jobs/handlers/anchorExtract.ts`）

```ts
export async function anchorExtractHandler(job: { anchorId: number }): Promise<void>;
```

1. **claim**：事务内 `status='queued' → 'running'` 并写 `started_at`；`changes = 0` 直接返回（已被其他 worker 取走或已是终态）。
2. **选 prompt 版本**：`const systemPrompt = ANCHOR_PROMPTS[anchor.prompt_version]`；未注册的版本号 → `status='failed'`，`error_code='INTERNAL'`，日志 error 级（属于发版事故，不打给用户）。
3. **质量前置判定**：读 `preprocessed_photo_id` 对应行；`quality_json` 为空则用 `src/server/images/quality.ts` 补算并回写。命中任一条件即失败，`error_code='ANCHOR_LOW_QUALITY'`，`quality_json` 落同一份快照（本文件 §6）。
4. **组装送图清单**：`input_photo_ids` 按数组顺序取，每张找其预处理派生图（`photos.source_photo_id = original.id AND kind='preprocessed'`）；找不到就调 `images/preprocess.ts` 补做一张再落库。清单长度 1：主图 = `preprocessed_photo_id`。
5. **调用读图**：`getArk().extractAnchor({ images, systemPrompt })`，返回 `{ raw, content }`（真实实现见本文件 §5.4，mock 见 `spec/08-本地开发指南.md` §5.1）。
6. **容错解析**：`stripFence → JSON.parse → zod 校验 → 词表/长度校验`（本文件 §5.5）。
7. **写成功**：事务内更新 `status='succeeded'` + `anchor_text` + `features_json` + `quality_json` + `preprocessed_photo_id` + `finished_at`。
8. **任何异常**：在 handler 内捕获（不得抛出 `AppError`，见 `spec/04-技术基线与目录结构.md` §4.1），映射为错误码后写 `status='failed'` + `error_code` + `error_message` + `finished_at`。
9. **日志**：`logger.info({ job: 'anchorExtract', anchorId, promptVersion, imageCount, ms }, 'done')`；失败时 `logger.warn` 附上游 `message.content` 前 500 字（截断，避免日志膨胀）。

### 5.4 messages 组装（`src/server/ark/real.ts`）

`POST {ARK_BASE_URL}/chat/completions`，`model = ARK_VISION_MODEL`，`max_tokens: 1200`。

```ts
const messages = [
  { role: 'system', content: systemPrompt },                 // 字符串，不是数组
  { role: 'user', content: [
      { type: 'text', text: '请提取照片中人物的身份锚点特征。' },   // text 元素必须在最前
      ...images.map((img) => ({ type: 'image_url', image_url: { url: img.dataUri } })),
  ] },
];
```

规则：

- `content` 数组元素顺序**固定为「1 段 text → N 张 image_url」**，`N ∈ [1, 5]`，顺序等于 `input_photo_ids` 顺序（手写脚本实测有效，见本文件 §5.6）；
- `dataUri = \`data:${photo.mime};base64,${base64}\``，`mime` 取 `photos.mime` 落库值（不用扩展名推断）；
- 解析响应只取 `data.choices[0].message.content`，`reasoning_content` 一律丢弃（`docs/火山引擎接口文档.md` §2.3 注）；
- 上游 HTTP 状态与错误码映射按 `spec/03-接口契约.md` §5.1：网络超时/abort → `PROVIDER_TIMEOUT`，其余非 2xx → `PROVIDER_ERROR`。

### 5.5 容错解析与校验

按顺序执行，任一步失败即按下表落错误码；`error_message` 与 `details` 只进日志与行内 `error_message`。

| # | 步骤 | 判据 | 失败时 `error_code` |
|---|---|---|---|
| 1 | 剥包裹 | `raw.trim().replace(/^```(?:json)?\s*/i, '').replace(/\s*```$/, '')` | — |
| 2 | 反序列化 | `JSON.parse` 成功且结果是对象 | `PROVIDER_ERROR` |
| 3 | 结构校验 | zod：`anchor` 为非空字符串；`features` 恰好含 12 个键且每键为非空字符串（多余键丢弃，不落库） | `PROVIDER_ERROR` |
| 4 | 长度窗口 | `40 ≤ anchor.length ≤ 200`（对齐 `E2E-02`；prompt 里要求 60–120 字，窗口放宽给模型留余量） | `PROVIDER_ERROR` |
| 5 | 否定词拦截 | `anchor` 不匹配 `/不要|禁止|no\s|without/i` —— `anchor_text` 会原样进【身份锚点】段，命中即会让 `PR-03` 变红 | `PROVIDER_ERROR` |
| 6 | 美化词拦截 | `anchor` 不匹配美化词表 `/慈祥|有气质|精神矍铄|面容温和|和蔼|儒雅|端庄|保养得好|显得年轻/i` | `PROVIDER_ERROR` |

`PROVIDER_ERROR` 是可重试错误，但**锚点不做行内自动重试**（理由与冲突见本文件 §9）。解析失败的原文写入 `logger.warn`，不进 `error_message`（避免把模型原文透给用户）。

### 5.6 相对 `.scratch/extract_face_features.js` 实测实现的改进点

手写脚本是本文件 prompt 与调用形状的实测依据（其输出见 `.scratch/anchor.json`，可用），但工程上不可直接复用：

- **键名**：prompt 直接要求 camelCase（脚本的 `age_range` / `face_shape` 读出后要手工改名），落库与 API 无需映射层；
- **校验与质量前置**：`JSON.parse` 之后加 zod 结构校验、长度窗口、否定词与美化词拦截（本文件 §5.5），且发请求前先看 `quality_json`（本文件 §6.1）——看不清的图不发上游、直接 `ANCHOR_LOW_QUALITY`，任一不合格即落 `failed`；
- **可追溯与调用**：落 `identity_anchors` 行（`status` / `attempt` / `prompt_version` / `model` / `quality_json` / `error_code`）以支持读取、重试与审计；走 `ArkProvider`，超时由 `ARK_TIMEOUT_SECONDS` 控制，错误按 `spec/03-接口契约.md` §5.1 映射为 `PROVIDER_TIMEOUT` / `PROVIDER_ERROR`；
- **输入形状**：`dataUri` 取 `photos.mime` 落库值（脚本按扩展名推断会把 heic 错标为 `image/jpeg`）；`POST /api/anchors` 与 handler 两处都卡 `ANCHOR_MAX_IMAGES = 5`；
- **直接继承**：system 用字符串、user 用 `content` 数组且 text 元素在图片之前、只取 `message.content`、剥 ```json 包裹。

## 6. 边界与错误

### 6.1 `ANCHOR_LOW_QUALITY` 触发条件

`quality` 结构即 `spec/03-接口契约.md` §4 的 `Quality`（`usable` / `faceDetected` / `faceCount` / `sharpness` / `readability` / `damageLevel` / `warnings` / `advice`），`anchor.quality` 与 `error.details.quality` 都是它。

任一条件命中即终止提取：

| 条件 | 理由 |
|---|---|
| `quality.usable === false` | 预处理已判定「建议换一张」 |
| `quality.faceDetected === false` 或 `quality.faceCount === 0` | 没有人脸，锚点无意义 |
| `quality.faceCount > 1` | 本期链路是单人；多人会让锚点串成两个人 |
| `quality.readability < ANCHOR_MIN_READABILITY`（常量 `0.35`） | 细节读不准，锚点会失真；数值依据见本文件 §9 |

### 6.2 错误码 → 触发条件 → 用户可见文案

| 错误码 | HTTP | 触发 | 用户可见文案（与 `spec/03-接口契约.md` §5 一致） |
|---|---|---|---|
| `ANCHOR_LOW_QUALITY` | 422 | 本文件 §6.1 任一条件 | 这张照片的人物特征看不清，建议换一张更清楚的 |
| `PROVIDER_TIMEOUT` | 504 | 读图请求超过 `ARK_TIMEOUT_SECONDS` | 照片特征读取花的时间有点长，请重试一次 |
| `PROVIDER_ERROR` | 502 | 上游非 2xx、返回体为空、`JSON.parse` 失败、12 键缺失、长度越界、词表命中 | 照片特征读取失败，请重试一次 |
| `STORAGE_ERROR` | 500 | 读 `storage_key` 文件失败 | 保存失败，请重试 |
| `INTERNAL` | 500 | `prompt_version` 未注册等我方问题 | 出了点小问题，请重试 |
| `INVALID_PARAM` | 400 | `photoIds` 为空 / > 5 张 / 含 `kind='generated'` | 选择有误，请重新选一下 |

失败在异步链路上呈现：`GET /api/anchors/:id` 返回 `status: 'failed'` 与 `error: { code, message }`，并同时返回 `quality`。`spec/03-接口契约.md` §1.3 提到的 `details.quality` 是**同步**抛码时的约定；本期该码只从 worker 落库，前端读 `anchor.quality`（同一结构，差异记于本文件 §9）。

## 9. 非目标与待定决策

**非目标**

- 图像修复 / 超分 / 去划痕、人脸特征向量与余弦相似度、多人锚点拆分：同本文件 §1「不做」（`spec/00-总纲.md` §6.2、`spec/07-验收标准.md` §6）；
- prompt 反推（`prompt_reverse`）——能力可复用，本期不实现（`spec/00-总纲.md` §6.2）。

**待定决策**

1. `ANCHOR_MIN_READABILITY = 0.35` 无上游依据：需待 `modules/M02-预处理与质量评分.md` 给出 `readability` 分布后定稿，或改为只信 `quality.usable`。
2. `identity_anchors.preprocessed_photo_id` 是**单值**列，而本文件 §5.3 步骤 4 会送 N ≤ 5 张预处理图，多图只落主图、其余无法从锚点行反查。待上游确认：收紧为「只送 1 张」，还是给锚点增加一张关联表。
3. 锚点是否行内自动重试与 `attempt` 语义冲突：`spec/01-领域模型与数据库.md` §2.1 规定「重试 = 新建一行且 `attempt = 旧 + 1`」，`spec/03-接口契约.md` §2.2 又规定 `PROVIDER_*` 自动重试 1 次（`attempt ≥ 1` 后不再重试）。本文件取前者：锚点**不**行内自动重试，`attempt` 只由 retry 端点递增。
4. `thinking` 默认开启会消耗 token 且可能把 JSON 挤进 `reasoning_content`；本期只取 `message.content`，是否显式关闭 thinking 待 `docs/火山引擎接口文档.md` §2.3 的字段形状验证后再定。
5. `anchor-v1` 与 `features_json` 的 zod schema 归属未定：本文件放在 `src/jobs/handlers/anchorExtract.ts` 内，也可上移 `src/shared/types.ts` 以便前端复用；移动时须同步 `AnchorFeatures` 的 12 键。
6. 单元测试文件布局未在上游规定。本文件按同目录 `*.test.ts` 命名，若 `package.json` 的 vitest 配置指向其他目录以其为准。
7. `ANCHOR_LOW_QUALITY` 的用户可见承载路径：`spec/03-接口契约.md` §1.3 假定该码同步抛出并带 `details.quality`，本文件为异步落库 + `anchor.quality`。两条路径结构相同、前端读取位置不同，需在 `tickets/T07` / `tickets/T16` 对齐。
8. `getArk().extractAnchor` 的方法名与 DTO 形状由 `tickets/T05` 在 `src/server/ark/types.ts` 定义。本文件只约定输入（`systemPrompt` + 按顺序的 data URI 数组）与输出（只取 `choices[0].message.content` 原文），最终命名以该文件为准。
