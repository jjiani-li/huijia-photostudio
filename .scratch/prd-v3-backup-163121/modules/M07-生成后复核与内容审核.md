# M07 · 生成后复核与内容审核

> **层级**：实现规格层 · 后端模块
> **上游**：`docs/raw/AIGC_PRD.md` §4、§5.5、§6.2、§9 ／ `spec/00-总纲.md`、`spec/01-领域模型与数据库.md`、`spec/03-接口契约.md`、`spec/05-Prompt工程.md`
> **下游**：`tickets/T10`、`tickets/T11`、`pages/P01-页面规格.md`

> 生成图落地前，用多模态模型做两件事：年代穿帮复核（可缺，不阻断）+ 年龄偏差估计；内容安全审核（不可缺，reject 即终止）。

---

## 1. 职责与边界

### 1.1 做什么

| # | 职责 | 产物 |
|---|---|---|
| 1 | **年代穿帮复核**：读生成图，判定画面中是否出现**所选年代之后才存在**的物件 | `generation_results.era_check_json`（形状 = `spec/03-接口契约.md` §4 `EraCheck`） |
| 2 | **年龄偏差估计**：估计生成图人物年龄区间中值，与锚点 `features.ageRange` 中值相减 | `generation_results.age_delta`（**可为负**） |
| 3 | **内容安全审核（result 阶段）**：判定生成图是否含违规内容 | `content_reviews(stage='result')`；reject 时终止任务 |
| 4 | **内容安全审核（prompt 阶段）**：判定拼装后的 prompt 是否含经用户输入间接进入的违规内容 | `content_reviews(stage='prompt')`；reject 时拒绝入队 |
| 5 | 审核 reject 的审计留痕 | `audit_logs(action='moderation.reject')` |

### 1.2 明确不做什么

- ❌ **不阻断年代穿帮的交付**：verdict 为 `review` / `reject` 时不删图、不置任务失败，只在结果卡片上标注（见 §5.3）；
- ❌ **不实现自动人脸相似度打分**：`generation_results.realism_score` 本期恒为 `NULL`（见 §9）；
- ❌ **不做"年代主题 cosplay"判定**：年代刻板化属人工评审（`spec/07-验收标准.md` §4）；
- ❌ **不做人工审核后台**：`verdict='review'` 本期等同放行并留痕，无人工处置通道（`spec/00-总纲.md` §6.2）；
- ❌ **不重复实现 upload 阶段审核**：它落点在 `tickets/T03` 的上传路径，本文件只声明其判定口径与失败路径（§5.4）；
- ❌ 不新增 HTTP 端点、不新增数据库表/字段、不新增环境变量。

## 3. 数据读写

| 表 | 字段 | 操作 | 说明 |
|---|---|---|---|
| `generation_results` | `era_check_json` | INSERT/UPDATE | 复核成功才写；失败保持 `NULL` |
| `generation_results` | `age_delta` | INSERT/UPDATE | `估计中值 − 锚点中值`，整数，**可为负**；不可计算时 `NULL` |

| `scenes` | `name` | SELECT | 仅用于日志与 fixture 选择，不进复核 prompt |
| `photos` | `deleted_at` | UPDATE | result 阶段 reject 时软删本次已转存的 `kind='generated'` 图 |

SQL 片段（复核结果写入，`era_check_json` 与 `age_delta` 同事务）：

```sql
UPDATE generation_results
   SET era_check_json = @eraCheckJson,   -- JSON.stringify(EraCheck) 或 NULL
       age_delta      = @ageDelta        -- INTEGER 或 NULL
 WHERE generation_id = @generationId AND ordinal = @ordinal;
```

```sql
INSERT INTO content_reviews
  (user_id, stage, target_type, target_id, verdict, reason, model, created_at)
VALUES
  (@userId, 'result', 'generation', @generationId, 'reject', @reason, @model, @createdAt);
```

## 5. 关键流程与状态机

### 5.1 生成任务内的调用顺序

`src/jobs/handlers/generate.ts`，每个 `generations` 任务：

```
claim → 置 running
  → ArkProvider.generateImages（tickets/T10）
  → 对每个 ordinal i，按顺序：
      ① 转存为 photos(kind='generated')
      ② moderateResult()                ← 审核在前：它是硬闸门
           reject → 终止流程（见 5.5）
           pass / review → 写 content_reviews(stage='result')
      ③ eraReview()                     ← 复核在后：它是软标注
           成功 → 写 era_check_json + age_delta
           抛错（PROVIDER_TIMEOUT / PROVIDER_ERROR）→ 不写，warn 日志，继续
  → 全部候选处理完 → status = succeeded（全成功）/ partial（部分失败）
  → audit_logs(action='generation.finish')
```

**顺序理由**：审核失败要撤销本次全部产物，越早发现代价越小；复核失败只是少一个标注，不应占用撤销路径。

### 5.2 年代穿帮复核：提示词设计要点

prompt 常量由 `src/server/security/eraReview.ts` 唯一持有（handler 不得内联文本），版本常量 `ERA_CHECK_PROMPT_VERSION = 'era-check-v1'`。

输入：生成图（`image_url`）+ `eras.name`（如 `1980s-1990s` 对应的 `80-90年代`）+ `eras.constraint_pack` 原文（其语义已含"必须属于该年代或更早"）。

设计要求（逐条都要落到 prompt 文本里）：

1. **只报告"所选年代之后才存在的物件"**。更早的物件、跨年代中性的自然物（树木、天空、地面、水体）**一律不报**——这是复核的唯一定义。
2. **不报告画质类问题**：颗粒、色调、曝光、对焦、构图、表情、服装是否好看，都不属于年代穿帮。
3. **不报告人脸相似度、美化程度、AI 感**——那是别的判据，混进来会污染 `findings`。
4. `findings[].item` 是**单一物件名**（≤ 12 字，如 `智能手机`、`玻璃幕墙现代楼宇`）；`reason` 一句话说明"画面何处 + 为什么晚于所选年代"（≤ 40 字）。
5. **宁漏不误报**：看不清、不确定的一律不报（误报会让结果卡片出现无意义标注）。
6. `verdict` 判定口径必须在 prompt 里写死：`pass` = 未发现晚于年代的物件；`review` = 发现 1–2 个且位于非主体位置（远景、背景角落）；`reject` = 主体位置或 ≥ 3 处穿帮（如人物手持智能手机）。
7. `findings` **最多 5 条**，超出按严重度截断；无发现时必须是空数组，不得输出占位项。
8. 同时估计画面中人物的年龄区间，键名 `estimatedAgeRange`（如 `"70-78"`），区间宽度 ≤ 8 岁；无法判断时给 `null`。
9. **严格 JSON 输出，禁止 Markdown 代码块与解释文字**，形状固定为：

```json
{ "verdict": "pass | review | reject",
  "findings": [ { "item": "智能手机", "reason": "人物右手持黑色全面屏手机，1990 年代不存在该物件" } ],
  "estimatedAgeRange": "70-78" }
```

代码侧的**收敛规则**（模型输出不可直接信任，必须在 `eraReview.ts` 里归一）：

```ts
// 1) verdict 非枚举值或缺失 → 按 findings 推导：空→'pass'，非空→'review'
// 2) verdict === 'pass' 但 findings.length > 0 → 提升为 'review'（一致性修正）
// 3) findings 超过 5 条 → 截断；item/reason 非字符串的条目丢弃
// 4) 落库投影严格只保留 EraCheck 的 4 个键；estimatedAgeRange 消费后丢弃
const passed = verdict === 'pass';
```

### 5.3 复核结果不阻断交付

| verdict | `era_check_json` | 结果卡片 | 图片 | 任务状态 |
|---|---|---|---|---|
| `pass` | `{passed:true, verdict:'pass', findings:[], model}` | 无标注 | 保留、可下载 | 不受影响 |
| `review` | `{passed:false, verdict:'review', findings:[…], model}` | 标"可能不符合所选年代，仅供参考" | **保留**、可下载 | 不受影响 |
| `reject` | `{passed:false, verdict:'reject', findings:[…], model}` | 标"明显不符合所选年代" | **保留**、可下载 | 不受影响 |
| 复核调用失败 | 保持 `NULL`（`eraCheck: null`） | 无标注 | 保留、可下载 | 不受影响 |

**不删图、不置失败的三个理由**：① 复核的 `item` / `reason` 本身可能错（把 90 年代的固定电话认成现代设备），升格为硬闸门等于用一次未经人工验证的判断没收用户已付额度的产出；② `spec/00-总纲.md` §4.4 的年代一致性 ≥ 70% 与年代穿帮率 ≤ 3% 都是**批次级比例**，逐张阻断无法达成、只会让用户拿不到图；③ `era_check_json` 落库后可离线统计穿帮率，反推是哪个年代包/组合需要迭代 prompt（`spec/05-Prompt工程.md` §7.2 的"改包 → 升 `pack_version`"回路）。

### 5.4 年龄偏差 `age_delta` 的计算

```ts
const ANCHOR_MID  = midOfRange(features.ageRange);     // identity_anchors.features_json.ageRange
const ESTIMATED_MID = midOfRange(review.estimatedAgeRange);
const age_delta = (ANCHOR_MID === null || ESTIMATED_MID === null)
  ? null : ESTIMATED_MID - ANCHOR_MID;

// "75-85岁" / "70-78" → 取两端整数求平均并四舍五入；解析失败返回 null
function midOfRange(s: string | null): number | null;
```

- 基准**只用结构化字段** `features.ageRange`（`spec/03-接口契约.md` §4 `AnchorFeatures.ageRange`），不解析 `anchor_text` 里的数字——单一来源，避免两处漂移；
- `age_delta` 是有符号整数：**负数 = 生成图比源照片年轻**。

> **负数是最危险的失败方向，必须在文档、代码、日志、卡片四处显式区分。**
> 模型的天然倾向是理想化与减龄，这正是 `spec/00-总纲.md` §4.3 的红线"把老人磨年轻"。
> 因此 `age_delta` **不得取绝对值后上报**；监控指标分别统计"变年轻"与"变年长"的比例，只有前者触发 `spec/05-Prompt工程.md` §4 的反美化回路。`ageReview.ts` 中对 `age_delta < 0` 的日志必须单独打一条 `warn`，附带 `eraCode` / `sceneId`，便于定位是哪个年代包在推减龄。

### 5.5 年龄偏差的呈现与产品含义

对齐 `spec/00-总纲.md` §4.4"年龄保真度 `|age_delta| ≤ 5` 岁"：

| 条件 | 卡片呈现 | 含义 |
|---|---|---|
| `age_delta ≤ -6` | "看起来比原照片年轻了 X 岁"（**强调态**） | 最危险方向：极可能是模型抹平皱纹/老年斑导致的减龄，家属最容易一眼否定 |
| `age_delta ≥ +6` | "看起来比原照片年长 X 岁" | 也不达标，但方向相对不刺眼（多为年代包带来的苍老感） |
| `\|age_delta\| ≤ 5` | 不显示任何提示 | 达标，静默 |
| `age_delta = NULL` | 不显示任何提示 | 无从判断，不猜 |

呈现只做标注，**不阻断下载，也不自动重生成**；"再来一组"仍是用户主动动作（`spec/01-领域模型与数据库.md` §2.2）。`spec/00-总纲.md` §4.4 的 60%/70%/5% 三项指标依赖人工评审，自动化只提供上述标注与落库数据。

### 5.6 内容审核三阶段

| 阶段 | 触发点 | 判定什么 | 落库 | reject 路径 |
|---|---|---|---|---|
| `upload` | `POST /api/photos`（`tickets/T03` 落点） | 上传文件本身是否含违规画面（裸露、暴力、违法内容） | `content_reviews(stage='upload', target_type='photo', target_id=photos.id)` | `422 CONTENT_REJECTED`；该 `photos` 行软删（`deleted_at`），**不落盘**；已落盘则立即删除文件 |
| `prompt` | `POST /api/generations` 的"拼装完成 → 入队前"（`generationService`） | 拼装后的 prompt 全文是否含违规内容 | `content_reviews(stage='prompt', target_type='generation', target_id=<预留 id>)` | `422 CONTENT_REJECTED`；**不产生** `generations` 行，不预扣额度 |
| `result` | worker 转存候选图之后（§5.1 ②） | 生成图是否含违规内容 | `content_reviews(stage='result', target_type='generation', target_id=generations.id)` | 终止任务：软删本次已转存的 `kind='generated'` 图、回滚额度、`status='failed'`、`error_code='CONTENT_REJECTED'` |

三阶段任何 `reject` 都额外写 `audit_logs(action='moderation.reject')`，`meta_json` 记 `{stage, targetId, reason}`。

**审核失败（上游超时/报错）与 verdict 的区别**：verdict 是模型给出的结论，失败是没拿到结论。审核是合规硬约束，**不放过未审核的结果**：`PROVIDER_TIMEOUT` / `PROVIDER_ERROR` 按 `spec/03-接口契约.md` §2.2 自动重试 1 次，仍失败则任务 `failed` 并写对应 `error_code`。这与复核的"失败就留空"（§5.3）是刻意的不对称。

**prompt 阶段的实际覆盖面（诚实说明）**：本期用户输入面极小，进入 prompt 的用户侧内容只有 `identity_anchors.anchor_text`，而它由模型读图产出、不是用户手打的文本；年代与场景只能从 `eras` / `scenes` 中选，`prompt_override` 来自种子数据，均不可注入。因此 prompt 阶段真正能拦到的是两类：① 锚点提取时模型从照片中读入的违规文字（例如照片上的标语），间接进入了 prompt；② 为将来"自定义场景描述"入口预留的注入防线（`spec/00-总纲.md` §6.2 明确本期不做该入口）。**它是防线不是主力**，主力仍是 upload 与 result 两个"对着真实图像"的阶段；此点须在实现注释与该 ticket 的 `## Comments` 中写明，不许把它当成已经解决的问题。

`verdict='review'` 在三个阶段都**等同放行**，仅留痕（无人工处置通道，见 §1.2）。

## 6. 边界与错误

| 错误码 | 触发条件 | HTTP / 落点 | 用户可见文案 |
|---|---|---|---|
| `CONTENT_REJECTED` | upload 阶段 verdict = `reject` | `422`，`POST /api/photos` | 这张照片暂时无法处理 |
| `CONTENT_REJECTED` | prompt 阶段 verdict = `reject` | `422`，`POST /api/generations` | 这张照片暂时无法处理 |
| `CONTENT_REJECTED` | result 阶段 verdict = `reject` | worker 写 `generations.status='failed'`、`error_code='CONTENT_REJECTED'`；前端由 `GET /api/generations/:id` 读到 | 这张照片暂时无法处理 |
| `PROVIDER_TIMEOUT` | 审核或复核调用超时（`ARK_TIMEOUT_SECONDS`） | 审核：重试 1 次后任务 `failed`；复核：留 `NULL` 继续 | 生成花的时间有点长，请重试一次 |
| `PROVIDER_ERROR` | 审核或复核调用返回上游错误 | 同上 | 生成服务暂时不可用，请稍后重试 |
| `INTERNAL` | 模型返回的 JSON 无法解析 | 审核：等同 `PROVIDER_ERROR` 路径；复核：留 `NULL` 继续 | 出了点小问题，请重试 |

约束（来自 `spec/04-技术基线与目录结构.md` §4.1）：

- handler 内**不得**抛出 `AppError`，审核导致的终止必须写进 `generations.error_code` / `error_message`；
- 文案取 `spec/03-接口契约.md` §5 表中对应行的"用户可见文案"，不得另造；
- worker 日志用 `logger.warn({ job: 'generate', generationId, stage }, 'msg')` 结构，不复用用户文案。
