## 5. 关键流程与状态机

### 5.1 `POST /api/generations` 完整校验顺序

**顺序即契约**，与 `spec/03-接口契约.md` §3.5 逐条一致；任一步失败立即 `throw new AppError(...)`，不进入下一步。

| # | 条件 | 错误码 / HTTP | 检查依据 |
|---|---|---|---|
| 1 | `count` 不在 {2,3,4} | `INVALID_PARAM` / 400 | 请求体 `count` |
| 2 | `eraCode` / `sceneId` 不存在或 `is_active=0` | `INVALID_PARAM` / 400 | `eras.is_active`、`scenes.is_active` |
| 3 | 锚点不属于当前用户 | `ANCHOR_NOT_FOUND` / 404 | `identity_anchors.user_id` |
| 4 | 锚点 `status != 'succeeded'` 或 `confirmed_by_user != 1` | `ANCHOR_NOT_CONFIRMED` / 409 | `spec/01-领域模型与数据库.md` §2.1 |
| 5 | `consents` 中 `photo_usage` 不存在或已吊销 | `CONSENT_REQUIRED` / 403 | `consents.revoked_at IS NULL` |
| 6 | 今日 `usage_counters.images + count > users.daily_image_quota` | `QUOTA_EXCEEDED` / 429 | `day = dayKey()` |
| 7 | 该用户已有非终态 `generations` | `GENERATION_IN_PROGRESS` / 409 | `status IN ('queued','running')` |

表中未列出的第 0 道关卡由 `src/server/http/validate.ts` 承担：zod 解析请求体（`anchorId` 正整数、`eraCode` 字符串、`sceneId` 正整数、`count` 可选整数），失败同样是 `INVALID_PARAM`（带 `details.fields`），且**发生在第 1 步之前**。第 3 步返回 `404 ANCHOR_NOT_FOUND` 而非 403（`API-04`：避免探测他人资源）；第 6 步必须在任何写操作之前完成（`SEC-04` 要求失败时**不产生 `generations` 行**）。

### 5.2 `createGeneration` 编排步骤

```ts
export function createGeneration(input: {
  userId: number;
  anchorId: number;
  eraCode: string;
  sceneId: number;
  count: number;
}): GenerationRecord;
```

按序执行：

1. **查锚点** —— `anchors.findById(anchorId)`，断言 `user_id === userId`、`status === 'succeeded'`、`confirmed_by_user === 1`，取出 `anchor_text` 与 `preprocessed_photo_id`；`anchor_text` 为空即 `ANCHOR_NOT_CONFIRMED`（`spec/05-Prompt工程.md` §2.1：【身份锚点】段缺失即拒绝生成）。
2. **查配置** —— `config.getEra(eraCode)`、`config.getScene(sceneId)`，断言两行存在且 `is_active = 1`；`preprocessed_photo_id` 为 NULL 时按 `reference_photo_ids = []` 处理并交给 `getArk()` 决定是否纯文生图（本期链路不会出现，`spec/00-总纲.md` §3 链路 ② 已产出预处理图）。
3. **解析组合档案** —— `config.getProfile(eraCode, sceneId)`，命中 `era_scene_profiles` 行则取其 `id` 写入 `generations.profile_id` 与 `prompt_override`；未命中（`is_active=0` 的行不视为命中）时 `profile_id = NULL`、`prompt_override = NULL`，并按两步拼装。
4. **调 `buildPrompt`** ——

   ```ts
   buildPrompt({ anchorText, era, scene, profile })
   // → { prompt, promptHash, templateVersion }
   ```

   段落顺序、正面化约束、长度 warn 全部由该函数负责（`spec/05-Prompt工程.md` §2、§9），本文件不修改其输出。
5. **取 `prompt_hash`** —— 直接使用 `buildPrompt` 返回的 `promptHash`（对最终 prompt 全文取 sha256 十六进制小写），**不另行计算**，否则 `E2E-03` 的逐字符相等断言会被破坏。
6. **单事务写入** ——

   ```ts
   db.transaction.exclusive(() => {
     if (generationsRepo.countActiveByUser(userId) > 0) {   // §5.1 第 7 步的排他复查
       throw new AppError('GENERATION_IN_PROGRESS', '上一组还在生成，稍等一下', 409);
     }
     const id = generationsRepo.insert({
       userId, anchorId, eraCode, sceneId,
       profileId: profile?.id ?? null,
       referencePhotoIds: preprocessedPhotoId ? [preprocessedPhotoId] : [],
       prompt, promptHash,
       templateVersion: templateVersion,
       eraPackVersion: era.packVersion,
       scenePackVersion: scene.packVersion,
       model: process.env.ARK_IMAGE_MODEL,
       params: { size: era.defaultSize, outputFormat: 'png',
                 watermark: process.env.WATERMARK_DEFAULT === 'true',
                 provider: process.env.PROVIDER },
       requestedCount: count,
       status: 'queued',
       attempt: 0,
       createdAt: nowIso(),
     });
     usageRepo.deduct(userId, dayKey(), count);   // generations += 1, images += count
     auditRepo.write({ userId, action: 'generation.create', target: `generation:${id}` });
     return id;
   })();
   ```

   §5.1 的第 1–6 步与第 7 步的判定在事务**之外**先跑一遍（快速失败、不产生写操作），第 7 步再在事务内复查一次，作为"同一用户同时只允许 1 个非终态任务"的排他保证；SQLite 单进程 + `better-sqlite3` 同步 API 下 `db.transaction.exclusive()` 的 `BEGIN IMMEDIATE` 语义足以覆盖（本期不做多 worker）。
7. 返回 `GenerationRecord`（含 `params`），由 route handler 转成 `Generation` 形状。

### 5.3 `generations` 状态机与终态判定

转移规则引用 `spec/01-领域模型与数据库.md` §2.2：

```
queued ──▶ running ──┬──▶ succeeded   n = requested_count
                     ├──▶ partial     1 ≤ n < requested_count
                     └──▶ failed      n = 0
                     (worker 崩溃回收：started_at 超时 → 回退 queued，attempt 不变)
```

其中 `n` = 本次执行**成功转存并落库**的 `generation_results` 行数（`E2E-05`、`E2E-06`）。判定在新行全部写入后、同一事务内完成：

```ts
const n = results.length;
const status = n === requestedCount ? 'succeeded' : n > 0 ? 'partial' : 'failed';
```

- `succeeded`：`error_code` / `error_message` 均写 NULL；
- `partial`：`error_code` 写造成张数不足的**最后一个**失败码，`error_message` 写其文案；
- `failed`：`error_code` 写失败原因，`error_message` 写上游原始 message（仅落库，不透给用户）；
- 三种终态都必须写 `finished_at = nowIso()`，并写 `audit_logs(action='generation.finish')`；
- `succeeded` / `partial` 必须至少有 1 行 `generation_results`。
- `partial` **不触发自动重试**：重跑会把额度与产出重复翻倍，补齐缺口须走 §5.7 `POST /api/generations/:id/retry`。这是对 `spec/01-领域模型与数据库.md` §2.2 的收窄，理由见 §9。

### 5.4 worker 拉取与 claim

`src/jobs/worker.ts` 主循环每轮做三件事：回收（仅首次启动）、拉取、执行。

**拉取**（单进程、串行为主，并发度 `WORKER_CONCURRENCY` 默认 1）：

```sql
SELECT id FROM generations
 WHERE status = 'queued'
 ORDER BY created_at
 LIMIT 1;
```

同一循环同时服务 `identity_anchors`：

```sql
SELECT id FROM identity_anchors
 WHERE status = 'queued'
 ORDER BY created_at
 LIMIT 1;
```

固定先处理锚点、再处理生成；`WORKER_CONCURRENCY` 为**同时执行的 handler 数上限**，默认 1 即完全串行（`spec/04-技术基线与目录结构.md` §4.6）。

**claim 的原子性**——不依赖内存状态，靠 `UPDATE ... WHERE status='queued'` 的 `changes` 判断：

```sql
UPDATE generations
   SET status = 'running',
       started_at = :startedAt
 WHERE id = :id
   AND status = 'queued';
```

```ts
const { changes } = db.prepare(CLAIM_SQL).run({ id, startedAt: nowIso() });
if (changes !== 1) return; // 没抢到：已被处理或状态已变，直接放弃本轮
```

`attempt` **不在 claim 阶段自增**，只由自动重试调度（§5.5）自增；因此 `ERR-01` 的"重试 1 次后 `attempt=1`"成立。

### 5.5 心跳、启动回收、超时、自动重试

- **心跳**：worker 启动即 `setInterval(5_000)`，把 `nowIso()` 写入心跳文件 `.<DATA_DIR>/worker-heartbeat`（字面路径见 `spec/03-接口契约.md` §2.3）。`GET /api/health` 读其 mtime，超过 15 秒未更新则 `worker.alive=false`（`ERR-04`）。等待任务时不阻塞该定时器。
- **启动时回收**（进程启动后执行一次，两类任务各一条）：

  ```sql
  UPDATE generations
     SET status = 'queued', started_at = NULL
   WHERE status = 'running'
     AND started_at < :staleBefore;   -- nowIso() 减去 WORKER_STALE_MINUTES 分钟
  ```

  `attempt` **保持不变**，`error_code` 不写（`ERR-02`：1 小时前的 `running` 行在重启后回到 `queued`）。
- **超时判定**：handler 用 `AbortController` 包裹，超过 `JOB_TIMEOUT_SECONDS` 即中止，按 `PROVIDER_TIMEOUT` 处理（可重试）。上游单次调用的超时另由 `RealArkProvider` 用 `ARK_TIMEOUT_SECONDS` 控制，两者关系见 §9。
- **自动重试规则**：

  ```ts
  const RETRYABLE: ErrorCode[] = ['PROVIDER_TIMEOUT', 'PROVIDER_ERROR', 'STORAGE_ERROR'];
  ```

  执行失败且 `n === 0` 且 `RETRYABLE.includes(errorCode)` 且 `attempt < 1` →

  ```sql
  UPDATE generations
     SET status = 'queued', attempt = attempt + 1, error_code = :code, error_message = :msg
   WHERE id = :id AND status = 'running';
  ```

  否则直接写终态（`failed`）。`attempt ≥ 1` 后不再自动重试，交由用户 `POST /api/generations/:id/retry`（`spec/01-领域模型与数据库.md` §2.2）。

### 5.6 额度预扣与失败回滚

- **预扣**发生在 `createGeneration` 事务内（§5.2 第 6 步）：`usage_counters(user_id, day)` UPSERT 后 `images += count`、`generations += 1`；`day` 取 **`generations.created_at` 的 UTC 日期**，不是 worker 完成日。
- **回滚**发生在写终态前的同一事务内：产出 `n` 张，未产出 `requested_count - n` 张：

  ```sql
  UPDATE usage_counters
     SET images = images - :unproduced
   WHERE user_id = :userId
     AND day = :generationDay;      -- 仍用入队日，跨天完成时不打错行
  ```

  `unproduced === 0` 时不执行该语句；`generations` 计数**不回滚**（任务确实发生了）。
- **保留产出张数**：`succeeded` 时 `images` 净增 `requested_count`（`E2E-08`）；`partial` 时净增 `n`；`failed` 时净增 0。
- 回滚后不会出现 `images < 0`：预扣与回滚用同一 `day`，且 `unproduced = requested_count - n ≤ requested_count`。

### 5.7 `POST /api/generations/:id/retry` 的新建行语义

- 允许的原任务状态：`succeeded` / `partial` / `failed`；原任务为 `queued` / `running` → `409 GENERATION_IN_PROGRESS`。
- 语义 = **新建 `generations` 行**，继承 `anchor_id` / `era_code` / `scene_id` / `requested_count` / `params_json`，`attempt = 0`，`status = 'queued'`，`created_at` 取当前时间；**绝不更新旧行**及其 `generation_results`（`E2E-09`）。
- 复用 `createGeneration` 的**同一校验序列与同一事务**（§5.2），因此第 4/5/7 步（`ANCHOR_NOT_CONFIRMED` / `CONSENT_REQUIRED` / `GENERATION_IN_PROGRESS`）同样生效，第 6 步额度不足返回 `429 QUOTA_EXCEEDED`。
- prompt **重新拼装**而非复制旧行：配置包可能已升级，`buildPrompt` 是唯一入口、必须重新落当时的 `template_version` / `era_pack_version` / `scene_pack_version`（`spec/05-Prompt工程.md` §7.2 第 3 条）。
- 入口签名：

  ```ts
  export function retryGeneration(input: { userId: number; generationId: number }): GenerationRecord;
  ```

### 5.8 上游错误码 → 本项目错误码映射（`src/server/ark/errors.ts`）

唯一映射函数：

```ts
export function mapArkError(err: unknown): { code: ErrorCode; retryable: boolean; raw: string };
```

覆盖 `docs/火山引擎接口文档.md` §5 的全部 8 类：

| # | 上游错误（raw §5） | 本项目错误码 | 可重试 | 说明 |
|---|---|---|---|---|
| 1 | `ModelNotOpen`（§5.1 生图模型未开通） | `PROVIDER_ERROR` | ❌ | 账号级开通状态，重试不会变；`health.provider.arkConfigured` 只反映 Key 是否存在 |
| 2 | `InvalidParameter`（§5.2 `size` 低于 3,686,400 像素） | `INTERNAL` | ❌ | 属我方拼装 bug（`eras.default_size` 配错），不打给用户（`ERR-03`） |
| 3 | platform profile 要求 endpoint（§5.3） | `INTERNAL` | ❌ | 本项目直连 HTTP + 模型名，不走 Endpoint（`spec/08-本地开发指南.md` §5.2）；出现即接入方式被改坏 |
| 4 | arkcli 创建 Endpoint 时模型未开通（§5.4） | `INTERNAL` | ❌ | 控制面 / arkcli 场景，不在 MVP 热路径；记录并告警 |
| 5 | `InvalidEndpointOrModel.NotFound`（§5.5） | `PROVIDER_ERROR` | ❌ | 模型 ID 写错或未对账号开放，属配置错误 |
| 6 | 未登录 / 未配置（§5.6） | `INTERNAL` | ❌ | 等价情形为 `ARK_API_KEY` 缺失或失效，属部署配置错误 |
| 7 | `InvalidParameter.NonUTF8Body`（§5.7） | `INTERNAL` | ❌ | 我们始终 `JSON.stringify` + UTF-8 发送，出现即我方 bug |
| 8 | 删除运行中的 Endpoint（§5.8） | —（不映射） | ❌ | 控制面操作，本项目不调用 |

同文件还需覆盖 `spec/03-接口契约.md` §5.1 已声明的其余分支：

| 上游情形 | 本项目错误码 | 可重试 |
|---|---|---|
| HTTP 429 / 限流 | `PROVIDER_ERROR` | ✅ |
| 网络超时 / fetch abort（含 `AbortError`） | `PROVIDER_TIMEOUT` | ✅ |
| `InternalServiceError`（含 `/responses` 通道失败） | `PROVIDER_ERROR` | ✅ |
| 其他 HTTP 5xx | `PROVIDER_ERROR` | ✅ |
| 其他 HTTP 4xx | `PROVIDER_ERROR` | ❌ |
| `data` 为空数组（未返回图片） | `PROVIDER_ERROR` | ✅ |
| 图片下载失败（签名 URL 过期 / 403） | `STORAGE_ERROR` | ✅ |
| 本地写盘失败 | `STORAGE_ERROR` | ✅ |

判定顺序：先看 `error.code` 字符串（`ModelNotOpen` / `InvalidParameter*` / `InvalidEndpointOrModel.*` / `InternalServiceError`），再看 HTTP 状态，最后落到 `INTERNAL`。返回体的 `model` 字段**不得用于断言**（返回值是规范化基础 ID `doubao-seedream-5-0-260128`，`README.md` §4.1）。

### 5.9 执行一个生成任务（handler 骨架）

```ts
// src/jobs/handlers/generate.ts
export async function runGenerateJob(generation: GenerationRecord): Promise<void>;
```

1. `getArk()` 按 `PROVIDER` 取 provider；`reference_photo_ids` 逐张读 `photos.storage_key` → 本地文件 → Base64 data URI。
2. 调用 `ark.generateImage({ prompt, images, size, outputFormat, watermark, count })`；`count > 1` 时请求体带 `sequential_image_generation: 'auto'` 与 `sequential_image_generation_options.max_images = requested_count`（`.scratch/seedream_era_scene.js` 实测用法）。
3. 逐张**立即转存**（上游 `data[].url` 是 86400s 有效期的签名链，`README.md` §4.1）：下载 → `LocalStorageProvider` 先写 `.tmp` 再 rename → 插 `photos(kind='generated')`，`AIGC_IMPLICIT_MARKER=true` 时写入隐式标识元数据（`spec/06-合规与风控.md`）。
4. 逐张插 `generation_results`，`ordinal` 从 0 连续递增。
5. 调 `modules/M07-生成后复核与内容审核.md` 的复核：写 `era_check_json`、`age_delta`；审核 `reject` → 该张不计入 `n`，写 `content_reviews(stage='result', verdict='reject')` 与 `audit_logs(action='moderation.reject')`，任务按 §5.3 判定（全部被拒即 `failed` + `CONTENT_REJECTED`，见 `SEC-08`）。
6. 按 §5.3 写终态、按 §5.6 回滚额度、写 `audit_logs(action='generation.finish')`，全部在**同一事务**内。
7. handler 内部捕获所有异常并转成 `error_code` / `error_message` 写库，**不得把 `AppError` 抛给 worker 循环**（`spec/04-技术基线与目录结构.md` §4.1）。

## 6. 边界与错误

| 错误码 | 触发条件 | 用户可见文案 |
|---|---|---|
| `INVALID_PARAM` | `count ∉ {2,3,4}`；`eraCode` / `sceneId` 不存在或未启用；zod 解析失败 | 选择有误，请重新选一下 |
| `ANCHOR_NOT_FOUND` | 锚点不存在或不属于当前用户 | 这次的人物特征记录找不到了 |
| `ANCHOR_NOT_CONFIRMED` | 锚点 `status != 'succeeded'` 或 `confirmed_by_user != 1`，或 `anchor_text` 为空 | 需要先确认"这就是他"，才能开始生成 |
| `CONSENT_REQUIRED` | `photo_usage` 授权不存在或已吊销 | 需要先确认照片使用授权 |
| `QUOTA_EXCEEDED` | `usage_counters.images + count > users.daily_image_quota` | 今天的生成额度用完了，明天再来吧 |
| `GENERATION_IN_PROGRESS` | 已有非终态 `generations`；retry 时原任务非终态 | 上一组还在生成，稍等一下 |
| `PROVIDER_ERROR` | 上游返回错误（含模型未开通、模型 ID 错误、限流、5xx） | 生成服务暂时不可用，请稍后重试 |
| `PROVIDER_TIMEOUT` | 上游超时或 `JOB_TIMEOUT_SECONDS` 超时 | 生成花的时间有点长，请重试一次 |
| `STORAGE_ERROR` | 图片下载失败、写盘失败 | 保存失败，请重试 |
| `CONTENT_REJECTED` | 结果审核 `reject`（由 §5.9 第 5 步写入） | 这张照片暂时无法处理 |
| `INTERNAL` | 上表中映射为 `INTERNAL` 的上游错误、未捕获异常 | 出了点小问题，请重试 |

写库的 `error_message` 保存上游原文用于排查；响应里的 `error.message` 一律用上表文案，**不得透出上游 message 与 RequestId**（`spec/04-技术基线与目录结构.md` §4.1）。

## 9. 非目标与待定决策

非目标（见 §1.2 与 `spec/04-技术基线与目录结构.md` §5）：多 worker、通用任务队列、用户可编辑 prompt、多人全家福（`reference_photo_ids` 本期只写 1 个元素）。

待定决策：

1. **`partial` 不自动重试**。`spec/01-领域模型与数据库.md` §2.2 只写了"失败自动重试 1 次"，未区分 `partial`（理由见 §5.3）。若后续要自动补齐缺口，需先定义"只补未产出的 ordinal"，属新功能。
2. **`WORKER_CONCURRENCY` 未登记**。`spec/04-技术基线与目录结构.md` §4.6 已使用该名，但 `spec/08-本地开发指南.md` §4 无此行；落地时需补一行默认值 `1`。
3. **心跳路径 `.<DATA_DIR>/worker-heartbeat` 的解析**。`spec/03-接口契约.md` §2.3 用的 `<DATA_DIR>` 在 `spec/08-本地开发指南.md` §4 无对应变量。MVP 按 `<DATA_DIR> = dirname(DATABASE_PATH)`（默认 `./data`）解析；是否引入独立的 `DATA_DIR` 变量、或改为 `./data/worker-heartbeat`，由 `spec/08-本地开发指南.md` 定稿。
4. **`JOB_TIMEOUT_SECONDS` 与 `ARK_TIMEOUT_SECONDS` 同为 120**。生成 handler 内联调用 `modules/M07-生成后复核与内容审核.md` 的复核（可能又是一次上游调用），两者默认值下总时限紧张；建议在 `spec/08-本地开发指南.md` §4 说明关系，或把 `JOB_TIMEOUT_SECONDS` 抬高（本文件不改默认值）。
5. **`params_json.outputFormat` 固定 `'png'`**：`output_format` 仅 Seedream lite 可设（`README.md` §4.1）。若将来换模型，需按模型能力降级为 `jpeg`。
6. **`POST /api/generations/:id/retry` 的完整错误集**。`spec/03-接口契约.md` §3.5 只列出 `GENERATION_IN_PROGRESS` 与 `QUOTA_EXCEEDED`；本文件因复用 `createGeneration` 而使 `ANCHOR_NOT_CONFIRMED` / `CONSENT_REQUIRED` 同样可能出现，需在 `spec/03-接口契约.md` 追认或改为独立校验序列。
7. **面部相似度阈值**（`spec/00-总纲.md` §4.4，≥ 0.55）本期不实现，`generation_results.realism_score` 已预留。
