# 契约收敛与检查项注册表

Status: ready-for-agent

## Problem Statement

`docs/prd/` 已经有 46 份文件、颗粒度足够让 AI 开工，但它自己不自洽。同一件事被写了很多遍，于是每一遍都可能不一样：

- 错误码表在 `spec/03 §5` 定义之后，`M01`–`M09` 又各写一遍，共 9 份；
- worker 的 claim / 心跳 / 回收 / 自动重试在 `spec/04 §4.6`、`M06`、`M08`、`M09` 各写一遍，任务来源两表 vs 三表已经打起来；
- prompt 长度有三套阈值（`spec/05 §9` 的"300–900 / 200 / 1200" vs `spec/07` `PR-07` 的 `[200, 1200]`）；
- 检查项注册表 `spec/07 §2` 与 `tickets/README.md` 的索引列已经有 8 行不一致（T05/T06/T07/T09/T10/T12/T13/T16/T17）；
- 4 处引用指向不存在的章节或文件（`M05 §5.5`、`pages/P04`、`spec/11`、`U14`）；
- `anchor_text` 有两个长度口径（60–120 字 vs `[40, 200]` 字符），`suggestSceneId` 在 5 处是场景 id、在 2 处是场景代号，`reject` 一个词同时表示"标注不阻断"与"终止任务"两个相反的后果。

上一轮整改建了 `.scratch/check-docs.mjs`，但它只断言 orphan / 双属 / 幽灵三态，因此索引漂移、破损引用、术语一号两义都从它眼皮底下过去了。结果就是：一个 AI 工人照 `T01` 开工，会在"错误码以哪份为准""prompt 正文以代码还是文档为准""`reject` 到底要不要阻断"这些地方做错或卡住——而这些都不是实现能力问题，是输入自相矛盾。

## Solution

做一次文档收敛 + 装一个机器校验闸门。

**收敛**：每类契约指定唯一事实源，删掉复制体；术语的**定义**与**落点**分权（定义进 `CONTEXT.md`，落点留 PRD）；把"不定就写不了代码"的契约缺口逐条裁定并回改权威文档；被降级的上游需求显式登记。

**闸门**：新增 `spec/check-registry.json` 与 `pnpm check:docs`，把"ID 唯一 / 恰一个 owner / 无孤儿 / ticket 声明的 ID 存在 / '新建'全仓唯一 / 声明的文件与 fixture 与章节存在 / 索引 ≡ ticket 表头 / 打印数与注册表一致"变成 8 条静态断言，挂在 `tickets/T01` 上先于一切编码工作完成。

收敛让 PRD 自洽，闸门让它保持自洽——只有前半段，下一次整改还会在别处重新长出来。

## User Stories

1. 作为按 ticket 开工的 AI 工人，我希望每条 ticket 表头声明的检查项 ID 都真实存在于注册表，以便不必猜测哪个是笔误。
2. 作为 AI 工人，我希望每个检查项 ID 只有一个 owner，以便不必判断"改期望值让检查变绿"是不是被允许的。
3. 作为 AI 工人，我希望 `tickets/README.md` 的检查项列与 ticket 表头逐格一致，以便开工时选票不会选错。
4. 作为 AI 工人，我希望错误码只有一处定义，以便不必在 9 份互不相同的表之间做选择。
5. 作为 AI 工人，我希望 prompt 正文只有一个事实源，以便不必决定"以代码为准还是以文档为准"。
6. 作为 AI 工人，我希望 worker 的任务来源、claim 原子性、心跳与回收规则只有一处定义，以便不会照 `M06` 写出一张漏掉的表。
7. 作为 AI 工人，我希望数值阈值只在一处声明，以便不会把三个长度阈值中的任意一个写进实现。
8. 作为 AI 工人，我希望 `年代复核判定` 与 `内容审核判定` 是词面可区分的两个概念，以便不会把"只标注"写成"终止产出"。
9. 作为 AI 工人，我希望 `anchor_text` 的长度只有一个区间，以便不必在两个口径之间选一个。
10. 作为 AI 工人，我希望 `suggestSceneId` 明确是场景 id 而不是场景代号，以便不必为可分享 URL 猜参数类型。
11. 作为 AI 工人，我希望 `storage.delete()` 对"文件不存在"的语义唯一且逐方法声明错误映射，以便级联删除不会被一个 `NOT_FOUND` 打断。

15. 作为 AI 工人，我希望每个文件的"新建"只被一条 ticket 声明，以便两条 ticket 不会各自以为自己创建同一份文件。
16. 作为 AI 工人，我希望依赖图包含全部真实依赖边，以便不会在缺少前置产物的阶段开始写代码。
17. 作为 AI 工人，我希望 M1/M2 期间的鉴权有一个明确的桩与明确的替换出口，以便受保护端点不会被写成没有鉴权的样子。

31. 作为合规负责人，我希望数据留存期、照片加密与传输、未成年人这三项要么落地要么被显式登记为"本期不做"，以便它们不会既没做也没人知道。
32. 作为合规负责人，我希望实名通过这件事留有审计痕迹，以便门槛动作可事后追溯。
33. 作为合规负责人，我希望"可见标识开关不做"这个结论在页面、合规文档与差异登记里只有一个说法，以便不会有人照页面上的待定项把它实现出来。
34. 作为前端实现者，我希望错误码到用户文案只有一份清单，以便不会在两个页面的文案表之间漂移。
35. 作为前端实现者，我希望反向提示词这个旁路能力的入口落在一个"照片已存在就能用"的位置，以便它不会必须先走完上传到授权的全链路。
36. 作为前端实现者，我希望"首次"这类一次性的状态有明确的存储口径，以便不会既被告知禁止本地存储、又被要求记住已读。
37. 作为前端实现者，我希望页面文档有一个最小必需节清单，以便新页面不会以任意形状出现。
38. 作为文档作者，我希望术语的定义与落点分开存放，以便术语表不会被表名列名污染，而落点也不会被复制成第二份定义。

## Implementation Decisions

### 事实源与去重

每个契约类别指定唯一事实源，其余位置一律改为引用而非复述：

| 契约类别 | 唯一事实源 |
| --- | --- |
| 错误码及其含义 | `spec/03-接口契约.md §5` |
| 数值阈值 | `spec/07-验收标准.md §2` |
| prompt 正文 | prompt 模板模块（代码） |
| 年代 / 场景 / 组合数据 | `spec/era-scene-seed.json` |
| 表与列 | `spec/01-领域模型与数据库.md` 与 `spec/02-schema.sql` |
| worker 契约 | `spec/04-技术基线与目录结构.md §4.6` |
| 目录与文件命名 | `spec/04-技术基线与目录结构.md §2` |
| 术语定义 | `CONTEXT.md` |
| 检查项注册表 | `spec/check-registry.json`（新建） |
| 错误码 → 用户文案 | `spec/03-接口契约.md` §5（服务端 `error.message` 即用户可见文案；`pages/P00-设计基准与路由.md` §8 只定义呈现形态与附加动作） |

- `M01`–`M09` 各自复述的错误码表体删除，只留指向 `spec/03 §5` 的引用。
- `spec/05-Prompt工程.md` 只写 prompt 的结构与约束，正文以代码为唯一事实源，加"文档与代码等值"断言。
- `spec/07 §2` 的检查项阈值成为唯一阈值来源；`spec/05 §9` 与 `PR-07` 的三套长度口径收敛为一处，其余改为引用。
- `tickets/README.md` 的检查项列改为由 ticket 表头派生，并由 `check:docs` 断言一致。
- 加一条施工纪律：**不许复制契约，只许引用**，并规定契约级分歧不得记为 ticket 的待定决策。

### 定义与落点分权

术语的**定义**以根 `CONTEXT.md` 为唯一事实源（该文件已建立）。`spec/00-总纲.md §5` 只保留"术语 → 表.列 / 模块"的落点映射，含义列改为指向 `CONTEXT.md`。理由：「落在哪张表哪个列」是实现细节，术语表不应承载；而定义有两份必然漂移。

### 术语裁定

- `reject` 一词承载两个相反后果，拆为 `eraCheckVerdict`（年代复核判定：不通过只标注、不阻断交付）与 `moderationVerdict`（内容审核判定：不通过终止该张及后续产出）。**列名与取值字符串不变**，只把概念与类型命名分开，并同步 `spec/01 §3.8`/`§3.13`、`M07`、`spec/07` 的 `REV-*` 与 `SEC-08` 的措辞。
- `anchor_text` 长度统一为 **60–120 字符**（`spec/01` 的"字"改"字符"，`E2E-02` 的 `[40, 200]` 改 `[60, 120]`）。
- `suggestSceneId` 唯一语义为**场景 id**（整数），`spec/03 §3.8` 的"代号"措辞与 `spec/07` 的 `REV-02` 断言同步改正；`suggestEraCode` 仍是年代代号字符串。
- canonical 术语取 `身份锚点`，`面部特征锚点` 记为别名。

### 检查项注册表与校验

新建 `spec/check-registry.json`，每条记录 `{ id, layer, owner, path, assertedBy, tickets[] }`；新建 `pnpm check:docs`（先有 `.scratch/check-docs.mjs` 原型可作起点），断言 8 条：

1. ID 全局唯一（拦一号两义）；
2. 每个 ID 恰有一个 owner（拦双 owner）；
3. 每个 ID 至少被一条 ticket 认领（拦无 owner）；
4. ticket 表头声明的 ID 必须存在（拦幽灵 ID）；
5. "新建"某文件在全仓唯一（拦双"新建"）；
6. 声明的文件、fixture 与**被引用的章节**都存在（拦破损引用）；
7. `tickets/README.md` 的检查项列 ≡ ticket 表头（拦索引漂移）；
8. 文档里写出的检查项总数 ≡ 注册表条数（拦计数口径）。

检查项计数口径统一为：B 层由 `check:acceptance` 断言、A 层由 `pnpm test` 断言，两层的数字都由注册表派生。

### 逐 ticket 的契约裁定

- **T01**：`check:docs` 与注册表的骨架创建归本条；`spec` 层骨架一并落地。
- **T02**：数据层之外，增加 `requireUser()` 桩一节（读种子 `DEV_USER`、不查 cookie）；PRAGMA 不进迁移文件。
- **T03**：HEIC 探测失败拆两类——容器可解析但读不到宽高则写 `NULL` 并继续，解码器打不开文件才返回 `INVALID_FILE_TYPE`；补 `sharp` 错误码到两分支的映射。`photos.mime` 的允许值补 `image/heic`。上传阶段的 `content_reviews` 每阶段都写一行。
- **T04**：`M01` 的 repository 签名清单补上 `M02` 依赖的两个函数与软删条件；预处理评分所需的输入形状显式声明（灰度图、直方图统计、宽高、人脸框），不再引用未定义符号。
- **T05**：`mapArkError` 的错误映射逐条断言；`ERR-01` 期望值为超时映射（`PROVIDER_TIMEOUT`、重试一次后仍失败）。
- **T06**：`features` 定 `.strip()`——多余键丢弃、落库恰好 12 键，`M03 §8` 的用例改为"多一个键 → 成功且落库 12 键"；prompt 版本注册表显式声明，未知版本映射为内部错误。
- **T07**：`consents` / 审计的边界与 `M08` 的分工写明；授权留痕的检查项不再是 `SEC-07`。
- **T08**：`realismAnchor` / `agePreserveClause` / `confidenceHintThreshold` 由 prompt 版本模块导出，加"与种子顶层逐字符一致"的断言；`M05 §5.5` 的破损引用修正为 §5.2。
- **T09**：三张任务表改**轮转拉取**（记录上一轮结束的表，下一轮从下一张开始），不再固定顺序；排他性检查放在插入之前，事务用 `BEGIN IMMEDIATE`，`SQLITE_BUSY` 归入可重试错误集。
- **T10**：结果图的宽高取**转存后实测值**；`generation_results.seed` 明确为"仅上游回传时记录，不作为复现依据"，`README §4.3` / `spec/00 §3` / `spec/05 §7.2` 统一为"可重新提交复现"。三条未验证的上游能力登记在 `spec/07 §6` 的诚实边界表，T10 为唯一挂起处。
- **T11**：`moderationVerdict` 为不通过时不写结果行、不计入张数，终态由张数决定；年代复核判定与年龄偏差的断言各归其位。
- **T12**：账号会话与额度；`readQuota` 的读取下沉到 `T09` 需要它的地方，依赖图补边。
- **T13**：历史范围扩展到"已上传但未确认锚点"的照片；删除恒返回成功（未清理的重复删除也成功）。
- **T14–T17**：页面层裁定见下节。
- **T18**：上游读图端点拼接统一（`ARK_BASE_URL` 已含版本前缀，只拼路径）；模型名取自环境变量而非硬编码进 SQL；repository 计数 11→12、fixture 计数 8→9 与目录命名以技术基线为准；文件与模块命名统一。
- **T19**：实名通过写入审计，并补一个实名相关的 action 到必记 action 清单（同步修正清单条数）。
- **T20**：`scripts/acceptance.ts` 的骨架创建前移到 `T01`，其余 ticket 一律标"修改"。

### 依赖边

- `T18 → T16`（反向提示词面板的前端归属在 `T16`，后端在 `T18`）。
- `T12 → T14`（站点头部消费当前用户信息）。
- `T02` 的 `requireUser()` 桩 → `T12` 的替换出口（含未登录访问受保护端点的回归项）。

### 页面层裁定

- **结果页**：新增"未完成的照片"区块（或等价路由），复用同一套删除确认，使任何未软删照片都可见可彻底删除。
- **结果页**：反馈取值域扩为 `喜欢 / 不喜欢 / 不像他 / 空`，并给出回到上传换一张照片的路径；本期该值只落库留痕，不做聚合（避免再造一个没有 owner 的指标）。
- **结果页**：下载扩展名从生成参数里的输出格式派生。
- **结果页**：首次使用的情感安全说明落在这里，触发口径为**每会话一次、状态放内存态**（页面规范禁止本地存储与"已读"状态，内存态是唯一可行解）。
- **新增 `pages/P04-失败与情绪安全路径.md`**：覆盖锚点提取失败、质量不可用、生成失败、结果不像他、超时、额度用尽、worker 未启动、未实名、未确认锚点这些负路径。该文件必须在 `T15`–`T17` 之前完成。
- **上传页**：多选时的取数规则改为"取前 5 张"，不再依赖选文件阶段拿不到的评分。
- **反向提示词入口**：从"要求锚点已确认"的选择页移到"照片已存在即可用"的上传页，否则这个降低门槛的能力必须先走完全链路。
- **错误码文案**：单一清单在页面规范的映射表里，另一处只保留触发位置并补上缺的那几个错误码。
- **页面文档**：给 5 份页面文档定最小必需节清单（目标、范围、依赖、接口消费、状态与错误、验收），由 `check:docs` 断言。

### 合规登记

- `spec/06-合规与风控.md` 的"生产必须补"对照表补三行：数据留存期（明确清理延迟不等于留存承诺）、照片加密与传输、未成年人场景——三项本期均不做，但必须显式登记。
- 可见标识开关维持"本期不做"，删除页面文档里与之相反的待定项，并在差异登记里记一行。
- `spec/07 §4` 的盲测报告模板不得出现禁用措辞（"逝者"等），改为"照片中人物的家属本人"。
- 与上游需求的差异登记从 3 行扩为 12 行摘要，并注明逐项的追溯矩阵延后。

## Testing Decisions

**什么是好测试**：只断言外部可观察的事实——文档树上的注册表、索引、引用与计数。不去断言校验脚本的内部实现（例如"它用了哪个正则"），否则每次重构脚本都要改测试。断言失败信息必须直接指出哪条 ID、哪份文件、哪一行，因为它同时是人类维护者的诊断工具。

**测什么**：

- `pnpm check:docs`（新）——8 条静态断言，被测对象是整个 `docs/prd/` 文档树。这是本 spec 的最高且唯一接缝。
- `pnpm check:acceptance`（已规划，B 层）——注册表里 B 层条目的口径与打印数一致。
- `pnpm test`（已规划，A 层）——注册表里 A 层条目的口径。

**已有先例**：上一轮整改的 `.scratch/check-docs.mjs` 已按同一思路跑过一遍全库，输出过 `registry / by family / UNOWNED / DOUBLE-OWNED / PHANTOM` 形态的摘要，可直接作为起点与对照基线。

**这些接缝与新代码的关系**：本 spec 不产出产品代码，因此没有更深一层的接缝可用；`check:docs` 是能覆盖全部收敛成果的最高点。它必须能独立运行、不依赖 `ARK_API_KEY`、不依赖产品进程。

## Out of Scope

- 修改 PRD 的**产品**内容：不新增功能、不动年代场景数据、不改 prompt 正文文本、不改已冻结的接口形状。
- 上游能力的真机验证与台账（另立 spec）。
- 与上游需求的逐项追溯矩阵。
- 6 条不影响开工的缺陷（确定性措辞、锚点侧词表缺检查项、375px 逐页布局规则、上游差异矩阵本体），继续留在各自 ticket 的 `## Comments`。
- 页面视觉规范与移动端布局细节的统一。
- 任何产品代码实现：`T01`–`T20` 的实现是另一条线，本 spec 只保证它们的输入自洽。

## Further Notes

- 本 spec 的裁定来自一次专门针对 `docs/prd` 的评审与逐条裁决；34 条契约级缺陷全部有过"保留现状"的替代方案，不是遗漏。
- `CONTEXT.md` 与 `docs/adr/0001-f1-is-feature-extraction-not-restoration.md` 已经存在。ADR-0001 决定了本 spec 里 F1 相关措辞的方向：不给用户"照片变清楚了"的承诺，因此任何回改都不得引入"修复效果"类验收。
