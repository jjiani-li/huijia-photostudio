# 上游能力验证与能力台账

Status: ready-for-agent

## Problem Statement

有三条上游能力被写进了数据库 schema、对外承诺和产品链路，但全仓库找不到任何实测证据：

1. **生图的 `seed` 参数**。"可复现"这个承诺完全建立在它身上——`generation_results` 有 `seed` 列，`spec/00 §3` 与 `README §4.3` 声称所有生图参数必须落库以保证复现。但上游接口文档自称完整的请求参数表里**没有 `seed`**，留存的响应报文顶层只有 `model / created / data / usage`，`data[0]` 只有 `{url, size}`；仓库里那份调用脚本从不设置、也从不读取它。
2. **多图参考带来的身份一致性**。这是本产品的核心卖点，`image` 参数被当作身份一致性的主要承载，但留存的端到端实测是**纯文生图，一次都没带过参考图**。上限（≤14 张、≤30MB、≤6000×6000）同样没有任何证据。
3. **`negative_prompt` 是否真的不被支持**。它决定了 prompt 工程"所有禁止项必须正向改写"这条路是不是唯一出路；现在这个结论来自推断而非报错。

前一条决定 schema 里一个列该不该存在、以及能不能对外说"可复现"；第二条决定产品的核心承诺有没有支撑。把没有证据的能力写成契约，代价是 AI 工人会照着实现一个不存在的行为。

## Solution

做三条最小实测，把结论写进一页能力台账，并在施工纪律里加一道闸门：**未验证的上游能力不得进 schema、不得进检查项、不得进对外承诺**。

实测不求覆盖参数矩阵，只求回答三个是/否问题，每条都留存原始请求与响应报文作为证据。台账一行一条能力，记录证据等级、影响面与"若不支持则怎么降级"。有了它，"可复现"该怎么说、`seed` 列该不该留、身份一致性能不能当卖点，都不再需要猜。

## User Stories

1. 作为产品所有者，我希望在开工前知道"生成图仍然像本人"这句话有没有实测支撑，以便不把核心卖点建立在假设上。
2. 作为产品所有者，我希望知道"可复现"到底能不能承诺，以便不对外说一句兑现不了的话。
3. 作为 AI 工人，我希望明确 `generation_results` 里 seed 列的语义，以便不会实现一个永远为空的字段还给它写测试。
4. 作为 AI 工人，我希望明确参考图的上限与真实效果，以便不会按未经证实的限制去写校验。
5. 作为 AI 工人，我希望明确禁止项是否必须全部正向改写，以便不会为一条不存在的通路做兼容。
6. 作为 AI 工人，我希望未被验证的能力在文档里带着"未验证"的标记，以便不会把它当成既定事实照做。
7. 作为维护者，我希望每条上游能力都有一个证据等级（已验证 / 间接验证 / 无证据 / 与证据冲突），以便评审时不必重新考古。
8. 作为维护者，我希望每条能力都记录"若不成立时的降级方案"，以便结论为否时不必重新开会决定怎么办。
9. 作为维护者，我希望实测的原始报文被留存成文件，以便结论可复核而不是口口相传。
10. 作为评审者，我希望台账能一眼看出哪些结论是推断出来的，以便区分"测过"和"看起来像"。
11. 作为评审者，我希望 schema 里的每一列都能追到它的证据来源，以便不会再有"实现了上游不存在的行为"这类缺陷。
12. 作为合规负责人，我希望"不用于训练""照片不被留存"这类对外表述依赖的调用参数是确认过的，以便表述与真实调用一致。

## Implementation Decisions

### 三条最小实测

每条只回答一个是/否，并留存原始请求与响应：

1. **`seed` 探针**：带 `seed` 发一次生图请求。观察三件事——是否被拒（参数错误）？响应里是否回传 seed？同一 seed 连发两次是否得到相同图片（比较结果文件的哈希）？三种结果分别对应三种处置，测完即定，不留中间态。
2. **参考图探针**：带 1 张预处理图发一次生成请求。这是三条里最重要的一条——它验证的正是产品的核心承诺。除"请求是否成功"外，要留存结果图供人工判断身份一致性；顺带把上限相关的假设（张数、单图体积）标注为"本次未覆盖"而不是自动成立。
3. **`negative_prompt` 探针**：请求里带 `negative_prompt`。被拒则为"确实不支持"，正向化改写是唯一出路；被接受则说明现有 prompt 工程的一条前提是错的，必须回改。

三条都复用仓库已有的调用脚本与留存约定，不新建一套冒烟框架。

### 结论的回写规则

- `seed` 被接受且回传 → 保留列并记录；被拒或不回传 → **删掉该列与该字段**，把"历史结果永远可以复现"改为"同一组输入（prompt、参考图、模型、尺寸）可重新提交复现"。
- 参考图不可用或身份一致性不成立 → 回改链路铁律与生成端点里参考图的定义，并重新评估产品定位。
- `negative_prompt` 被接受 → 回改 prompt 工程的"全正面化改写"章节，并检查所有正向化约束是否过度。
- 任何"未验证"的能力在台账里保持"未验证"标记，**不得**在 schema、检查项或对外表述中被当成已知事实。

### 台账形态

单页，一行一条能力，字段为：能力名 / 证据等级 / 证据位置 / 对实现的影响 / 不成立时的降级方案。证据等级取四值：已验证、间接验证、无证据、与证据冲突。台账只承载上游能力，不承载产品需求差异。

### 闸门

在施工纪律中加入一条：上游能力在进入 schema、检查项或对外承诺之前，必须有一条台账记录且证据等级不是"无证据"。已在契约里被当作事实的未验证项（`seed` 列、多图参考上限、`negative_prompt` 不支持）在实测前一律降级为"待验证"，并在文档里带上标记。

## Testing Decisions

**什么是好测试**：上游能力的验证对象是**外部服务的真实行为**，因此好测试的定义与通常相反——它必须真的发请求，必须留存原始报文，必须能被第三方复核；不能用 mock 回放冒充证据（mock 只能验证我们自己的代码如何处理某个假设的结果，不能验证上游是否真的那样返回）。

**测什么**：

- 三条探针各自独立运行、各自输出原始请求与响应到文件，结论不依赖运行者的主观印象（同 seed 是否同图用文件哈希比较）。
- 只有第 2 条包含主观判断（身份像不像），因此它的产出是"材料 + 人眼结论"，不追求自动化。
- 台账落地后，可在文档校验层加一条断言：schema 中被引用为"复现依据"的列，必须在台账里有非"无证据"的等级。这属于契约收敛那一侧的接缝，不在本 spec 的产出里。

**已有先例**：仓库里已有两份留存报文与一份调用脚本，可直接作为报文格式与存放位置的先例；结论文件沿用同一处。

**接缝说明**：本 spec 的唯一接缝是**真实的上游调用**，不存在更浅的替代品——把这条接缝换成 mock，验证就退化成了对既有假设的重述。

## Out of Scope

- 评估生成质量、美感、年代一致性等需要人眼评审的指标（那是盲测材料与评分表的事）。
- 覆盖完整的参数矩阵（尺寸上下限、宽高比、输出格式、水印、优化模式等）——只在探针顺带被观察到时记录。
- 产品代码实现与自动化验收脚本。
- 与上游需求的逐项差异登记（那是契约收敛那一侧的事）。
- 取消任何已规划的功能：本 spec 只负责让结论有证据，功能范围由产品决定。

## Further Notes

- 需要可用的上游凭证；没有凭证时本 spec 无法开始，且**不得**以 mock 结论代替。
- 三条探针的最小形态各只需一次调用，合计是分钟级的工作量；唯一稀缺的是凭证与人眼判断第 2 条结果的耐心。
- 第 2 条的结论会直接影响产品定位是否成立，因此它的优先级高于另外两条；若时间只够一条，做第 2 条。
- 台账是"未验证能力不得进契约"这道闸门的载体，因此它必须在契约收敛完成之前建立——否则契约收敛会继续把未验证的假设当成事实固化下来。
